# 离线视频转码工具与详情页兼容性提示

日期：2026-10-05（北京时间）
状态：proposed
关联需求：尚未新增 PRD requirement；本轮先讨论工具设计，随后再决定实施与详情页集成。

## 1. 用户诉求与讨论边界

用户提出：当影片默认播放需要转码时，详情页显示可点击的「建议转码」标签；「更多」菜单提供「将视频转码」工具。先设计转码工具，再集成入口。工作文件不建议生成在影片原目录，原因是对机械硬盘写入性能存疑。

本方案提供一次生成、后续复用的兼容副本，减少重复实时编码。用户已在本轮明确选择：**SSD 只作工作盘，完成后把兼容副本复制到资料库的独立目录，保留原片。** 这是已确认的存储约束；工具整体方案仍处于讨论阶段，未获准进入业务实现。

本轮只新增设计及文档索引。未添加 HTTP API、配置项、数据库迁移、UI 入口或后台转码任务；不把讨论方案标为已实现。

## 2. 当前代码能够复用的基础

| 当前基础 | 源码证据 | 对工具的意义与边界 |
| --- | --- | --- |
| 按媒体信息、浏览器 codec 能力和播放设置选择直放、remux、transcode | `backend/internal/app/playback_decision.go` | 可复用判断；HLS 并不等于重新编码，策略强制推流也不等于源文件必须转换 |
| 播放描述符携带 sessionKind、reasonCode、源容器与音视频 codec | `backend/internal/app/app.go` 的 `resolvePlayback` / `buildDirectPlaybackDescriptor` | 能给提示提供理由，但现有 descriptor 请求可能实际启动 FFmpeg，不能拿它当详情页只读探测接口 |
| ffprobe 结果的内存及 SQLite 缓存，按路径、大小、mtime 与 schema 检查 | `backend/internal/playback/media_probe.go`、`backend/internal/storage/media_probe_cache.go` | 可复用轻量探测；目前字段不足以可靠判断像素格式、HDR、尺寸、完整音轨及字幕，离线工具需要更完整的探测 |
| FFmpeg 可执行文件解析与硬件编码器试运行探测 | `backend/internal/playback/ffmpeg_command.go`、`encoder_probe.go` | 可复用能力发现；具体分辨率、像素格式及滤镜仍需按任务验证，不凭编码器名称承诺性能或兼容性 |
| HLS 会话有临时目录、节流及结束清理 | `backend/internal/playback/manager.go`、`backend/internal/config/config.go` | 当前产物是播放会话临时分片；持久 MP4 需要独立任务和目录，不能纳入会话清理 |
| 通用内存任务注册表、task.updated 与 Restore | `backend/internal/tasks/manager.go` | 可复用任务展示与事件；长任务及成品关系须另行持久化，注册表本身不提供磁盘上的恢复保证 |
| 同一作品多个稳定 fileId、独立文件进度、详情选择分部 | `backend/internal/storage/movie_files.go`、`backend/internal/contracts/movie_files.go`、`src/components/jav-library/DetailPanel.vue` | 转码对象必须绑定 fileId；成品是该文件的衍生版本，不是新分部 |
| 前端 LibraryService 契约及 Web / Mock 分层 | `src/services/contracts/library-service.ts` | 新能力经服务层进入 UI；业务转码在 Server 执行，不进入 Electron 业务 IPC |

现有播放诊断作为辅助证据，不能直接把「上次使用 transcode-hls」永久固化为作品标签：它可能来自不同客户端能力、用户强制模式或 remux 运行失败。

## 3. 工具输出与自动选择

工具在用户侧以「将视频转码」进入，面板说明目标是生成兼容版本。默认采用最少必要的处理，并在开始前展示具体动作。

| 源文件情况 | 推荐处理 | 画质与速度含义 |
| --- | --- | --- |
| 视频、音频、时间轴均可直接播放 | 提示已有兼容源；不推荐重复处理 | 用户仍可显式选择生成标准兼容版本 |
| 仅容器不兼容，音视频码流可安全放进 MP4 | 换封装为 MP4，复制视频与音频码流 | 音视频不重编码，通常较快；需验证目标容器、客户端及时间轴 |
| 视频可用，音频不兼容 | 复制视频，音频转 AAC | 避免重编码视频；例如 H.264 + AC3，不能只因现有 remux-hls 可运行就认定离线 MP4 适用 |
| 视频 codec / 像素格式不兼容，或确需修复异常时间轴 | 视频转 H.264，按需转换音频 | 有损重新编码；目标是减少未来播放开销，并不改善原始画质 |
| 仅设置强制 HLS，源本身正常可播 | 展示播放策略原因，不标建议转码 | 可以手动生成版本，但不制造源文件问题 |
| 媒体探测失败或信息不足 | 显示尚未完成检测及可重试状态 | 不把未知当作确定需要重新编码；不能因扩展名猜测后自动开始 |

首版建议一个「通用兼容」预设：MP4 + H.264、8-bit yuv420p、AAC 或已验证的兼容音频，带 faststart。默认保留原分辨率、宽高比和正常帧率，不放大，不默认降至 1080p。重编码属于有损处理；HEVC 改 H.264 后体积可能明显增加，不能承诺压缩或固定质量。

质量档初始可用软件 x264 的中等速度 / CRF 20–22 作为调优起点；硬件编码采用各自的质量参数，经样片比较后固化。不同编码器的 CRF / CQ 数值不能视为相同画质。复用硬件能力探测，失败后提示并允许重新开始软件编码，不在同一个 MP4 中途切编码器。

HDR / Dolby Vision、隔行、旋转元数据、异常 VFR、超出编码器限制的尺寸需要明确处理。首版通用 SDR 预设检测到 HDR 时应提示暂不支持自动转换；后续独立加入经过验证的色调映射预设，避免静默丢失色彩信息。正常 VFR 不一律强改 CFR，修复负 PTS 等已确认问题时才采用经过验证的时间轴方案。

完整探测应列出多音轨、字幕、章节及语言信息。首版默认处理选定主音轨；有其它轨道时开始前明确提示保留范围，用户须选择或确认。不能静默丢弃额外音轨、图形字幕或默认烧入字幕。多轨无损保留、外置字幕及字幕转制可作为独立后续能力。

## 4. 存储：工作目录与成品目录分离

建议由 Server 本机配置两个绝对目录：

- **工作目录**：优先选本机 SSD，存放每个任务的临时 MP4、探测快照及必要诊断。
- **成品目录**：位于资料库的独立持久目录，按用户选择接收 SSD 工作盘复制来的兼容副本。若资料库在机械硬盘，最终复制由该盘写入；SSD 不长期保存已提交成品。

示意路径仅用于设计，不能直接写入实际配置：

```text
E:\CuratedWork\transcode\<jobId>\output.partial.mp4
D:\Library\_curated-compatible\<movieId>\<fileId>\<profileVersion>\video.mp4
```

Server 可以位于另一台机器。上述目录与 FFmpeg 均属于 Server，客户端的 SSD 不会自动成为 Server 工作盘。Electron 本地目录选择只在直连本机 Server 时适用；远端不得用客户端路径修改 Server 目录。

### 已确认的运行方式与备选

| 方式 | 写入流程 | 适用情形 |
| --- | --- | --- |
| **本轮确认：SSD 工作，资料库独立目录保存成品** | 读取原片 → SSD 编码 / 校验 → 资料库临时目标复制 / 校验 → 在目标盘改名提交 → 登记关系 → 清理本任务 SSD 临时文件 | SSD 用作工作盘；最后复制仍受资料库盘写入速度影响，但不与本任务编码阶段混在一起 |
| 备选：工作及成品留 SSD | 读取原片 → SSD 编码 → 校验 → 提交成品 → 登记关系 | 仅作为其它部署的可选方式，不作为本轮默认行为 |

直接从 HDD 连续读片源一般是合理起点，无需默认把完整源文件也搬到 SSD。同盘并发读取、其它扫描和网络读取可能影响速度；实测显示源读取成为瓶颈时，再增加「先复制源文件到工作盘」选项。

不能仅凭 HDD / SSD 名称判断是否够用。近似吞吐需求为：`(源平均码率 + 输出平均码率) × 编码倍速 ÷ 8` MB/s，适用于同盘同时读写的粗略估计，未计入寻道和其它负载。例如源 30 Mb/s、输出 12 Mb/s、编码 5×，约为 26.25 MB/s；这是计算示例，不是本机性能测量。机械硬盘顺序写入可能满足需求，主要不确定性还包括同盘混合读写、并发、源盘读取及编码器速度。

### 空间与清理规则

创建任务前检查可写性、卷可用空间、任务预计峰值和保留余量。CRF 输出大小未知，展示范围而非精确值，运行中继续检查空间与输出字节上限。faststart 重写或跨盘复制可能额外占用空间，应计入峰值。

空间示例：两小时视频若平均视频码率 8 Mb/s，视频约 7.2 GB（十进制），再加音频和封装开销；AAC 192 kb/s 约再占 0.173 GB。H.264 副本可能比原 HEVC 更大。工作盘和成品盘分开时要分别核算容量。

临时任务有配额及过期清理；清理仅处理工具自己记录和拥有的临时文件。**兼容成品是持久文件，不随缓存清理或 HLS 会话结束自动删除。** 提供成品占用和删除入口；删除时先检查播放引用，仅删除兼容副本并解除关联。源文件始终保留。

工作目录默认不在普通扫描根下；本轮成品位于资料库的独立子目录，因此扫描 / 监听 / 整理必须在遍历时排除已管理的衍生目录，避免错误创建分部或对成品再次整理。不能依赖文件名后缀避免误入库。成功发布并登记后清理本任务工作文件；复制失败保留已校验的 SSD 输出以便只重试发布，受明确的临时文件配额和保留期限管理。

## 5. 任务机制、校验与资源分配

任务阶段建议为：`queued → probing → encoding/remuxing → validating → publishing → completed`。`copying` 可作为跨盘发布子阶段；另有 `failed`、`cancelled`、`interrupted`。这些是离线任务的详细状态，对通用 TaskDTO 做投影，不把当前任务枚举已支持这些状态当作事实。

首版提供排队、取消、失败重试和查看结果；不承诺普通单文件 MP4 的断点续编码。显示已处理时长 / 全片时长、FFmpeg speed、输出大小、当前阶段；预计剩余时间只在速度趋稳后给出，换封装及复制按各自阶段显示。编码达到末尾后仍有校验及发布，全部完成前进度不得显示为完成。

持久记录源 fileId、源指纹、预设版本、输出轨道选择、任务阶段、工作路径、成品路径及错误分类。Server 启动恢复排队任务；编码中断任务变为 interrupted，由用户重试并从头编码。不得宣称重启后可继续写入半个 MP4。

跨文件系统发布使用：复制到目标卷内由任务独占的临时名称 → 检查大小 / 校验复制字节 → 同卷改名 → SQLite 事务登记成品。不能把跨盘 move 当原子操作。工作文件和最终文件都不覆盖已有文件；命名含任务或不可变版本标识。

发布提交点与崩溃恢复需明确：重启时对账已改名但未入库的工具成品、已入库但文件缺失的记录、验证后尚未复制完成的任务。只有通过校验且登记成功的版本可以被自动选中；对账失败保留诊断和人工重试入口。

完成校验包含：FFmpeg 正常退出、非空目标、完整 ffprobe、选定轨道与目标 codec / 像素格式、时长在容许误差内、开始 / 中段 / 尾段解码抽检。抽检不是逐帧完整校验，不宣称它证明全片绝无损坏；首次预设验收增加代表性文件的完整解码。跨盘校验验证复制一致性，不能把容器探测当作字节一致性检查。

转码开始及登记前检查源大小、mtime 和文件身份；发现被替换或删除，停止发布并提示源已变化。复用现有 size / mtime 作为基础守卫，同时评估同大小 / 同 mtime 替换风险；转码结果复用可额外记录采样指纹，严格去重时需全文件哈希，不能称前两项是内容哈希。对源改名与整理建立文件操作协调，活跃任务读取的源不得被不协调移动。

默认只运行一个离线编码任务。实时 HLS 与离线任务共享资源调度，播放准备优先；活跃 HLS 时可推迟新离线任务，已在运行的离线任务须通过可取消的进程控制或明确资源限制协调。仅调低进程优先级不能保证 GPU 编码会话、VRAM 或 HDD 带宽不冲突；这部分须真实设备验收。暂停 / 恢复编码若实现，必须验证控制对象和恢复可靠性，不能仅在 UI 改状态。首版可以只提供取消与重新开始，避免承诺可靠暂停。

离线任务可以以设备能力允许的速度处理，不照搬实时 HLS 的 readrate 或领先播放器节流。仍需要单任务并发、磁盘配额和播放优先的资源约束。

## 6. 成品关系与播放接入

建议独立关系 `source fileId → compatible rendition`，成品不加入 `movie_files` 分部集合。一部影片两段源文件分别生成两个兼容版本；任务去重按「fileId + 源指纹 + 预设版本 + 轨道选择」判断，并保持幂等。

播放选择顺序：已校验且当前客户端可用的兼容版本（用户选择优先使用）→ 原片直放 → 原片实时 remux / transcode。兼容版仍需客户端能力判断，高分辨率 H.264 不保证每台设备都能解码；转换生成也不保证网络带宽足够。文件存在但打开失败时重新判断源路径，不在循环中无限回退。

沿用原 fileId 的播放进度、历史、收藏和评分，不能创建新的作品或分部。成品保持完整内容和时间轴原点，不剪片；时长 / 时间轴差异超出容差的版本不能共享秒级进度。萃取帧保存原 source fileId 与位置，若使用兼容版读取，必须保留版本信息；转码本身不改写既有萃取帧时间。

兼容版路径缺失或源指纹变化时不继续自动选中。已开启播放保持当前源直到结束 / 下次主动换源，不在任务完成时强制中断正在播放的视频。副本删除、源文件离线、源文件主动删除后的独立使用策略需要分别定义；首版仍要求有效源关系，不把兼容目录自动当独立资料库。

## 7. 详情页标签与更多菜单

增加不启动播放会话的只读兼容性评估接口，复用纯播放决策及媒体探测缓存。评估同时给出「当前默认播放路径」和「源兼容性原因」，防止 force_stream_push 掩盖实际原因。不能为了标签调用当前可能启动 FFmpeg HLS 会话的 GET /playback。

只在详情页按当前选定 fileId 懒加载 / 探测；浏览器能力变化或文件变化时重算，不遍历全库后台转码。canPlayType 只是能力信号，profile / level / 位深及实际解码仍有不确定性，提示不宣称保证。

| 评估 / 任务状态 | 推荐界面 |
| --- | --- |
| 当前客户端默认需要视频 / 音频重编码，且确实由源兼容性问题导致 | 主操作或技术信息旁「建议转码」，展开说明当前设备理由及预计动作 |
| 仅需换封装 | 「建议转换封装」；工具内显示「换封装，不重新编码视频」 |
| 设置强制推流，源可直放 | 不显示建议转码，可在播放诊断说明设置原因 |
| 探测未知 / 失败 | 不展示确定性标签；菜单仍可打开检测及工具 |
| 排队 / 处理中 | 「等待转码」 / 「正在转码」，点击打开同一任务 |
| 有可用兼容版 | 「已有兼容版本」，允许查看、选择源与管理成品 |

该标记属于系统技术状态，和用户标签 / 元数据题材分开；换文件时跟随选定文件更新。必要时作品级摘要可显示「2 个文件中 1 个建议转码」，不能把某分部结果套给整片。

「建议转码」点击和「更多 → 将视频转码」进入同一个面板。第一步检测，展示源文件 / 分部、理由、推荐处理、预设、轨道保留范围、成品位置、空间预估和原片保留说明，再由用户按「开始」创建任务。已存在相同任务直接查看；已有相同有效成品优先提示使用，不重复编码。

菜单可对可直放影片手动开放，回收站 / 只读预览 / 无源文件时给出对应禁用原因。目录配置和任意路径管理延续 Server-local 的管理权限；如开放远端启动任务，只能使用服务端已配置目录和预设，并由后端检查业务权限、文件归属、配额及去重，不能接受远端任意路径或任意 FFmpeg 参数。是否首版开放远端创建仍是待决定范围，远端读提示和播放兼容版不依赖目录写权限。

普通任务状态在任务列表内显示；成功 / 失败 / 空间不足等可行动状态进入消息中心，进度不反复弹 toast。页面离开不取消 Server 任务，回来通过持久任务状态恢复显示。Mock 只模拟检测与任务，不生成真实文件，不把模拟成功当作转码验收。

## 8. 建议分阶段实施

1. **先定工具行为与用样片验证**：落实已确认的 SSD 工作 / 资料库独立目录成品 / 保留原片策略，确定 Server 工作盘、质量预设与主音轨范围；使用当前最常触发转码的代表性文件进行只读探测，并在独立目录验证转换输出、画质、速度、峰值空间和目标设备播放。样片须经用户指定，不能擅自覆盖或改动真实片源。
2. **实现离线任务与存储发布**：新 DTO / 错误代码、SQLite 任务与成品记录、队列、取消 / 重试、磁盘预检、资源协调、校验及崩溃对账。通过暂时的内部验收入口验证工具闭环，尚不依赖详情标签。
3. **接入成品读取与播放选择**：以原 fileId 关联兼容版本、Range 播放、续播及原片回退，排除扫描误入库。此阶段完成后用户转换一次才能获得后续播放收益。
4. **最后集成详情页**：只读评估、可点击状态标记、更多菜单、同一工具面板与任务中心。按现有 Vue / shadcn-vue 规范实现并验证多文件、移动布局、键盘操作和多语言。

决定实施时再新增稳定 REQ-xxxx、明确验收标准，把状态改为 approved / in-progress。技术拆分按最小行为单元提交，API / 配置落地后同步项目事实、配置说明和 API 文档；不在设计阶段写成已经存在的端点或配置键。

## 9. 验收重点与首版范围

首版建议：用户主动发起、单源文件 / 当前分部、一个通用兼容预设、自动最少必要处理、保留原片、独立成品目录、持久任务、取消 / 重新开始、有效副本的播放选择、标签和更多菜单。整库自动转换、默认替换原片、完整编辑器、任意命令行、HDR 转 SDR、多码率和精确断点续编码不纳入首版建议。

实施时需要验证以下行为，测试不应只重复函数实现：

- MKV H.264 + AAC 优先换封装；H.264 + 不兼容音频只转音频；不兼容视频或确需修复的时间轴才重编码。force HLS 不产生误导标签，探测失败不产生确定判断。
- 独立工作盘 / 成品盘、同卷发布和跨盘复制、写满 / 不可写 / 目标离线、取消与 Server 重启，不改变或截断源文件。
- 源文件转码中被替换、整理改名协调、重复创建、多客户端提交及原指纹变化，不发布错误关系或重编码同一任务。
- 同番号多分部只更新被选中的 fileId；重新扫描、目录监听、自动整理不会把兼容版当新分部。
- 输出开始 / 中段 / 结尾可播、目标浏览器能解码、时长 / A/V 同步及正常 / 异常帧率符合预设；画质与真实 GPU / HDD / SSD 性能用样片验收，不凭单测宣称。
- 实时 HLS 与后台转码争用时播放优先，副本完成不突然中断当前播放；兼容版丢失能回退原播放方案，原 fileId 的进度 / 历史与萃取位置保持正确。

本次为源码审查与方案沉淀，未实际运行影片转码、磁盘测速或目标设备播放验收。仅进行文档 diff、索引和路径一致性检查。

## 10. 已确认选择与后续讨论

**已确认：SSD 只作工作盘，完成后兼容副本复制到资料库独立目录，保留原片。** 因此最终复制、校验、成品登记、扫描排除和成功后的工作文件清理属于首版工具闭环，不能只做编码后把 SSD 路径交给用户。

后续讨论首版的远端任务权限、音轨 / 字幕保留范围和代表性样片。通用兼容预设、默认最少必要处理和优先播放有效副本为当前建议；若用户之后改变保留原片的决定，再单独设计备份、验证、文件操作锁及关系迁移流程。

## 11. Jellyfin 处理方式与可借鉴边界（2026-10-05）

用户追问 Jellyfin 如何处理。以下来自本轮读取的 Jellyfin 官方文档与服务端 `v12.1` 源码；GitHub latest release 查询返回该 tag。官方在线文档可能随版本更新，源码链接固定 tag。未实际部署 Jellyfin 或运行媒体性能对比，不把插件 / 第三方工具能力当作服务端原生播放功能。

### 11.1 按客户端能力选择四条播放路径

官方 [Transcoding](https://jellyfin.org/docs/general/post-install/transcoding/) 把播放路径按负载区分为：

| Jellyfin 路径 | 实际处理 | 对本方案的启示 |
| --- | --- | --- |
| Direct Play | 直接交付原文件 | 能直放就无需转换 |
| Remux | 改容器，保留音视频码流 | 将换封装与重新编码分开 |
| Direct Stream | 重新编码音频，保留视频 | 首版评估应支持只转音频 |
| Transcode | 重新编码视频，音频按需处理 | 重编码只用于实际必要的情况 |

客户端提供 codec、分辨率、码率等约束，服务端据此选择输出；所以「需要转码」属于当前播放条件，不是作品永久属性。带宽限制、字幕需要烧入、视频 profile / level / 位深 / HDR 等也可能触发转码，不能只按扩展名或视频 codec 判定。

源码 [TranscodeReason](https://github.com/jellyfin/jellyfin/blob/v12.1/MediaBrowser.Model/Session/TranscodeReason.cs) 对这些原因分项表达；[MediaInfoHelper](https://github.com/jellyfin/jellyfin/blob/v12.1/Jellyfin.Api/Helpers/MediaInfoHelper.cs) 处理播放媒体源与设备能力。Curated 可以借鉴结构化原因，但为字幕烧入或客户端带宽不足生成永久副本，需要用户选择相应预设，不能把任意实时转码理由都直接转成默认重编码建议。

### 11.2 转码目录是可配置的临时工作目录

Jellyfin 的 `EncodingOptions.TranscodingTempPath` 独立于原片路径；未设置时，源码回退到 `CachePath/transcodes`。服务端从原位置读取文件，FFmpeg 将流式产物写到该临时目录，客户端边生成边读取；标准播放流程不修改源文件。

官方硬件加速说明明确建议：当现代 GPU 编码速度受硬盘 I/O 限制时，用 **SSD 或 RAMDisk 缓存转码临时视频分片**。这支持本方案使用 SSD 工作盘，但并不表示把完整源文件自动复制到 SSD，也不表示所有 HDD 都无法满足顺序写入需求。

来源：[临时目录解析源码](https://github.com/jellyfin/jellyfin/blob/v12.1/MediaBrowser.Common/Configuration/EncodingConfigurationExtensions.cs)、[Hardware Acceleration — Speed And Quality](https://jellyfin.org/docs/general/post-install/transcoding/hardware-acceleration/)。本方案处理完整长期成品，首版仍采用磁盘 SSD 工作目录，不因 Jellyfin 支持 RAMDisk 就默认依赖内存盘。

### 11.3 节流与清理服务于播放会话

Jellyfin 实时转码有编码领先下载进度时的节流，以及旧 HLS 分片清理选项。`v12.1` 的 `EncodingOptions` 构造默认 `EnableThrottling=false`、`EnableSegmentDeletion=false`；配置中存在这些能力不代表新安装默认启用。节流启动还检查 FFmpeg 暂停能力 / 兼容版本，不能把其 stdin 控制命令直接复制给任意 FFmpeg。

会话管理会在停止 / 超时等路径结束编码任务并按规则删除相关临时产物；另有 `DeleteTranscodeFileTask`，默认启动和每 24 小时触发，清理最后写入超过一天的临时文件。旧分片清理是独立可配置机制，不应把「启动 / 周期清理」描述成每个分片都会马上删除。

来源：[EncodingOptions](https://github.com/jellyfin/jellyfin/blob/v12.1/MediaBrowser.Model/Configuration/EncodingOptions.cs)、[TranscodeManager](https://github.com/jellyfin/jellyfin/blob/v12.1/MediaBrowser.MediaEncoding/Transcoding/TranscodeManager.cs)、[TranscodingSegmentCleaner](https://github.com/jellyfin/jellyfin/blob/v12.1/MediaBrowser.Controller/MediaEncoding/TranscodingSegmentCleaner.cs)、[DeleteTranscodeFileTask](https://github.com/jellyfin/jellyfin/blob/v12.1/Emby.Server.Implementations/ScheduledTasks/Tasks/DeleteTranscodeFileTask.cs)。

这些产物是当前播放过程的缓存，不构成「转换一次，以后保证直接使用」的持久兼容版本；后续播放仍可能重新转码。Curated 的实时 HLS 清理与离线成品清理必须分开，不能将已发布 MP4 放进播放临时目录后依赖其存留。

### 11.4 永久副本采用现有多版本能力承载

Jellyfin 官方 [Movies — Multiple Versions](https://jellyfin.org/docs/general/server/media/movies/#multiple-versions) 支持识别已存在的多版本文件：同一影片目录内按父目录完整名称前缀及版本标签命名。文档说明版本选择列表及默认排序；它不是自动生成永久版本的说明，也不能据此宣称系统总会自动选中最易播放的版本。服务端还提供 [MergeVersions](https://github.com/jellyfin/jellyfin/blob/v12.1/Jellyfin.Api/Controllers/VideosController.cs) 将现有条目关联。

标准实时转码路径没有「SSD 编码完成 → 复制到资料库 → 登记永久副本」发布步骤。要长期预转换，可以由 FFmpeg / HandBrake 等外部转换流程先生成文件，再按 Jellyfin 多版本规则或显式关联管理；插件能力需单独评估，不能混为本次已核实的核心功能。

Curated 已有同番号多分部，用户又选择将成品放在资料库独立目录，因此不直接照搬 Jellyfin 的同目录命名推断：采用原 `fileId` 到兼容版本的显式关系，并排除成品目录扫描，更能避免把兼容版误认成新分部。

### 11.5 对当前方案的结论

保留用户已确认的 **SSD 工作 → 校验 → 资料库独立目录复制 / 校验 → 登记副本 → 清理工作文件，原片保留**。借鉴 Jellyfin 的客户端能力协商、四级最少必要处理、独立临时目录、编码器能力检查与会话清理；持久任务、发布校验、衍生版本关联及后续播放选择仍是本工具需要单独实现的部分。此次研究没有扩大获准实施范围，文档仍为 proposed。
