# 消息中心：从事件归档到系统发言

日期：2026-08-14
状态：research

上位文档：[2026-05-01-notification-center-prd.md](2026-05-01-notification-center-prd.md)、[2026-05-02-notification-center-overflow-analysis.md](2026-05-02-notification-center-overflow-analysis.md)
后续方案：[2026-08-14-message-center-repair-plan.md](2026-08-14-message-center-repair-plan.md)（REQ-0024）

本文不是实施清单。它记录一次产品反思：现有「通知中心」为什么用得上的感觉很弱，以及它真正该替用户做什么。

## 本轮已落地（文案与入口）

用户可见名称从「通知中心」改为「消息中心」；顶栏图标从铃铛改为对话气泡（Lucide `MessageSquare`）。内部模块名、`localStorage` key、i18n 命名空间仍是 `notificationCenter`，避免无行为变更的大重构。

改名本身不是功能升级，但它点出了旧隐喻的问题：铃铛暗示「打断你」，消息暗示「系统留给你一句话」。

## 现状：消息被拆成了四套口

Curated 里用户感知后台工作，并不走一条通道：

```
后台真实在做什么
        │
        ├── 进行中 ──▶ 右下角 ScanProgressDock / 批量条 / loading toast
        ├── 刚结束 ──▶ 右上角 toast（4.5s 消失）
        ├── 部分终态 ──▶ 顶栏消息中心（localStorage，7 天 / 200 条）
        └── 持续状态 ──▶ Settings 行内、侧栏 New badge、资料库阻断
```

消息中心当前写入点大致是：

| 来源 | 写入什么 | 用户真正需要知道的是不是这个 |
|---|---|---|
| 手动扫描开始 / 完成 / 失败 | 任务终态标题 | 开始几乎不需要；完成要看「有没有新片 / 失败了什么」 |
| 目录监听扫描 / 关联刮削 | 同上 | 连扫多片时容易变成流水账 |
| 单部刮削终态 | 资料已更新 / 失败 | 有用，但缺少「为什么失败、下一步」 |
| 导入终态 | 完成 / 失败 | 有用 |
| 存储离线 | 设备不可达 | 高价值，这是少数真正「需要你」的消息 |
| 更新可用 | 有新版本 | 高价值，但侧栏已经有 New badge，入口重复 |

同时大量 toast **不进**消息中心：批量操作摘要、播放回退、代理保存、备份、健康扫描、演员刮削开始态、字段校验等。2026-05-10 的缺口清单仍然大体成立，但「补全覆盖」已经不是第一问题。

第一问题是：就算全部接上，它也只是 **toast 的冰箱**，不是系统在对用户说话。

## 诊断：为什么感觉「没有完全用得上」

当初的产品定义是：

> 通知 ≠ Toast。Toast 是瞬时浮层，通知是持久化的消息记录。通知中心是二者的桥梁。

这个定义把「消息」做成了 **事件归档**。实现也忠实地跟着走：`pushAppToast(..., { notification })` 才落盘；打开面板即全部已读；行是标题 + 一句结果 + 相对时间。

后果是：

1. **它复述手法，不解释系统。** 「扫描完成」「资料已更新」描述的是一次动作的收尾，不是资料库现在处于什么工作节奏。用户看不到「正在刮 12 部、4 个在排队、JavBus 冷却中」。那些信息散落在 dock、任务 DTO、设置页健康状态里。
2. **它很少做判断。** 「系统认为你需要知道什么」需要编辑权：同一类事件有的该沉默、有的该摘要、有的该升级为需处理。现在几乎没有政策层，调用方各自决定要不要写一行。打开面板等于已读，也削弱了「需处理」的分量。
3. **进行中和已结束被拆开。** 进度在右下角，结果在右上角，历史在顶栏。用户要拼三处才能回答「刚才发生了什么」。
4. **成功默认也占位。** 扫描开始、空扫描完成、刮削成功，都会和存储离线抢同一条未读红点。红点一旦经常亮、点开又没什么要做的，入口就会被学会忽略。

所以不是面板做得不够精致，而是它承担了错误的工作：记录发生过的事，而不是帮助用户理解系统、决定要不要插手。

## 两个产品职责

用户点出的 (a)(b) 可以当成消息中心仅有的两份工作。其它表面都可以从这里推出来。

### (a) 让用户从这里察觉系统怎么在工作

不是把任务日志搬进下拉框，而是给一个 **可读的系统状态**：

- 现在在忙什么（扫描、导入、刮削队列、资源下载）
- 卡在什么上（存储离线、代理失败、provider 冷却、排队等待）
- 刚才安静地做完了什么（一次摘要，而不是 N 条成功）

用户合上应用再打开，或从播放器回到资料库时，顶栏入口应能回答：「Curated 有没有在干活？干活正不正常？」

这和 Settings 里的运维细节不同。设置页给控制权；消息中心给处境感。

### (b) 系统认为用户需要知道什么

不是「所有终态都值得留」，而是系统替用户做一次分拣：

| 层级 | 含义 | 例子 |
|---|---|---|
| 需要你 | 不处理会继续错，或有明确下一步 | 存储离线、导入冲突、刮削因配置/网络系统性失败、更新已下载待安装 |
| 值得知道 | 库发生了可见变化，但不必立刻动手 | 扫描发现 8 部新片、夜间刮削补全了 20 部封面 |
| 可以沉默 | 用户刚操作过、页面上已有反馈、或零变化成功 | 扫描开始、复制路径成功、0 新增的监听扫描、字段校验 |

「需要你」才配红点。「值得知道」进历史，打开时不必制造焦虑。「可以沉默」只留在当场的 toast / 行内，不进中心。

## 若继续演进，比较干净的形态

先不要做成聊天，也不要做成后台任务管理器。更接近：

```
┌─────────────────────────────────────────┐
│  消息中心                               │
├─────────────────────────────────────────┤
│  现在                                   │
│  正在刮削 3 / 12 · JavBus 冷却中 12 分钟 │
│  D: 资料库磁盘离线 · 去设置             │
├─────────────────────────────────────────┤
│  需要你                                 │
│  4 部元数据失败 · 可从健康修复重试      │
│  Curated 1.5.2 已下载 · 去安装          │
├─────────────────────────────────────────┤
│  最近                                   │
│  今晚扫描：+8 部新片，3 部刮削失败      │
└─────────────────────────────────────────┘
```

三块对应三种时间：

- **现在**：活的系统状态，不是一条条已结束事件
- **需要你**：有判断、有动作
- **最近**：压缩后的工作记忆，用来建立信任（系统确实在干活），而不是供审计

这要求消息不再只从 toast 旁路复制，而要从任务 / 存储 / 更新 / 健康等权威状态 **归纳** 出来。SSE `task.updated` 已经存在，缺的是前端（或后端）的归纳层，不是又一条事件管道。

## 明确不做

- 不把所有 toast 补进消息中心。覆盖越全，越像噪音日志。
- 不把 ScanProgressDock 原样搬进下拉框。进度条和「系统在说什么」不是同一 UI。
- 不先做后端持久化 / 多端同步。本机归纳层没想清楚之前，持久化只会把错误模型存得更久。
- 不把打开面板当作「全部已读」。需要你的条目应显式处理或稍后处理；值得知道的条目可以打开即消化。

## 和旧优化清单的关系

[overflow 分析](2026-05-02-notification-center-overflow-analysis.md) 里仍值得保留的是：去重、burst 摘要、可跳转动作、toast / 历史 / 行内三级政策。那些是手段。

过时的默认假设是：「把更多终态接到通知中心，它就会更有用。」在 (a)(b) 之前补覆盖，只会让红点更勤、内容更空。
