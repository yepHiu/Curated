## 3. 需求详述

### REQ-0039 AI 设置与隐私治理面板（P0，批次 A）

**场景**：小雨第一次想用 AI 功能，打开设置，看到"AI"分区：她本机装了 Ollama，填 `http://127.0.0.1:11434/v1` 点"测试连通"即就绪。阿哲更谨慎：他想知道 AI 到底能干什么、干过什么——打开审计页能看到每一次工具调用的记录。

**需求**：Settings 新增「AI」分区：
1. provider 配置：类型（OpenAI 兼容）、baseURL、apiKey、model、连通性测试（交互照搬 proxy ping）；
2. 隐私：脱敏级别（full / sanitized / minimal，云端默认 sanitized，附"本库内容较敏感，本地模型更合适"的明示）；
3. 权限：Agent 写权限总开关（默认关）、低风险直写子开关（默认关）、MCP 写暴露（默认关）；
4. 行为：步数/频控/预算阈值（默认值见 charter §5.4）；
5. 用量统计（请求数/token，按 provider）；审计日志只读视图（时间/工具/参数摘要/结果，异常标红）。

**验收要点**：未配置 provider 时所有 AI 入口降级为引导（P-07）；apiKey 永不进 release 样例配置与日志；审计覆盖含被拒绝调用在内的每次工具调用（P-08）；设置变更即时生效且不可被 Agent 修改（P-03）。

**落实**：B1（`internal/llm` + 配置键进 `library-config.cfg`）+ B2（审计表 0039 与网关）。前端 `SettingsAISection.vue` 挂进现有 settings-nav；Mock 模式提供假配置态。

### REQ-0043 实验性功能门控 + Agent Window（P0，E1）

**场景**：阿哲想尝鲜 Agent 但产品还在验证期：他打开设置，侧栏出现「实验性功能」类目，里面一个「启用 Agent 能力」开关。打开开关，顶栏多出一个 ✦ 图标，同时弹出一个浮动对话窗口（Cursor 的 Agent Window 那样覆盖在页面上）——他就在里面试用各种 Agent 能力。哪天不想用了，关掉开关，所有 Agent 界面消失，应用回到原样。

**需求**：
1. 设置侧栏新增「**实验性功能**」类目（通用实验容器，Agent 是第一个入驻者）；
2. 类目内「**启用 Agent 能力**」开关：默认关；每浏览器状态（localStorage），毕业时迁为后端全局设置键；
3. **gating**：开关关闭时，顶栏入口、就地动作按钮、Agent Window 一律不出现；开启后全部出现；关闭开关中止进行中的流式请求（前端 abort + 后端 ctx 取消）；gating 为纯前端呈现层，后端端点始终注册且受 PIN 保护；
4. **Agent Window**：开启开关后自动弹出一次；Cursor 式浮动窗口——可拖动（标题栏）、可关闭（按钮/Escape）、位置与尺寸记忆、移动端全屏化；内容为流式消息区 + 输入框；E1 单会话，E2 起会话持久化与切换。

**验收要点**：开关关时全应用无任何 Agent UI（组件测试覆盖默认关闭态）；开关状态与窗口位置重启可复现；视觉与工程约束照旧（shadcn-vue、dark、三语、≥44px 触控、懒加载不进首屏）；Mock 模式可用（假流式）。

**落实**：见 [`2026-08-19-agent-milestone-plan.md`](2026-08-19-agent-milestone-plan.md) §1（组件落点：`SettingsExperimentalSection.vue`、`src/components/agent-window/`、`use-experimental-agent.ts`）。E1–E3 期间 Agent Window 是所有 Agent 需求（0032/0040 等）的交互载体；正式 Copilot 抽屉为 E4 毕业期决策项。

### REQ-0029 AI 笔记助手（P0，批次 A）

**场景**：阿哲看完一部片，在详情页笔记框写了句"节奏慢但结尾反转不错，演员阵容强"。他想把口语整理成一条像样的短评——点笔记区的「AI 润色」，出现 diff 预览：AI 整理了措辞、不改事实。他看完点「应用」，笔记保存；也可以点「放弃」回到原文。

**需求**：详情页笔记区（`MovieCommentSection`）只提供 **润色**（整理语言、不改事实、保持原文语言）。结果先 diff 预览，用户确认后写回（走既有 `PUT comment` 语义）。**不做扩写、不做笔记翻译**（2026-08-21 确认）；简介/标题翻译分别是 REQ-0030 / REQ-0041。

**验收要点**：原文在应用前绝不丢失；AI 不得编造笔记中不存在的事实（提示词约束 + 无工具调用，L1 纯文本变换）；同语言润色；未配 provider 时按钮降级；字符上限沿用现有 `MAX_MOVIE_COMMENT_RUNES`；三语 UI；界面上没有扩写或翻译笔记的入口。

**落实**：action preset `polish_comment`，`POST /api/ai/actions/polish_comment`（B7）；模型自行识别原文语言并保持同语言润色；写回经网关 `save_movie_comment` 的 preview→apply（B6），确认动作即 UI diff 确认卡。

### REQ-0030 刮削摘要一键翻译（P0，批次 A）

**场景**：老陈点开一部新刮的片，简介是日文或英文。他不想手翻，点元数据编辑简介框里的「AI 翻译」——预览显示界面语言的简介，确认后保存。原始刮削文本仍在库里可查（展示覆盖设计）。标题框里的「AI 翻译」是另一条独立动作，点简介不会带动标题。

**需求**：详情页/`MovieEditDialog` 提供「AI 翻译简介」：把当前展示简介译到界面语言；结果写入 `user_summary`（展示覆盖列），**永不改动刮削原始列，也不改标题**。

**验收要点**：刮削原始 summary 只读保留，翻译结果可随时通过清空覆盖恢复显示原文；diff 预览；已是目标语言时提示无需翻译；标题翻译与简介翻译互不触发。

**落实**：preset `translate_summary`（L1）；写回走 `update_movie_display_overrides` preview→apply。批量入口随 REQ-0036 批量代理再上。

### REQ-0031 洞察 AI 解读（P0，批次 A）

**场景**：小雨打开"我的洞察"，看到的是卡片数字：本月观看 6.4 小时、完播率 72%、最常看演员是 XX。她能读懂数字但看不出"所以呢"。点「AI 解读」，生成一段话：观看时长环比上升、完播率下降可能因为开了几部没看完的、演员口味从 A 系转向 B 系——并给一条行动建议（"有 3 部看到一半的可以建个续看视图"）。

**需求**：Insights 页（`PersonalInsightsPage`）顶部提供「AI 解读本期数据」：基于当前已选范围（30d/90d/365d/all）的 overview + 三个 breakdown，生成自然语言总结（趋势、结构变化、1～2 条可执行建议），页内卡片渲染。

**验收要点**：只读、无确认卡；解读必须基于真实聚合数据，不得编造数字（结构化输入优先，P-09）；明示数据口径（如 full-per-entity 合计可超 100%、无分母时为 —）；三语输出跟随界面语言。

**落实**：preset `insights_narrative`（L2）：后端拉取 insights 聚合 JSON 作为结构化上下文（不经工具循环，action 内固定数据获取）；前端懒加载渲染组件。

### REQ-0032 Copilot 库管家（P1，批次 B）

**场景合集**（顶栏 ✦ 打开右侧抽屉，可与主内容并排）：
- **统计问答**：小雨问"这个月看了多久？比上个月多吗？"→ Agent 调 insights 工具，答出对比。
- **查找**：阿哲问"XX 演员的片我还有几部没看？"→ search_movies(actor=, playState=unplayed)，回列表摘要并可点开跳详情。
- **决策**："今晚只有 40 分钟，从我没看过的 4 星片里挑一部短的"→ 检索 + 时长过滤 + LLM 决策，给一部及理由（charter 价值主张"翻译+模糊判断"的典型组合）。
- **上下文指代**：在 ABC-123 详情页打开抽屉问"类似这部的还有哪些"——"这部"由上下文注入解析；注入内容在抽屉顶部可见、可清除。

**需求**：全局 Copilot 抽屉（charter §7.1 完整定义）：多轮流式对话、只读工具（查询域 11 组）、工具调用内联卡、上下文注入、会话持久化（新建/切换/清空）。

**验收要点**：答案中的实体可点击跳转（影片/演员路由）；列表类答案展示条数与截断提示（"命中 23 部，显示前 5"）；步数触顶时明确汇报"已完成/未完成"；PIN 锁定随 `/api/*` 一同锁定；Mock 假流式可开发。

**落实**：B3（查询域工具）+ B5（AgentLoop + `/api/ai/chat` SSE + 会话表）；前端 `components/copilot/*` 懒加载、`use-copilot.ts`、独立 fetch+ReadableStream 消费 SSE。

### REQ-0033 一句话视图（P1，批次 C）

**场景**：小雨想在睡前看短片：90 分钟内、自己评过 4 星以上、还没看过。用筛选面板要点七八下。她在 Copilot 里说"帮我建个睡前短片视图：一个半小时以内、我打 4 星以上的、还没看过的"→ Agent 解析成筛选条件，**先展示解析结果卡**（片长 ≤90min、评分 ≥4、未看），她确认后一键创建 Saved View 并跳转资料库应用。

**需求**：Copilot 支持自然语言创建 Saved View：解析 → **可视化确认卡（展示解析出的完整筛选条件，不盲建）** → 确认后 `create_saved_view` 落库并引导应用。

**验收要点**：解析不出时说明缺什么而不是硬建；瞬时导航字段绝不进视图（沿用 saved views v1 规则）；创建后视图出现在现有视图控件里、可按现有方式改名/删除；整个过程走 preview→apply。

**落实**：`create_saved_view`（preview 展示解析后的 filters JSON 人性化渲染，apply 落库）；复用 REQ-0026 加强后的筛选词汇（rating>=、unrated、runtime 等均可表达）。

### REQ-0038 外部 Agent 直连 / MCP（P1，B4 后独立交付）

**场景**：阿哲日常在 Cursor/Claude Desktop 里干活。他不想为查个库切到 Curated——在 MCP 客户端里加上 Curated（设置页一键复制配置 JSON），然后直接问"我库里 XX 演员有几部 4 星以上的"。

**需求**：Curated 作为 MCP server 暴露：stdio（`curated.exe -mode mcp`）与 Streamable HTTP（`/api/mcp`，PIN 保护）两种接法；默认只读工具集；设置页提供配置 JSON 复制与接入指引。

**验收要点**：MCP 客户端可发现工具并完成查询；HTTP 接法受 PIN/CORS/Host 校验保护；默认无任何写工具暴露；不配置内置 provider 也可用（客户端自带模型）。

**落实**：B4（`internal/mcp`，官方 go-sdk 桥接注册表）；工具暴露遵循 P-06（写档需显式开启）。

### REQ-0034 标签归一化管家（P2，批次 C）

**场景**：老陈的库里"巨乳 / 大胸 / Big"是三个标签、"单体 / SOLO"是两个。他对 Copilot 说"帮我整理标签"→ Agent 给出分组建议清单：每组列出成员标签、覆盖影片数、建议保留的规范名与理由，他逐组勾选（或全选）→ 确认应用 → 涉及影片的标签被合并，空标签消失。

**需求**：标签归一化建议流：分组建议（只读）→ 逐组确认 → 批量应用（重打标签 + 清理空标签）。

**验收要点**：建议依据可解释（语义相似 + 共现影片重叠）；应用前展示影响面（每组影响多少影片）；应用走批量写上限与确认协议（>25 转任务）；过程全审计。

**落实**：`suggest_tag_normalizations`（propose）+ `modify_movie_tags` 批量 apply；入口双位置：Copilot 指令 + 资料库批量栏按钮。

### REQ-0035 演员归并助手（P2，批次 C）

**场景**：老陈发现"深田えいい"和"深田咏美"是两个人名条目，影片、头像、统计被拆散。他在演员详情页点「疑似同一人建议」（或在 Copilot 里问"哪些演员可能是同一人"）→ 得到候选清单（依据：名字规范化相似度 + 出演片商/年代重叠）→ 每条直接进现有 `ActorMergeDialog` 走既有 preview/confirm/audit 流程。

**需求**：疑似同一演员候选发现 + 逐条进入现有归并流程。**AI 只负责发现和排序，合并执行完全复用现有 actor merge 管线（含事务、审计、alias 解析）**。

**验收要点**：绝不自动合并；建议列表展示依据；合并后旧名路由到 canonical（现有行为）；canonical/alias 语义与既有 `actor_merge_audits` 一致。

**落实**：`suggest_actor_merges`（propose，LLM 对服务端候选集排序）+ `apply_actor_merge`（复用现有 token 机制，charter §5.7：LLM 不产生 apply 资格）。

### REQ-0036 批量维护代理（P2，批次 C）

**场景**：阿哲对 Copilot 说"把没有封面的片子都重新刮一遍，完了告诉我结果"。Agent 先检索统计（"找到 37 部缺封面"），展示计划卡（预计任务、批量边界），他确认 → 任务入队（ScanProgressDock 可见进度）→ 完成后 Agent 汇报：成功 31、失败 6，失败清单可展开追问。

**需求**：Copilot 指令式批量维护：目标检索 → 计划确认卡 → 触发任务（复用现有刮削任务与并发治理）→ 终态汇报（成功/失败明细）。

**验收要点**：批量 >25 必须转任务（P-10）；循环内不轮询等待（charter §6.4），终态经 `task.updated` SSE 续报；失败明细可追问可重试；与 REQ-0023 的刮削并发治理共用限流。

**落实**：`search_movies`（定位目标）+ `trigger_movie_scrape`（转任务）+ `get_task_status`；复用 Health repairs 的批量确认交互模式。同类指令可扩展：批量翻译简介（REQ-0030 的批量形态）。

### REQ-0037 每周库报告（P2，批次 D）

**场景**：小雨周末收到通知中心的"本周库报告"：观看时长与完播、本周新增、新打的评分、推荐命中情况、一条洞察（"你这周看的片比平均短 20 分钟"）。点开可看全文，历史报告可翻。

**需求**：设置开启后每周自动生成库报告（观看/新增/评分/推荐/一条洞察），产出入通知中心（needs-you/notify-only 按 REQ-0024 与消息目录 REQ-0025 的政策登记），报告历史保留可查。

**验收要点**：生成是后台任务（L4），失败不影响其他功能；报告内容全部来自现有聚合（insights + 库统计），无新增原始数据导出；消息展示遵循 message-catalog 政策（需登记 MSG 条目）；本地 provider 未运行时的缺省处理（跳过并静默记录，不打扰）。

**落实**：任务系统定时 + 报告 preset（复用 REQ-0031 解读生成）；通知中心按现有 Now/Recent 结构分发。

### REQ-0040 会话式选片推荐（P1，批次 B）

**场景**：小雨晚上九点打开 Copilot："今晚想看点轻松的，一个小时内，没看过的。"Agent 结合她最近的口味（insights：常看类型/演员）与真实检索（片长 ≤60、未看）给出 3 部候选卡片，每部一句推荐理由，可点开详情或直接播放。小雨回"第二部看着太老了"，Agent 记住会话内负反馈，换一轮候选。阿哲的用法："从我打过 4 星的演员里，挑一部我还没看的。"

**需求**：Copilot 会话式选片：条件协商 → 真实检索候选集 → 带理由的推荐卡片（跳详情/播放）→ 会话内迭代（负反馈本轮生效）。与首页"每日推荐"（规则算法 v8）**互补不替代**：会话式按需响应，规则式每日供给；推荐结果是会话产物，不写库（用户可自行收藏/评分落地）。

**验收要点**：候选必须来自真实检索且所用条件对用户可见（防"编造影片"）；推荐理由只能引用真实字段（演员/评分/片长/标签）；会话结束推荐即逝、零写入；步数与截断规则照常。

**落实**：纯复用 B3 查询域工具（`search_movies` + `get_insights_*` + `get_movie_detail`）+ B5 循环，**无新工具、无新写路径**；前端在 Copilot 消息流新增"推荐卡片"渲染单元。

### REQ-0041 AI 标题翻译与本地化（P1，批次 A）

**场景**：阿哲库里的标题多是罗马音或生硬直译，看着费劲。他在详情页点「AI 翻译标题」→ 预览给出中文译名（目标语言跟随界面语言，也可手动指定）→ 应用后列表与详情显示译名；原刮雕标题仍在元数据里，清空覆盖即恢复显示原文。

**需求**：详情页/`MovieEditDialog` 提供「AI 翻译标题」：译名写入 `user_title`（展示覆盖列），原 `title` 永不改动；目标语言显式（跟随界面 zh/en/ja 或手动指定）。批量形态（"把这个演员的作品标题都翻成中文"）随批量代理机制（REQ-0036）提供。

**验收要点**：diff 预览后应用；原 title 只读保留；清空覆盖恢复原文；已是目标语言的标题提示无需翻译；三语 UI。

**落实**：preset `translate_title`，写回走 `update_movie_display_overrides` preview→apply；与 REQ-0029/0030 同一机制，边际成本低。

### REQ-0042 AI 用户标签与偏好画像（P1，批次 C）

**场景**：
- 小雨在库页多选最近看的 5 部 → 批量栏「AI 归纳标签」→ 建议如"高颜值""节奏快""适合睡前"（依据元数据、笔记、萃取帧标签）→ 勾选应用到选中影片。
- 老陈想全库整理："帮我把全库按风格打一轮用户标签"→ 批量建议先预览影响面（每个标签覆盖多少部）→ 分批确认（>25 转任务）→ 执行完汇报。
- 偏好画像：小雨在 Insights 或 Copilot 问"我的口味有什么规律"→ 生成画像（常看片商/年代区间/类型结构 + 一条主要变化），画像中的结构化结论可一键沉淀为用户标签。

**需求**：
1. **标签建议**：单部/选中集/全库的 AI 用户标签建议（propose），与既有标签去重合并（同义建议映射到已有标签而非新建重复项）；
2. **批量打标**：预览影响面 → 批量确认 → 任务化执行，全审计；
3. **偏好画像**：只读口味规律报告，结论可选择性地沉淀为标签体系。

**验收要点**：**只写用户标签列，INFO/刮削标签永不触碰**；AI 打的标签带来源标记（如 `ai`），可按来源一键清理；建议可解释（列出依据）；批量上限与任务化遵循 P-10；画像基于真实聚合与检索，口径明示。

**落实**：扩展用户数据写/治理域工具——新增 `suggest_movie_user_tags`（propose）与用户标签写工具（对齐现有 PATCH userTags 语义，与 INFO 标签的 `modify_movie_tags` 分列，不共用）；偏好画像复用 insights 聚合 + 检索；批量执行走 REQ-0036 的任务模式。

### REQ-0044 源站周边：评价、介绍、库外作品（P1，E5）

**场景**：阿哲在 Agent Window 问「这个演员还拍过什么？评价怎么样？」库里只有几部，但 Metatube 源站页和检索里有评分、介绍和更多番号。Agent 先读已刮的 `homepage` / 站点评分，再按演员检索源站作品列表，标出哪些已在库内；需要长评时才打开本轮已经出现的源站 URL。不拿去搜天气或新闻。

**需求**：沿刮削源站补周边，不接通用网页搜索。分三期：暴露已落库的 homepage 与站点评分；`search_provider_titles` 列出库内外番号；可选 `get_source_page` 只读本轮已知 https 源站页。库外作品不得伪装成本地 `movieId`，也不得进入 `present_movies`。

**验收要点**：无锚点（本轮未见的 movieId/演员）的检索被拒绝；无 `search_web`；页面读取拒绝允许名单外的 URL；失败留在工具结果里，非 AI 功能不受影响；Mock 能假跑「还拍过什么」。

**落实**：细则见 [`2026-08-21-agent-provider-related-lookup.md`](2026-08-21-agent-provider-related-lookup.md)。Phase A/B/C 已落地（2026-08-21）。底层复用 Metatube `SearchMovie*` 与已存 `movies.homepage` / `actors.homepage`，出站走现有 `proxyenv`。

### 组合场景：把选中的影片"整理一下"

用户对选中影片说"帮我整理一下"时，**不引入新工具，而是 L3 编排**：Agent 按需组合 REQ-0030 翻译简介 + REQ-0041 翻译标题 + REQ-0042 建议标签，逐项出确认卡后执行。PRD 不为此单立需求（复合是 Agent 规划层的事，即 charter P-04 的产品面表述），其可用性随上述三条需求自然达成。

## 7. 2026-09-30 需求澄清：大规模个人片库的自动组织与自然发现

**状态：原始需求整理，待继续讨论。** 本节补充 REQ-0034、REQ-0042 及选片推荐、Saved Views 的真实使用背景，不代表已实现或已决定实施。暂不变更需求登记状态、既有里程碑和技术选型。用户希望先理解需求，本轮不操作正式库。

### 7.1 用户明确表达的背景与目标

- 正式库已有约 500–600 部影片，无法短期全部观看，也难以逐部人工分类。
- 现有组织主要依赖源站标签与人工分类，不能充分表达影片之间的内容关系。
- 看过某部影片后，希望次日能够顺着兴趣，发现库里类似、近似的影片。
- Agent 虽然可以按要求建立视图，但用户仍需主动发问、设想分类条件；希望发现与组织能更自然地发生。
- 希望 AI 利用影片信息、标题、简介等进行归纳，并协助治理标签体系，减少重复劳动。

核心需求可表述为：**让逐渐增长的个人片库持续形成可理解、可浏览、可发现的组织，并在用户产生兴趣时帮助找到下一部影片，减少逐片整理和反复下指令的负担。**

### 7.2 四个相互关联、需要分别定义的需求

| 需求 | 用户要解决的问题 | 有价值的产出 |
|---|---|---|
| 存量影片组织 | 几百部影片放在那里，不知道有哪些内容、从哪里看起 | 依据实际库内容形成可浏览的分类或主题集合，允许一片多归属 |
| 标签治理 | 同义、异名、粒度混乱或过于宽泛的标签难以用于检索 | 一致的分类词汇与映射规则，后续影片能够复用 |
| 从一部发现更多 | 看了这部，想找内容或感觉相近的下一部 | 基于当前影片的候选，以及简明的相似理由 |
| 持续维护与自然触发 | 不想每次新增影片或产生兴趣都重新让 Agent 整理 | 新影片沿用已有组织，相关入口在合适的浏览与观看场景中出现 |

这四项共享对影片内容的理解，但不能互相替代。标签更整齐不保证推荐有用；一次推荐回答也不会自动形成可持续使用的分类体系。

### 7.3 需要区分的产品概念

- **原始标签**：源站提供的描述，是输入资料；其中可能有噪声或同义词。
- **内容分类**：影片可能属于哪些主题、题材、场景或风格；维度是讨论示例，应结合真实元数据质量与用户习惯再确定。一部影片可以属于多个维度，无需塞进唯一目录。
- **个人偏好**：用户喜欢什么、为何喜欢；收藏、评分、笔记等可提供信号，但观看过不等于喜欢，收藏原因也未必单一。
- **浏览集合／视图**：用户进入这些内容的入口，例如某类未看影片。现有 Saved View 能保存已有字段的筛选条件；尚未被识别和保存的语义，不能仅靠创建视图凭空获得。
- **相似推荐**：围绕某部影片或当下兴趣临时选出候选，不必为每次推荐永久新增标签。

用户在 2026-09-30 的后续讨论中明确：**“相似”首先指题材接近**。其片库领域本身有较强的类型化表达，同题材作品已经具有较高的近似度。演员／系列等资料关联可以辅助组织，但不能替代题材关联；风格与观看感受不是当前优先判断目标。仅凭标题和简介，也不能可靠判断所有观看体验。

### 7.4 建议的体验方向（尚未确认的产品假设）

1. **第一次整理存量库**：先根据资料形成少量有区分度的主题与分类草案，展示覆盖情况和代表影片。用户主要判断分类是否有用、纠正少数例外，避免把 600 部的手工分类换成 600 次 AI 结果确认。
2. **日常浏览与观看**：在详情或最近观看等合适位置提供“继续找类似的”入口，说明候选为何相关；次日仍能沿着最近的兴趣继续探索。确切位置和触发条件未定。
3. **逐渐完善偏好**：收藏、高评分或明确表达喜欢可作为较强信号；仅打开或播放一部影片不足以推断用户喜欢它。用户能轻量纠正“不像”“这次不想看这类”。
4. **后续增量维护**：新影片导入或资料更新后，沿用既有分类体系，处理变化部分；用户修正应能保留，避免重复生成相同错误。

“无感”在此理解为减少主动操作与反复对话，不直接等同于静默覆盖原有标签。可自动生成的可撤销 AI 分类，与合并、删除既有标签等治理写入，需要分别定义自动化边界。若未来采用后台任务、自动应用或新的推荐入口，应在实施前同步修订既有 charter/PRD 的相关限制；本节只登记新的体验诉求，不因旧边界排除讨论。

### 7.5 现有基础与本次新增缺口

- 项目已有每日推荐、可解释推荐反馈、Saved Views，以及 Agent 创建视图等基础；不能把此次需求描述成“当前完全没有推荐”。当前状态参考 `.cursor/rules/project-facts.mdc`，具体实现以代码为准。
- REQ-0034 已提出标签归一化，REQ-0042 已提出用户标签建议与全库批量整理；截至本次查阅，`docs/prd/requirements.csv` 中两者仍是 `idea`。规划中的能力不能当作当前可用能力。
- 本次强调的新增缺口是：**组织结果长期可用、多个维度表达影片、存量与增量接续、围绕一部影片自然触发发现，以及无需逐部审阅的低负担体验。**
- 历史 AI 研究曾把语义搜索与嵌入列为远期方向。本次先定义用户价值，不预定向量数据库、多 Agent、视频分析或重做首页推荐系统。

### 7.6 判断需求是否满足的观察标准

- 用户无需完整看过或逐部编辑，也能理解库里有哪些内容并开始浏览。
- 从某部影片出发，能够找到用户认可的相似候选，且理由有资料依据。
- 用户需要纠正的主要是分类体系与少量例外，整理负担明显少于逐片人工归类。
- 新增影片能够沿用既有组织，不持续制造同义标签，不覆盖用户已明确的修正。
- 资料不足时允许保留“待归类”，推断有来源、可纠正；不为了全库覆盖率编造影片特征。

具体效果阈值应在取得代表性样本并试用后确定，本轮没有访问正式库或验证其资料完整度。

### 7.7 下一轮最值得澄清的问题

1. 已明确题材优先；后续用少量代表影片校准哪些题材表达应该合并、哪些虽相关但需要区分。
2. 用户进一步强调打开片库就能看到同类型作品成组呈现；具体放在首页、资料库或独立发现入口，仍待体验设计。
3. 已明确 AI 整理结果落在用户标签，原始元数据标签保持隔离；用户进一步接受 AI 直接接管用户标签，默认批量应用、事后纠正，详见 §7.10。具体任务入口与运行时机仍待定义。

本节保留这些问题作为后续讨论入口，不要求用户现在一次性完成分类体系设计。

### 7.8 后续澄清：按题材和属性组织，让浏览本身产生兴趣

**用户已明确的方向：**

- 相似度以题材接近为主；优先利用领域现有的类型化表达，不必先解决抽象的观看感受推断。
- 影片拥有多个属性，属性之间可以交叉；归类不意味着物理文件搬动，也不意味着每部影片只能进入一个目录。
- 打开片库时，希望看见几部同类型作品放在一起，从这种并置中产生浏览和选择的想法。主动呈现相关内容本身就是价值，不需要先指定某部影片或向 Agent 提问。
- 用户觉得现有每日推荐体验偏随机、缺乏归纳。这是体验反馈，不能据此声称现有算法是纯随机：当前实现包含评分权重、曝光／冷却、演员／片商多样性和反馈处理（`backend/internal/app/homepage_daily_recommendations.go`）。本次需要补足用户可感知的主题组织。
- 目标除了减少整理劳动，也包括“有意思”：重新发现自己已经拥有的内容，看见此前没有意识到的关联。当前发现范围优先是库内影片。
- 用户提到内容具有敏感性；需求仍聚焦元数据整理、分类和浏览。内容分析使用哪些字段、是否调用外部模型应沿用现有 AI 配置与数据边界，不由本次讨论扩大授权。

**据此提出的产品解释（建议，尚非已选定的界面或实现）：**

可以把核心体验称为“主题浏览”：系统从实际库内容归纳题材集合，以清晰的主题名称、简短的共同点说明和若干部代表影片作为入口；用户展开后浏览更多，也可以从一部影片切到其另一项题材属性，继续探索。

概念示例：影片 A 具有题材 X、题材 Y，影片 B 具有题材 X、题材 Z，影片 C 具有题材 Y。A 与 B 可以在 X 组相遇，A 与 C 可以在 Y 组相遇；A 不需要在两个目录中二选一。这里的 X/Y/Z 是抽象示例，不代表已经分析过正式库。

推荐可以先选择值得展示的主题，再在主题内选择代表影片。主题内保证相关性，主题之间保留差异和探索空间；同一影片可属于多组，但同屏应避免反复出现少数影片。稳定的主题可以持续浏览，入口和代表作品适度变化，不必每天重建分类。

AI 的候选职责是理解标题／简介中的题材、统一同义表达、补充有依据的属性以及解释分组理由。已有清晰标签和确定规则仍可直接复用。分类理解结果应能反复用于浏览与推荐，不需要每次打开页面都重新让 Agent 整理全库。具体运行方式与自动应用边界尚未决定。

**补充体验验收方向：** 用户无需先输入查询，就能理解每组影片为何放在一起；同组题材有一致性，不同组有可感知差别；能展开继续浏览并沿交叉属性发现更多；不能只有一个“猜你喜欢”的混合列表，也不能退化为大量零散标签和重复海报。

这次澄清将需求重心进一步明确为：**以题材为主、多属性交叉组织的片库发现体验，由 AI 协助持续归纳，让浏览本身产生兴趣。**

### 7.9 后续澄清：AI 通过用户标签沉淀整理结果

**用户明确的边界：** 整理标签本身是重要需求。原有标签依赖元数据来源，直接让 AI 修改存在误改风险；项目已有与原始标签隔离的“用户标签”，本次希望利用它承载 AI 整理结果。此处是需求确认，不是立即批量修改正式库的指令。

本次方向对应 REQ-0042：**AI 可以读取原始标签、标题、简介等资料，归纳题材并写入用户标签；原始元数据标签保留原样。** 本次“标签治理”优先指用户标签的词汇统一与影片归属整理，以及原始表达到用户标签的映射，不包含直接合并、删除或重写源标签。REQ-0034 的历史原始标签修改设想不自动纳入本次范围。

| 层次 | 本次需求中的职责 |
|---|---|
| 原始标签与元数据 | 作为可追溯的参考输入，保留源站原貌 |
| 用户标签 | 承载用户自己的组织方式，以及 AI 协助归纳的题材属性 |
| 主题浏览与相似推荐 | 使用整理后的标签组织影片，形成可重复使用的浏览与发现入口 |

例如，多个源站用不同名称描述同一题材，AI 可将它们映射到统一的用户标签；原始名称仍然保留。归纳结果能用于筛选、成组展示和相似发现，不只存在于一次聊天回答中。

**为支持持续整理的行为建议（按后续 §7.10 的直接接管方向更新，实现方式未定）：**

- 优先复用已有用户标签与明确的命名习惯，避免每次分析都产生新的同义词。
- 在影片与标签的关联层面区分人工添加、AI 添加以及用户明确确认／修正的结果；同一名称可能同时被人工和 AI 使用，仅给标签名称统一标记来源不足以安全撤销。
- AI 可以直接整理用户标签，包括有依据的增补、同义归并、规范命名和纠正不合适的归属；不再默认仅可新增。首次整理保留当前状态以便撤销，后续尊重用户明确修正或保留的结果，不要求每项变更单独审批。
- 用户纠正优先：明确移除或否定的 AI 归类应被记住，避免下一轮自动加回；原始资料刷新也不应直接覆盖用户标签。
- AI 变更应可查看依据、按批次撤销；撤销时保留用户此后新增或确认的内容。这些是目标要求，不能当作现有能力已具备。
- 批量体验默认执行后按标签组汇报覆盖影片与变化，用户按需检查代表影片、异常项或撤销。预览可以作为可选入口，不作为每批写入的必经审批步骤。

由此形成需求闭环：**资料输入 → AI 归纳与统一题材表达 → 沉淀为用户标签 → 主题浏览与相似推荐 → 用户纠正并持续维护。** 标签整理提供可复用的基础，成组发现提供日常可感知的价值。

### 7.10 后续澄清：用户标签由 AI 主导维护，默认直接应用

用户说明当前正式库中真正手工添加的用户标签很少，因此认为 AI 直接接管用户标签的风险相对可控。此为用户对现状的说明，本轮未读取正式库核实数量。

**据此确定的需求方向：** 用户标签作为 AI 主导维护的组织层。用户发起整理或开启相应自动整理能力后，AI 可以直接批量应用整理结果，用户主要在浏览中纠错；不要求逐片、逐标签或逐批重复确认。接管包含统一已有用户标签，而不只是向空白影片追加标签。

建议体验为：发起一次片库整理 → AI 归纳题材、整理用户标签并应用 → 展示主题组及整理摘要 → 用户按需纠正或撤销。后续新影片复用既有体系，具体增量触发方式仍待设计。

保留的基本能力是：原始元数据隔离、整理前状态与批次变更可恢复、后续人工修正优先。来源和批次记录可以由系统内部维护，不要求用户先建立复杂的标签权限体系或逐项标注历史标签来源。

本节更新 §7.4／§7.8 中尚未确定的自动应用方向，并取代 §7.9 早期“默认只增补、治理另行确认”的建议。REQ-0042 及 charter 中旧的逐批确认约束，应在进入实施时同步对齐此项用户选择，不能继续把旧约束当作用户需要重复审批的理由。

本轮仍处于需求梳理阶段，未实施功能、未修改正式库标签，也未开启后台自动任务。

### 7.11 首版建议：从标签整理到主题浏览的完整路径

状态：基于前述已确认需求提出的产品方案。2026-10-01 用户已确认“从一个题材开始逛”放在首页；首页具体区块顺序、展示数量、其他入口及实施顺序仍为建议，尚未实施。此次方案优先回答“需要做什么、主题组怎样呈现”。

#### 需要交付的四项能力

1. **AI 整理用户标签**：读取影片已有资料，先形成全库共用的题材词汇与同义映射，再分批为影片打标及整理旧用户标签。支持全库与新增／资料变化影片，应用前保留恢复信息；缺少依据的影片列为待整理，不强行归类。任务可查看进度、取消后续处理、重试失败项与撤销已应用批次；关闭页面不丢失任务。
2. **从标签生成可持续浏览的主题组**：以规范化题材用户标签作为首版分组依据；为主题保留稳定标识、名称、简短含义和动态成员规则。默认一个题材标签形成一个组，一片可以多组归属。用户标签中的个人备注、状态或评价用语不自动提升为题材组。
3. **主题展示与组内浏览**：首页展示少量主题海报行，资料库提供完整主题入口，点入主题后复用影片网格、详情与播放流程。主题成员随标签和影片变化自动更新，AI 不必每次打开页面重新生成。
4. **同题材发现与轻量纠错**：详情页按题材提供相关作品与主题入口；支持改标签、标记归类不符、隐藏主题及查看／撤销整理。隐藏主题仅影响展示，不删除影片或标签；明确纠正归类时改变标签关联，并由后续 AI 整理尊重。

#### 主题组的定义与生成

主题组是“有明确共同题材的一组库内影片”的展示入口。它消费用户标签并按需查询影片，不是物理目录，也不是每次随机产生的一份固定 ID 清单。

首版先做单题材组，避免一开始枚举所有标签交叉组合产生大量重复小组。小组可以保留在完整主题列表中，首页优先选择有足够代表影片、题材清楚且相互重叠较少的组；具体数量阈值由实际库分布验证，不凑组、不强求覆盖每部影片。复合题材、自由编排专题可后续再加。

同义归并用于规范题材表达，但相关题材不等于同义词，不能为了减少标签数量过度合并。主题命名尽量采用用户熟悉的领域词汇，避免每次让 AI 创造新名称。显示名称调整不应导致主题链接或固定状态丢失。

#### 三个入口及呈现方式

| 位置 | 用户目标 | 首版呈现建议 |
|---|---|---|
| 首页“从一个题材开始逛”（位置已确认） | 没有明确目标也能产生浏览兴趣 | 先展示约 3 个主题，每组一行 4–6 部海报；主题名称、影片数、简短共同点及“查看全部” |
| 资料库“主题”入口 | 看清整个库有哪些题材 | 主题概览使用少量代表海报的拼图、主题名与数量；进入后展示该组完整影片网格 |
| 影片详情“同题材作品” | 从当前影片继续探索 | 展示相关影片及共同题材；有多个题材时可切换或进入对应主题，不自动推断观看即喜欢 |

首页建议将主题区置于 Hero 之后的靠前位置，先承接当前每日推荐的主要展示位置；继续观看、最近加入保留。旧推荐规则中的反馈、冷却和曝光信息可用于组内代表影片选择，不能只新增数行内容而无限拉长首页。最终区块顺序需在页面设计中确认。

每行建议结构：

```text
题材名称             共 N 部 · 未看 M 部       查看全部 →
一句话说明这些影片共同的题材（含义不明显时才显示）
[影片海报] [影片海报] [影片海报] [影片海报] …
```

海报使用真实影片已有素材，不生成虚构封面。卡片沿用现有影片卡，点击打开详情并保留主题浏览来源，返回后恢复原位置。手机端每次显示较少卡片，可横向浏览，始终提供可见的“查看全部”。

进入主题后，顶部显示主题名、数量与必要说明，下方直接是可排序／筛选的完整影片网格；“只看未看”“收藏”等进一步缩小范围。沿用现有观看状态口径并在实施时核实。主题入口可被保存或固定，以便下次直接进入；固定功能可以后续补充。

现有 Saved Views 和标签筛选可作为复用候选，但当前筛选是否独立区分用户标签与源标签、是否支持稳定主题 ID，必须实施前验证并补齐；不能假设现有 `tag` 查询已满足全部语义。自动主题不应默认占满用户的 Saved Views 配额。

#### 推荐如何有组织地变化

- 先选择主题，再选组内代表影片：主题之间提供不同方向，组内保证题材相关。
- 初次没有观看偏好也可展示：根据片库实际题材覆盖与组间差异选择；不能把收藏量直接当作题材定义。
- 有浏览／观看记录后可以增加“接着探索某题材”的入口，同时保留其他题材。观看行为用于提供探索上下文，喜欢与否仍依赖明确反馈。
- 同屏尽量不重复展示相同影片；一片多组归属仍保留在各组完整列表中。
- “换一组”只更换展示的主题或代表作品，不触发全库 AI 重打标签。主题本身保持稳定，允许用户持续返回。
- 延续有效的“不感兴趣／稍后再看”推荐排除；完整主题目录仍按资料库与观看范围规则提供浏览，推荐反馈不等于删库或改标签。

#### 第一次使用与持续维护

尚未整理时，主题区提供“整理片库”入口和简短作用说明。用户发起后按批次直接应用；完成后显示已整理数量、生成主题和待处理数量，立即进入浏览。资料不够或处理失败应分别汇报，不能把失败影片计为已整理。

后台整理中的页面可展示已有有效主题与进度，分析服务暂不可用时继续使用上次已保存结果。首次整理成功后建议在同一入口提供“新影片自动整理”设置；开启后，在资料准备就绪时增量处理，新资料或词汇变化只处理受影响项。具体默认值和运行时机在实施设计中确定，不因浏览页面本身调用模型。

#### 建议实施顺序与首版边界

1. **先打通最小纵向流程**：在测试数据或明确选择的样本中完成“资料 → 用户标签 → 主题海报行 → 全部影片 → 纠正／撤销”，用题材一致性和浏览吸引力验证效果。内部抽样验证不增加正式使用时的逐批审批。
2. **扩展到正式的全库整理任务**：补齐进度、失败重试、取消、批次恢复、原始标签隔离及人工修正保留，再支持数百部存量片库。
3. **接上日常体验**：增量整理、首页主题选择与曝光控制、详情同题材推荐共用同一标签与主题定义。

首版验收至少覆盖：同题材影片正确归组；一片多组；同义标签统一；原始标签不变；失败可恢复；人工纠正不会反复被覆盖；主题数量与网格匹配；离线／受限内容不从主题入口泄漏；返回保留浏览位置。还需通过代表性影片的人审判断分类是否有意义，不能只验证 API 成功。

首版不预设独立向量数据库、视频内容分析或复杂推荐模型。其核心交付是：**整理一次，即可按题材浏览已有片库；从任一组或影片出发，都能继续找到相关内容。**

## 8. 2026-10-01 实施计划：AI 用户标签整理与首页题材发现

状态：**实施计划，尚未开始开发**。承接 §7 已确认需求；本节为该功能的执行计划入口，避免另建重复主题文档。阶段按依赖顺序实施，每个可独立验收的行为单独提交，不自动 push。当前工作区其他主题的改动不纳入此项。

### 8.1 交付目标与范围

首版可交付结果：用户主动发起一次整理，AI 直接维护影片用户标签；首页“从一个题材开始逛”展示约 3 个题材、每组 4–6 部代表影片；“查看全部”进入完整主题网格；能够查看任务结果、纠正标签及撤销整理。新增影片的自动整理作为下一阶段交付。

- 仅处理影片库的用户标签，不修改原始元数据、演员标签或漫画／写真标签，不移动文件。
- 一片可属于多组；只有明确的题材标签成为主题，个人评价与状态标签不自动成为主题。
- UI 发起整理与 Agent 发起整理共用任务与权限；用户发起的整理直接应用，不重复逐批确认。自动整理开关由用户操作，模型不能自行开启。
- 浏览已保存主题不依赖模型在线；不引入向量数据库、视频识别、独立主题编辑器或新的顶层导航。
- 首版首页位置建议：Hero 后展示主题区，保留继续观看和最近加入；旧每日推荐在主题可用时收起为次级入口，无主题时保留原入口。此具体排序属于实施默认方案，可在界面验收调整，不删除旧反馈数据。

### 8.4 P0：先确定合约与产品默认值

1. 定义稳定主题 ID、题材名称／别名／含义、关联 user 标签 ID、主题隐藏状态；名称变化不更换 ID。首版一个规范题材对应一个主题，不自动展开所有交叉组合。
2. 定义任务范围：选中影片、当前库全量、新增／变化影片。发起全量任务时固定目标 ID 集合，后来新增的影片由后续任务处理。
3. 定义结果计数：成功、无变化、资料不足、冲突跳过、失败、未处理；任务成功不等于每部都有标签。
4. 对齐 charter P-02/P-10、用户 PRD REQ-0042 与 milestone 中的旧批批确认要求：仅为用户发起／开启的题材整理增加范围受限的自动应用模式；其他工具仍沿用原确认行为。用户本轮选择已提供方向，不再因旧文档要求重复审批。
5. 合成样本覆盖同义／跨语言表达、题材交叉、同名 nfo/user、资料缺失、简介冲突、人工纠正及恶意指令文本。标题／简介只作为数据，模型只能返回目标影片与合法题材结构。

### 8.5 P1：数据模型与主题查询

以下为拟新增的逻辑实体，表名和迁移号在实施时依照仓库最新迁移确定，不提前占号：

- **题材词汇／主题定义**：稳定 ID、规范名称、别名、题材说明、user 标签映射、词汇版本、隐藏状态。仅 user 标签成为成员依据。
- **影片归类状态**：输入资料指纹、词汇／提示词版本、处理结果、用户标签版本；输入指纹不包含 AI 自己更新的标签，避免触发循环。
- **关联来源与人工纠正**：影片—题材的来源、最新变更者及明确保留／排除记录。历史少量手工标签作为首次接管前状态保存，不要求用户逐条补来源。
- **整理任务与逐项记录**：范围、检查点、状态、尝试次数、模型／版本、用量、结果和错误；足以从进程重启中恢复。
- **变更审计与撤销记录**：变更前后关联、版本、批次和依据摘要；与标签变更同事务提交。

AI 写入采用受限 user 标签差量与乐观并发校验，不能先读旧数组再盲目整表覆盖。原有人工 PATCH 接口的外部合约保持兼容，内部同样更新版本；显式增删成为后续 AI 应尊重的修正。

撤销按批次逆向恢复仍由该批次拥有的变更，遇到后续人工修改或其他批次变更时跳过并报告冲突，不用旧快照整表覆盖。涉及主题改名／合并也需审计；被后续引用的主题定义不能直接删除。撤销重试必须幂等。

主题计数、代表影片和完整网格使用相同活动库／可见性范围。垃圾箱、不可见离线来源和锁定范围沿用现有规则；推荐排除只用于首页代表影片，不从完整主题目录中删除影片。已有 `tag` 语义保持不变，主题查询独立按 user 标签 ID 精确匹配。

### 8.6 P2：可恢复的 AI 整理执行流程

1. **准备范围**：服务端检查 AI 启用、只读状态、用户明确发起的范围；持久化 job，再返回 taskId。任务与聊天连接解耦，关闭 Agent 面板不应取消已交接的整理任务。
2. **归纳词汇**：读取范围内已有题材表达、用户标签与精简元数据，分段汇总出规范词汇；已建立体系时优先复用。服务端验证名称、别名与题材类型，避免同义重复与泛化合并。
3. **分批分析**：以 token 预算切分影片输入，单批写入不超过既有 25 实体上限；初始低并发，有限重试。只输出目标影片 ID、题材 ID／受检验的新题材、依据字段和待归类原因；批次词汇保持同一版本，新词汇由服务端统一归并后再提交。
4. **验证与应用**：验证 ID 属于任务范围、资料和标签版本未过期、结果数量／格式合法；遵守人工纠正；事务提交 user 标签差量、审计和检查点。模型拒答或无有效输出时报告对应失败／待处理，不能清空旧标签。
5. **汇报结果**：经 `task.updated` 推送进度并使主题缓存失效；页面显示已处理／总数、当前阶段、失败项及结果入口，不显示虚构精确剩余时间。
6. **恢复处理**：启动时恢复未完成任务到可继续状态；重试跳过已提交项，人工取消仅停止后续项，已应用项明确保留并可另行撤销。提交前再次检查取消与权限版本，事务中已开始提交的最小单元可完成，之后不再开始新写入。

同一影片避免并发整理，输入变化或写入冲突重新排队而不覆盖新资料。权限被关闭或 Provider 配置发生变化时停止后续模型调用，保留已完成结果；用户恢复任务时重新校验配置。请求超时、限流和总用量要有界；先用样本测调用量和耗时，不给出未经实测的费用承诺。

UI 和 Agent 工具都调用同一受控任务服务；任务中的模型访问与标签应用沿用网关权限、投影与审计，不能暴露原始 SQL 或任意 PATCH。任务授权由服务端签发并绑定范围，不由模型自行声明。MCP 写权限不随此功能自动开放。

### 8.7 P3：首页与组内浏览

- 新增领域组件，候选命名 `HomeTopicSection.vue`／`HomeTopicRow.vue`；组合现有 `HomeSectionRow`、影片卡和 shadcn-vue 基元，不在组件中直接访问具体 adapter。
- 首页默认最多 3 个主题，每行最多 6 部代表影片，小屏减少可见卡片并允许横向浏览；明确“查看全部”，不靠滑动才能发现入口。数量不足不填充虚构影片或重复影片。
- 区块显示“从一个题材开始逛”，每组显示题材名、总数与必要说明；已观看／未看计数使用既有口径，不在本功能中重新定义“看过”。
- 首版主题排序采用可解释规则：足够影片支持、组间覆盖差异、近期曝光；组内尊重已有负反馈和冷却。跨行去重只影响代表卡片，不改变真实归属。后续才增加复杂个人偏好排序。
- 在资料库路由增加 `topicId` 上下文，网格复用现有筛选／分页；主题名与数量在顶部呈现，用户可叠加收藏／未看条件，返回恢复位置。规范名称调整不使 URL 失效。

- 首版纠错复用影片标签编辑，并在组内提供“题材归类不符”；该动作删除对应 user 关联并保存明确排除。隐藏主题仅改变呈现，不修改影片标签。
- `library-service` 承载主题读写，`ai-service` 承载整理发起／结果接口，两者通过共享 DTO 和事件协作；Web 与 Mock 同步实现，Mock 用确定性结果模拟进度／失败／撤销，绝不调用真实模型。
- 繁重的全主题概览与固定主题操作可后置；首版通过首页“查看全部”即可完成浏览，不以新增独立导航为前置条件。

### 8.10 P5：增量整理与详情继续发现

首版稳定后增加“新影片自动整理”：用户在 Server 本机启用后，元数据就绪事件触发有去重／防抖的持久化任务；同一影片资料变化合并处理，用户标签自身变化不触发循环。关闭后停止新增调度；运行中的任务可取消并保留结果。

详情页增加“同题材作品”，依据共享规范题材选候选，显示共同题材并允许切换。与首页、完整主题列表使用同一主题 ID 与成员规则；不另建相互矛盾的分类体系。用户观看产生的近期上下文可影响推荐入口顺序，不能覆盖明确不感兴趣反馈或把观看直接解释为喜欢。

**开工顺序**：先落实 P0/P1 的合约、迁移和恢复测试，再做 P2 的可恢复任务，最后将真实结果接到 P3 首页。首个可演示成果必须包含“真实标签整理后出现在首页”，不能只交付静态海报原型。

### 8.11 触发时机与低打扰的状态反馈

**状态：2026-10-01 用户已确认本节触发时机与低打扰反馈规则，作为实施基线；尚未实现或启用。** 批量整理必须有明确触发时机，让用户知道何时、为何开始，也能感知正在整理，同时避免过于打扰。默认采用下述 60 秒合并等待／5 分钟最长等待规则；后续若根据试用调整，应同步更新计划与用户可见说明。

#### 触发规则

| 场景 | 默认触发时机 | 用户看到什么 |
|---|---|---|
| 第一次整理存量库 | 用户在首页点击“整理片库”，或明确向 Agent 发起整理 | 发起处先说明范围、将更新用户标签、可后台运行；点击即启动，不另加逐批确认；立即显示已排队／运行状态 |
| 后续手动整理 | 用户选择“整理新增／变化影片”，或主动选择全库重新整理 | 显示本次范围与触发来源；没有待处理项时直接说明，无模型调用 |
| 自动整理新增影片（P5） | 用户开启自动整理后，新增影片完成入库且对应元数据任务结束，具备可分析资料，再合并调度 | 固定状态显示“新增 N 部影片，等待整理”，开始后转为“正在整理” |
| 自动整理资料变化影片（P5） | 标题、简介、原始标签等分析输入发生实质变化，并且相关元数据更新已结束 | 显示“因影片资料更新，整理 N 部”；指纹未变不触发 |
| 开启自动整理 | 仅启用后续新增／资料变化的处理，不立即补跑全部历史库 | 开关附近明确说明范围；已有待整理存量给出可选的“整理已有影片”入口 |
| 重启恢复 | 恢复持久化的未完成任务，在原范围与权限仍有效时继续；明确取消、暂停或需要处理错误的任务不自动恢复 | 显示“继续上次未完成的整理”；不重新播放旧的开始／完成通知 |

首次整理前的说明是发起按钮附近的常驻简短文案，不是额外审批弹窗。自动整理默认关闭，由用户开启后持续生效，不要求每次增量任务确认。范围接管与标签直接应用遵循 §7.10。

**自动增量合并时机：** 同一导入／刮削批次等待上游任务结束，仅将已就绪影片纳入；随后等待 60 秒，期间新就绪事件合并。持续新增导致等待不断延长时，从首个就绪项起最多 5 分钟就提交当前就绪项，不再无限等待。两者以先到者为准。没有批次标识的独立事件按同样的 60 秒／5 分钟规则合并。未完成资料准备的影片继续等待，不为满足时限提前分析；资料任务结束但资料不足的影片记录待归类，不无限重试。

每个库同时最多运行一个整理任务，新变化合并到下一批；已运行任务的总数保持固定，另外显示待整理数量。模型批次仅是内部切分，不为每 25 部另弹一次提醒。人工重新触发时，对同一影片与输入版本去重。

**不触发 AI 重整的操作：** 打开首页、刷新页面、换一组推荐、播放、收藏、评分、人工修正用户标签、AI 自身写标签、仅修改模型配置、应用升级。它们可以更新展示或排序，但不会默默重跑全库。词汇体系重大变化时提供明确的重新整理入口，不自动重算所有旧影片。

#### 运行状态：随时可见，不抢占当前操作

- **首页固定位置**：在“从一个题材开始逛”标题附近显示一条简短状态，例如“正在整理 · 已处理 36/120 部”，可点开详情。原有主题保持可用；归纳词汇尚无影片进度时显示“正在归纳题材”，不伪造百分比。
- **全局任务入口**：复用现有任务进度展示／任务中心入口，支持离开首页后查看状态；不自动打开 Agent 面板、不弹模态框。播放全屏时不覆盖画面，退出后仍能查看任务。
- **任务详情**：明确触发原因（手动／新增入库／资料更新／重启继续）、范围、开始时间、阶段、已处理与待处理数量、错误，以及取消／重试／结果入口。运行、等待合并、排队、暂停／需处理、部分完成必须能区分。
- **客户端离线或断开**：提示“状态暂不可用”，不把旧进度当成正在实时推进；重连获取持久化任务快照，避免重复提醒。

#### 通知节奏

| 事件 | 默认反馈 |
|---|---|
| 手动任务开始 | 发起处立即反馈并显示固定任务状态，不另弹重复“已开始”通知 |
| 自动任务等待／开始 | 更新固定状态，无 toast、无声音、无系统通知 |
| 手动任务完成 | 最多一次轻提示“整理完成，查看主题”，同时保存一条可回看的任务摘要；当前正在结果页时仅原位更新 |
| 自动任务完成 | 首页更新“最近整理 N 部”；通知中心同一次合并运行仅保留一条完成摘要，不触发 toast／声音／系统通知。连续自动任务的成功摘要按资料库与本地日合并更新，不重复制造未读提醒 |
| 可自动恢复的短暂错误 | 状态显示“等待重试”，不每次重试都提醒 |
| 部分失败、重试耗尽或需用户处理 | 同一任务一次非模态提醒，摘要明确成功／失败数量并提供处理入口；相同阻塞原因持续存在时不重复弹出 |
| 用户取消 | 发起处说明“已停止，已整理 N 部保留”，提供查看／撤销；不再发送成功或失败提醒 |

播放器处于全屏时抑制所有整理 toast，结果保留在任务和通知中心，不在退出全屏后补播一串过期消息。其他客户端已完成的历史任务在重连时只显示记录，不重放 toast。通知事件使用持久化 job/event 标识去重，任务详情始终保存真实逐次记录；合并通知不丢失处理结果。

首页浏览中主题成员更新后，不强行重排当前视口或抢回滚动位置；可以显示“主题已更新”，在自然刷新／用户进入时呈现新结果。

#### 调度控制与验收补充

关闭自动整理时，停止新的自动调度，取消尚未开始的自动队列；正在运行的自动任务在当前最小提交单元结束后停止，保留已应用结果。用户手动发起的任务不受此开关影响；全局禁用 AI／开启只读仍按 §8.6 阻止后续写入。取消的输入版本不能因重复事件马上重新入队，仅由用户重试或新的真实输入变化重新触发。

P0 定义 `triggerReason`、输入批次、等待期限、恢复原因和通知去重标识；P2 完成任务状态与恢复记录；P3 即实现固定进度／低打扰反馈；P5 接入自动增量触发。因此通知设计不推迟到自动整理阶段。

新增验收：一批 100 部入库只形成一次可感知整理运行；持续就绪事件不会无限推迟；普通浏览零触发；关闭开关后队列和运行行为符合上述规则；重启不扩大范围；全屏播放无整理弹窗；失败重试不刷屏；断线重连不重放通知；运行时离开首页仍可找到进度与触发原因。

### 9.12 硬约束：AI Agent 只能修改用户标签

**2026-10-01 用户再次明确：AI Agent 不得修改 NFO 标签，只能修改用户标签。** 此约束覆盖手动发起、聊天发起、后台自动整理、归并／改名／删除、重试和撤销全过程。NFO／原始标签可以作为分析输入，但不得被 Agent 新增、修改、删除或改成 user 类型；也不得通过写回 NFO 文件间接改变原始标签。

3. **数据库写入**：Agent 专用存储入口只更新 user 标签行及其影片关联，所有 UPDATE／DELETE 明确限定 user 类型；不调用原始元数据写入、刮削重写或 NFO 导出回写来绕过限制。撤销同样只恢复用户标签与本功能内部状态。

## 10. Agent 影片整理方法与判断规则

状态：**2026-10-01 整理方法实施方案，尚未运行**。本节补齐 Agent 如何理解、归纳和整理影片，作为 C1 合约、C4 分类器／提示词和 C8 质量验收的依据；严格遵守 §9.12，NFO 标签只读，所有标签变更仅限 user 类型。

### 10.1 总体流程

采用“盘点资料 → 建立题材词汇 → 按片提取证据 → 分批归类 → 校验应用 → 汇总主题”的固定流程。Agent 承担题材理解与歧义判断，程序承担范围、校验、执行和恢复。不能让每个批次各自自由命名标签，也不能把 600 部资料一次性塞进聊天后直接覆盖标签。

首轮整理按全库已选范围建立共用词汇；后续新增影片沿用该词汇，只对确有新题材的表达扩充。相同输入、相同词汇版本的影片默认跳过，人工明确要求重新分析时才重跑。

### 10.2 输入资料与可用证据

构建专用 `TagOrganizationMovieInput` 投影，不直接使用带路径、海报 URL 和评分等字段的通用影片详情卡。投影包含 movieId、原始标题／简介／NFO 标签、已有用户标签及来源／人工决定、资料完整度和输入版本；展示覆盖标题／简介如有保留应明确标记来源，不能与原文混为同一事实。现有详情查询使用 effective columns，实施时需增加能区分原始字段与展示覆盖的只读查询。

| 输入 | 用途及限制 |
|---|---|
| 原始／NFO 标签 | 已有题材线索与同义映射输入；只读，不因清洗而回写 |
| 标题、简介 | 识别明确题材、场景／设定，补充标签未表达的信息；理解否定、宣传语和多义词 |
| 现有用户标签 | 优先复用题材名称；区分题材、个人评价、观看状态、演员／系列等，避免全部作为主题 |
| 人工保留／排除 | 对具体影片题材归属的最高优先约束；明确排除后不能再自动加回 |
| 演员、片商、系列等 | 仅有实际字段且消歧需要时补充，不能仅凭某演员／片商推断每部作品题材 |
| 收藏、评分、观看历史 | 不参与判定影片题材；只在主题展示／排序阶段使用 |

首版不自动联网搜影片、不读取视频内容、不分析封面、不把个人笔记作为必需输入。资料缺失保留待归类。分析文本中的指令、链接或模型知识不能授权任何动作，也不能替代该影片的证据。

### 10.3 先建立可维护的题材词汇

1. 程序只读统计范围内原始标签和用户标签的名称、数量及共现；名称清理仅用于内存比较，保留原始字符串与来源。
2. 对标签表达分段梳理，再读取来自不同表达、稀有标签、无标签和资料缺失影片的代表资料。不能仅凭高频标签或前一页影片决定所有分类。
3. Agent 为候选概念给出规范名称、别名、类型（题材／辅助属性／非题材）、简短定义、纳入条件、排除条件及支持它的输入引用。使用用户熟悉的领域词汇，不生成花哨的营销标题。
4. 严格区分同义与相关：同义表达可归并；近似题材、子题材、共同演员或系列关系不自动合并。出现多义词时采用上下文匹配条件，不能把该词全局无条件映射到一个题材。
5. 服务端校验规范名称唯一性、跨类型冲突和 user 标签映射；确定词汇版本。已有人工命名优先，旧名称作为 alias 保留。确实成立的稀有题材可以保留，不因暂时不足一组海报就删除。

每个题材规范至少包含 `topicId/canonicalName/aliases/definition/includeRules/excludeRules/vocabularyVersion`。不预设必须生成多少题材，不自动枚举“题材 × 演员 × 片商”等组合；首页数量限制与标签体系规模分开。

首次任务在词汇建立后开始应用影片归属；续批使用明确的词汇版本。新概念先进入候选池，由集中规范化步骤判断“已有别名／已有相关概念／确属新题材”，再发布下一词汇版本并处理受影响影片；不能每批直接创建近义新标签。

### 10.4 逐片归类：证据决定是否写入

为每部影片生成候选题材，再对照题材定义判定。候选来自已验证的别名映射、原始标签和标题／简介语义；无匹配时允许提出新题材候选，不因候选召回遗漏强迫影片进入现有组。

| 判断结果 | 典型依据 | 默认动作 |
|---|---|---|
| 明确支持 | 明确、无歧义的源标签匹配规范题材，或标题／简介直接表达题材且无相反信息 | 可以添加对应用户题材标签 |
| 仅有弱线索 | 单个歧义词、宣传修辞、演员／片商印象、与其他影片的笼统相似 | 保留候选／待归类，不自动加标签 |
| 信息冲突 | 源标签与简介矛盾、同一题材有明确否定／排除证据 | 当前冲突题材不写入，记录冲突；其他独立且明确的题材仍可归类 |
| 资料不足 | 只有代码、无有效标题／简介／题材线索 | 标记资料不足，不生成标签、不清空已有用户标签 |
| 人工决定 | 用户明确保留或排除该题材 | 执行人工决定，覆盖 AI 归属建议 |

一个明确且无歧义的证据可以成立，不要求必须有多个字段；多个字段一致能增加支持，但不能用重复宣传词制造可信度。不用模型自报的“置信度 0.9”直接决定写入，采用可复核的证据与冲突规则。

输出为结构化记录：`movieId/inputFingerprint/vocabularyVersion/topicDecisions[]/newTopicCandidates[]/unresolvedReasons[]`。每个决定含 `topicId/action/evidenceRefs/reasonCode`；证据引用由程序校验字段、原始片段和范围是否存在。证据存在不代表语义一定正确，仍需质量评测与用户纠正。拒绝模型输出任意数据库字段、NFO 标签写入、范围外 movieId 或不存在的 topicId。

题材标签优先保留有实际区分价值的属性，通常应是少量明确题材，不设“每片至少几个”的配额；合法上限沿用现有标签约束，不能以凑满上限为目标。允许一片多个独立题材，不强制唯一主类。

### 10.5 已有用户标签如何处理

AI 接管包括规范化和调整，但每种变更有明确规则：

- **新增**：有明确题材证据，且无人工排除时新增。
- **同义归并／改名**：语义确实等价、全部为 user 类型且无人工保留冲突时执行，保留 alias 和变更记录。原始标签的名称与关联完全不变。
- **个人备注／状态／评价**：识别为非题材后保留为用户标签，不进入题材主题组；不能因不适合主题展示就删除。
- **移除错误归属**：需要明确否定证据、已验证的错误别名映射或用户纠正；“这次模型没有提到”不构成删除理由。
- **资料退化／模型拒答／截断**：保留已有标签，将未能判断的项记为待处理，不把空输出解释为空标签列表。
- **近期人工修改**：版本检查冲突时重新读取／跳过；不使用旧模型结果覆盖新修改。

同义词规范化属于词汇级治理，应先形成完整变更集并核对任务范围。对于只整理选中影片的任务，不允许借全局标签改名改变范围外影片：可将选中关联映射到已有／新规范 user 标签；全局合并或改名仅在任务范围涵盖全部受影响影片时执行。此规则需补入 C2/C4 的范围测试。

### 10.6 批次、校验与一致性

- 分批按实际 token 预算和字段长度组织，单次写入仍 ≤25 部；不为了固定批量截断关键证据。长资料记录截断状态，无法完整判断的题材不作自动删除依据。
- 有确定且无歧义的已验证映射时，程序可直接复用；歧义或新表达再交给模型。批次共享规范词汇与判断规则，禁止自由“想到什么打什么标签”。
- 每批应用前检查目标范围、user 类型、证据引用、输入指纹、词汇版本、人工决定和标签修订号；通过后由专用事务应用差量及检查点。
- 输出格式错误最多进行一次结构化修复；网络类错误使用有上限的重试与退避；证据不足不反复问模型直到获得肯定答案，安全拒答也不以变换说法反复规避。
- 每轮完成执行程序一致性检查：重复同义题材、孤立／无效映射、相同明确证据对应不同归类、排除规则冲突；异常项集中复核，不能因此自动重跑全库。
- 对新题材和歧义映射增加内部抽样检查，确定性映射也保留抽样；抽查是质量控制，不增加用户逐片审批。新规则若影响旧影片，只标记受影响集，按 §8.11 的已确定触发规则处理。

### 10.7 整理输出与用户可见结果

本次任务产出三类持久结果：规范题材词汇及别名、影片用户标签归属、带依据与版本的变更记录。主题组由已提交的 user 标签关系查询产生，不再由模型额外编造一份“推荐名单”。

结果页汇报：处理总数、成功／无变化／待归类／失败数量，新增或规范化的题材、主要变更及代表影片；允许打开主题、检查单片归类依据、纠正和撤销。避免展示海量技术字段或原始模型思考。一般用户主要看到整理后的主题，只有关心时才展开依据。

示例（抽象测试数据）：影片 A 的原始标签是“题材 X 的别名”，影片 B 的简介明确描述题材 X，影片 C 只有演员信息。整理后 A/B 获得同一 user 题材 X 并组成主题；C 保留待归类。A 的 NFO 别名仍完整保留，不改名也不删除。

### 10.8 提示词、评测与代码任务补充

将 C4 分成词汇归纳提示词与逐片归类提示词，各自版本化；系统规则明确数据边界、题材定义、人工约束、只允许 user 标签、证据不足可弃权及结构化输出。模型不能修改这些规则或任务授权。记录 Provider／模型／提示词／词汇／输入版本，用于复现和对比。

新增纯函数／模块候选：`BuildTagOrganizationInput`、`NormalizeTopicVocabulary`、`ResolveTopicCandidates`、`ValidateTopicEvidence`、`BuildUserTagDelta`，分别负责只读投影、词汇规范化、候选召回、证据校验和 user 差量。LLM 调用仍留在 `tag_organization_classifier.go`，不要混进 storage。

评测集至少覆盖：清晰源标签、标题补充题材、别名／跨语言同义、多义词、否定描述、冲突资料、稀有题材、多题材、只有演员／番号、非题材用户标签、模型拒答、重复运行、选中范围外标签、人工排除、同名 nfo/user。分别报告新增标签准确率、明确题材召回率、待归类率、错误删除数和同义词重复数；在 §8.9 的初始质量目标外，NFO 越界写、范围越界写和覆盖人工排除必须为零。

先以确定性规则／Fake LLM 验证执行正确性，再用受控测试资料检验实际模型的语义质量。用户未要求正式整理前，不把本节方案当成读取、外发或改写正式库的指令。
