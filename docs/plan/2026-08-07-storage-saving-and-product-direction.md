# Curated 存储空间节省与产品方向讨论

日期：2026-08-07  
状态：讨论稿，尚未进入实现排期

## 1. 结论摘要

当前最值得优先解决的不是压缩 SQLite，而是控制“原始视频之外的派生文件”和重复副本。SQLite 中的影片、演员、标签、评分、播放进度等通常只占很小空间；封面、缩略图、预览图、演员头像、临时下载、备份和日志才是可持续增长的部分。原始视频则应视为用户的主数据，除非用户明确要求，不应由 Curated 自动复制或转码。

建议采用三步顺序：

1. 先做存储可见性与清理策略，让用户知道空间花在哪里，并能安全清理可再生成内容。
2. 再做“远程优先、按需缓存、尺寸受控、可去重”的媒体资产策略。
3. 在此基础上扩展 AV 信息，但以结构化、可筛选、来源可追溯为主，不默认下载更多图片或视频。

“点击海报墙卡片跳到外部站点”可以保留为小功能（来源链接），但不建议把它发展成产品主线。它容易复刻已有站点的浏览模式，也不会帮助解决存储问题。

## 2. 先区分四类数据

| 数据类别 | 例子 | 是否可再生成 | 存储策略 |
| --- | --- | --- | --- |
| 主数据 | 用户的视频文件、用户手工编辑的 NFO/标签/评分 | 否或代价高 | 只引用原路径，不复制；删除前必须明确确认 |
| 结构化索引 | SQLite 中的影片、演员、标签、播放进度 | 大多可重建，但含用户状态 | 保留；定期清理孤儿记录并维护索引 |
| 派生缓存 | poster、thumb、preview image、演员头像、浏览器缓存 | 是 | 默认远程 URL + 按需下载；设置上限、过期和清理 |
| 临时/发布产物 | 上传临时文件、HLS 临时片段、更新安装包、日志、旧构建包 | 是 | 生命周期管理、配额、保留期和告警 |

这套分类很重要：压缩或清理只能针对后三类，不能把用户原始视频误当成缓存处理。

## 3. 可节省空间的方法（按收益和风险排序）

### A. 先做盘空间盘点和“存储顾问”

在设置页显示按目录/类型的占用：原始视频、媒体缓存、演员头像、预览图、数据库、备份、更新包、日志、临时目录。每一类给出“可清理大小”和安全说明，并提供扫描、预览、清理、撤销/备份前置检查。

这项能力本身几乎不增加存储，却能避免用户盲目删除主数据。建议记录每次清理审计，清理对象只允许是已确认的派生文件或过期临时文件。

### B. 媒体资产采用远程优先和按需缓存

- 数据库优先保存 `source_url`、来源、尺寸和抓取状态；进入列表时只加载小尺寸图。
- 默认不下载预览图和预览视频，只有打开详情或播放预览时才缓存。
- 缓存按最近使用时间（LRU）或最近 N 天淘汰，并提供“仅保留收藏/最近使用”的策略。
- 缓存失效后可重新抓取，因此清理前要明确标注“可再生成”。

这比“导入更多 AV 信息时顺便把所有图片都下载下来”更节省空间，也更容易控制网络流量。

### C. 图片尺寸、格式和数量设上限

- 海报只保留一份受控尺寸的展示图；列表缩略图从该图实时缩放或生成小缓存，避免同时保存 large/small 两套原图。
- 优先使用 WebP/AVIF（保留 JPEG 回退），按用途设宽度上限和质量上限，例如列表图、详情图、演员头像分别设定预算。
- 预览图设每部影片最大张数和总字节数；超出部分只保留 URL 或按需生成。
- 同一演员头像、同一来源图片做内容哈希去重，使用引用关系或硬链接，避免每部影片复制一份。

具体尺寸和质量不应现在拍死，应先抽样统计当前库中各类型文件的平均大小，再按“视觉可接受 + 每部影片预算”确定。

### D. 清理孤儿、重复和失效资产

现有 Library Health 已能发现部分孤儿和路径问题，后续可增加媒体缓存专项检查：数据库没有引用的文件、数据库有记录但文件已不存在的记录、重复内容、失效下载临时文件。清理动作应：

1. 先重新扫描并生成清单；
2. 仅对明确属于派生缓存/临时文件的项目执行；
3. 写入清理审计；
4. 不触碰影片文件、用户 NFO、用户自定义标签和收藏状态。

### E. 限制临时文件、更新包、日志和备份增长

- 上传会话、HLS 片段和失败下载设置自动过期时间，应用退出或任务结束时清理。
- 更新安装包只保留当前版本和用户明确保留的版本；下载完成后提供“安装后删除”选项。
- 日志使用大小上限 + 天数上限，异常日志可压缩归档。
- 备份保留策略按“最近若干份 + 月度份”分层；备份包继续只含数据库、配置和 manifest，不打包媒体源文件。
- 发布目录中的 installer/portable 包属于交付物，清理策略要与运行时数据分开，不能误删用户已有的生产包。

### F. 数据库层的收益有限，但应做维护

SQLite 主要是文本和小型结构化数据，收益通常远低于图片缓存。可以提供低风险维护：清理确认无用的历史任务/审计、删除孤儿行、`VACUUM`/检查点，并在执行前显示预计释放空间。不要把数据库压缩当成主要节省手段，也不要为了省几 MB 牺牲恢复能力。

### G. 对原始视频保持“引用而非复制”原则

扫描时只记录路径和必要属性；导入、整理、重命名等动作必须显式开启。不要为了生成海报墙而复制视频、生成无必要的转码副本或永久保存 HLS 文件。若未来增加转码，必须设计“缓存配额、清晰的源文件/派生文件标识、可删除和失败回收”。

## 4. 两个功能方向的判断

### 方向一：导入更多 AV 信息

可以做，但要定义成“信息密度提升”而不是“媒体文件增量”。优先级较高的内容是：

- 标准化编号、别名、发行日期、系列/合集、片商、导演、时长和分辨率；
- 演员的规范化身份、别名、作品关系和来源链接；
- 标签、来源、抓取时间、字段置信度和冲突状态；
- 用户可关闭的字段级导入，以及“只导入文本、不下载图片”的模式。

这样能显著提升搜索、筛选、去重和推荐，却几乎不增加磁盘占用。对于大段简介和来源原文，建议保留必要摘要，不要默认保存完整网页快照。

### 方向二：卡片点击跳转到对应外部页面

建议作为“来源链接”或“在来源站点打开”的轻量能力，而不是单独建设一个仿海报墙的外部站点浏览器。它的价值是补足详情页的出处和核验路径；它不应缓存整页 HTML、图片或视频，也不应成为主要导航模型。

如果担心与 Javdb 等产品相似，可以把差异放在：本地文件与外部信息的绑定、元数据冲突提示、可解释的来源、个人收藏/评分、离线可用和存储预算，而不是复制其站点式浏览。

## 5. 更适合 Curated 的产品主线

建议把产品叙事定义为：**“本地媒体资产的低占用、可解释资料库”**。

核心体验可以是：

`扫描本地文件 → 结构化导入 AV 信息 → 远程优先显示 → 按需缓存 → 存储顾问定期回收`

这条主线同时回答了用户的两个目标：信息更丰富，但磁盘不因信息丰富而线性膨胀。可形成的差异化功能包括：

- 每部影片的“存储成本”与“可释放空间”；
- 缓存策略预设（极省空间 / 平衡 / 离线优先）；
- 来源与字段级可信度；
- 重复海报、重复演员头像和跨目录重复文件提示；
- “只保留我收藏和最近观看内容的高清图”这类用户可理解的策略。

## 6. 建议的决策顺序

### 第 0 步：先测量，不改行为

抽样统计当前库：视频总量、缓存总量、各资产类型文件数/平均大小/P95、重复率、备份/日志/临时文件占比。没有这组数据，不宜直接决定压缩格式或缓存上限。

### 第 1 步：低风险释放空间

实现存储盘点、孤儿/临时文件清理、更新包和日志保留策略；不改变默认抓取内容，先验证用户是否愿意使用清理入口。

### 第 2 步：媒体缓存预算

引入按类型上限、LRU、按需下载和“只保存 URL”模式；为清理和重新抓取提供状态反馈。

### 第 3 步：AV 信息增强

先扩充结构化文本字段和来源链接，再评估是否需要额外图片。默认走“文本丰富、图片克制”。

### 第 4 步：外部来源链接

在详情页提供受控的来源跳转，验证使用率后再决定是否扩展更多联动。

## 6.1 修正：以影片文件本身为主要空间对象

根据讨论反馈，当前方案的优先级需要调整：预览图、海报和演员头像在实际库中占比很小，不能把它们作为主要节省空间手段。真正需要优先观察和治理的是影片文件本身，包括重复副本、不同清晰度/编码版本、长期不观看的冷数据，以及是否存在可以由用户主动确认的重新编码机会。

后续存储顾问应优先统计每部影片的文件大小、时长、分辨率、编码格式、码率、音轨/字幕数量、所在目录、最后观看时间和播放次数，并提供以下候选分析：

- 完全相同的重复文件：可提示删除副本或改用硬链接；
- 同一作品的多个版本：只提示版本关系和占用，不自动替用户删除；
- 长期未观看的冷数据：建议迁移到大容量低成本磁盘或离线归档介质；
- 编码效率明显偏低的文件：进入“重新编码候选列表”，显示预计可释放空间；
- 已经是 HEVC/AV1 或码率合理的文件：避免为了节省空间而无收益重编码。

重新编码应是用户主动确认的高风险操作，而不是扫描或刮削时的默认行为。流程必须先生成新文件、校验可播放性，再由用户决定替换或保留原文件，并明确告知可能的画质损失和不可逆性。完全重复文件识别也应先用大小、时长等特征缩小范围，再计算内容哈希，避免对全库做昂贵的扫描。

图片缓存、临时文件、日志和更新包仍值得治理，但它们属于第二优先级；它们的清理应作为基础维护能力，而不是 Curated 节省空间的核心产品叙事。

## 6.2 影片存储分析的总体设计

影片存储分析不应是一次性“扫描并给结论”的脚本，而应是一个可增量更新的长期索引。建议将它拆成四层，越靠前越轻量：

1. **文件盘点层**：只遍历已配置的 library roots，读取路径、文件大小、修改时间、文件类型和可访问性。
2. **媒体探测层**：对新增或变化的影片读取容器和流信息，例如时长、分辨率、视频编码、码率、音轨、字幕和封装格式；只读头信息，不解码视频。
3. **重复识别层**：先使用大小、时长、分辨率等廉价特征分组，再对候选组计算局部指纹或完整哈希。
4. **建议层**：结合收藏、评分、播放历史、版本关系和存储成本，生成“重复副本、冷数据、编码效率异常、多版本”等建议。建议默认只读，不直接删除或改写影片。

这四层应该分别记录状态和耗时。用户可以只运行第一层，也可以在空闲时继续后续层；分析中断后从上次成功的文件继续，不要求每次从头开始。

### 建议的数据模型（概念层）

不要把每次扫描的完整结果复制成一份历史快照，否则分析本身会制造新的数据库增长。可以保留：

- 当前文件索引：规范化路径、大小、mtime、文件标识（可取得时）、影片 ID；
- 当前媒体探测结果：duration、width、height、video codec、bitrate、audio/subtitle 摘要和探测版本；
- 指纹状态：指纹算法、指纹范围、哈希值、计算时间和是否完整；
- 分析运行记录：开始/结束时间、范围、取消原因、错误数量和统计摘要；
- 建议结果：稳定的 recommendation ID、原因、预计释放空间、风险等级、当前状态。

字段级结果应覆盖更新，而不是为每次运行无限追加明细。只有用户执行了迁移、删除或重新编码，才保留不可变的操作��计。

### 分析结果在产品中的落点

- **设置页/存储顾问**：总容量、可分析容量、已分析比例、预计可释放空间、当前运行状态。
- **影片库筛选器**：按文件大小、编码、分辨率、最后观看时间、重复组和“优化候选”筛选。
- **影片详情页**：展示技术信息和“为什么被建议优化”，例如“同一作品还有一个 1080p 版本，占用 14.2 GB”。
- **重复组页面**：并排比较文件大小、画质、播放次数、收藏和评分；只提供用户确认后的动作。
- **任务中心**：允许暂停、继续、取消和查看失败项，不把分析任务和刮削任务混成一个不可解释的长任务。

## 6.3 如何做到轻量运行

### 增量优先

每个文件记录上次盘点的大小、mtime、可取得时的文件 ID 和探测版本。下次运行时：

- 路径、大小、mtime 和文件标识都未变化：跳过媒体探测和哈希；
- 只发生重命名或移动：更新路径绑定，不重新读取整个文件；
- 大小或 mtime 变化：重新探测，并使旧指纹失效；
- 新增文件：先进入盘点层，探测和哈希排队在后面。

这比每次全库调用 FFmpeg 或读取文件内容轻得多，也能适应库中只有少量新增影片的日常情况。

### 采用“廉价特征 → 候选 → 深度校验”漏斗

不应一开始就对所有视频做完整 SHA-256。推荐顺序：

1. `stat` 和扩展名检查；
2. 文件大小分组；
3. 时长、分辨率和编码等媒体特征分组；
4. 读取文件头或固定位置的小片段计算局部指纹；
5. 只有用户准备处理的重复候选，才计算完整哈希。

大多数不可能重复的影片会在前几层被排除，从而避免大量磁盘读取。

### 受控的任务调度

- 默认单 worker 或极低并发，不与播放、扫描和刮削争抢磁盘；
- 每处理一批文件就让出时间片，支持取消和暂停；
- 播放中、系统电池供电、磁盘高负载或用户正在进行大规模复制时自动降速；
- 对机械硬盘以顺序遍历为主，避免多个 worker 随机跳读；
- 对网络盘和可移动盘默认更保守，必要时只做文件盘点；
- 允许设置“仅手动运行、空闲时运行、夜间运行”三种调度模式。

### 媒体探测只读元信息

探测阶段只调用能够读取容器和流头信息的工具，不生成缩略图、不解码画面、不转码、不写回原视频。探测失败时记录错误并跳过，不应反复重试造成磁盘和 CPU 浪费。

### 可观测的性能预算

设置页应显示本次分析的文件数、已处理数、跳过数、读取字节数、耗时和当前速度。产品层面可以设定软预算：例如每次最多处理固定数量、最多运行固定分钟数，或者达到磁盘读取预算后自动暂停。具体数值应通过真实库测量后再决定，不宜现在硬编码。

## 6.4 整个产品如何围绕存储分析形成闭环

存储分析不应成为孤立的“设置页统计图”，而应贯穿扫描、资料库、播放和维护流程：

`文件扫描 → 增量盘点 → 技术信息 → 重复/版本关系 → 用户行为信号 → 存储建议 → 用户确认操作 → 重新盘点`

- 扫描新文件时只做轻量盘点，避免新影片导入变慢；
- 元数据刮削成功后补充番号、演员、片商和版本关系；
- 播放和收藏行为用于判断热/温/冷数据，但不改变用户文件；
- 存储顾问将建议按“预计收益、风险、可逆性”排序；
- 删除、移动和重编码都必须使用独立、可审计的任务；
- 操作完成后重新验证路径、播放可用性和数据库一致性。

产品默认只做观察和建议。任何会改变原始影片的动作都要有明确的确认、目标文件、预估释放空间和失败回滚说明。

## 6.5 第一阶段最值得做的范围

建议第一阶段只包括：

1. 增量文件盘点；
2. 影片大小、时长、分辨率、编码、码率等技术信息；
3. 按目录、编码和文件大小的统计；
4. 基于廉价特征的重复候选识别；
5. 可暂停、可取消、低并发的后台分析任务；
6. 存储顾问页面和影片库筛选；
7. 只读建议，不自动删除、不自动移动、不自动转码。

重新编码、自动迁移和复杂的语义版本合并可以放在第二阶段，等真实数据证明它们确实能释放大量空间后再投入。

## 6.6 转码系统的现实边界

转码不应被设计成“把整个库全部转换一次”的一次性工程。以 400 部、每部约 2 小时的影片为例，原始媒体时长已经约 800 小时；如果单机实际转码速度接近 1 倍实时速度，就算连续运行也需要约 33 天，还没有计算失败重试、磁盘读写、验证和用户使用电脑的时间。速度低于实时速度时会更久，硬件编码虽然可能更快，但通常需要在压缩率、画质和兼容性之间取舍。

因此建议把转码分成三个产品阶段：

1. **转码顾问**：只分析当前编码、码率、体积和预计收益，不真正转码；
2. **小样本试转**：用户选中影片后先转一小段或一部样片，比较体积、画质、播放兼容性和实际速度；
3. **可恢复队列**：只有用户确认的候选进入后台队列，支持暂停、继续、失败重试、夜间运行和逐项确认。

候选排序应优先考虑“预计释放空间 / 预计转码耗时”，而不是只按文件大小排序。例如一部 40 GB、已经是 HEVC 的影片可能几乎没有收益；一部 25 GB、H.264 高码率且长期不看的影片，可能更值得处理。已经是 HEVC/AV1、码率合理或用户非常重视画质的影片，默认应排除或标为低收益。

转码实现还需要处理这些现实问题：

- 默认一次只运行一个任务，避免影响播放和正常扫描；
- 优先在系统空闲、夜间或用户明确允许时运行；
- 可选择硬件编码，但清楚说明 NVENC/QSV/AMF 等硬件路径的质量和兼容性差异；
- 音轨、字幕、章节和封装信息默认复制，不要无意丢失；
- 输出先写到临时文件，完成后做可播放性和时长校验，再原子替换或保留为新版本；
- 原文件是否删除必须单独确认，不能由“转码成功”自动推断；
- 转码前必须检查临时空间，因为原文件和新文件可能需要同时存在；
- 任务中断、磁盘空间不足或进程崩溃后，要能清理临时文件并从断点继续。

Curated 的第一版不必立即成为完整的视频编码平台。更稳妥的边界是先提供候选分析、试转和 FFmpeg 任务编排；等实际数据证明用户确实愿意长期运行转码队列，再增加更多编码预设、硬件后端和版本替换流程。

## 7. 需要后续确认的产品问题

- 用户是否要求完全离线浏览？这会决定“远程优先”能否成为默认值。
- 海报墙的主要用途是快速识别、长期离线查看，还是视觉收藏？三者对应不同图片预算。
- 用户能接受多长的缓存保留期、每部影片的默认缓存上限是多少？
- 是否需要跨多台设备共享缓存，还是每台设备独立管理？
- 原始视频是否永远只由用户管理，Curated 是否允许整理/移动？

在这些问题明确前，推荐先做“存储顾问 + 可再生成缓存治理”的产品设计，不急于实现大规模 AV 信息抓取或仿站式跳转浏览。
