### 2. 当前出包链路

当前正式入口是 `.github/workflows/cd-release.yml` 与 `scripts/release/component_cd.py`：

1. 人工判断变更归属、修改对应组件版本 JSON、写 `docs/release-notes/<component-tag>.md`。
2. 创建并推送 `server-vX.Y.Z` 或 `desktop-vX.Y.Z` 标签触发 CD。普通 master push 运行 CI，并不自动决定组件更新或发布。
3. 校验标签固定提交、版本源及说明表格；表格强制只有标签对应模块为 Updated，另一端必须 Unchanged。**当前模型不能在一个新 Release 中把两端都标为 Updated。**
4. 对固定提交运行前端、Electron、Go、e2e 和发布脚本质量检查。
5. 构建该组件：Server 为 Go + 托管 Web UI + FFmpeg；Desktop 为 Electron + 本地连接 UI，不包含 Server。Server 当前正式包只有 Windows x64；Desktop 同时要求 Windows x64 与 macOS arm64。
6. 执行安装、生命周期、升级等验收，汇总固定资产集合、组件 manifest、`release.json`、`SHA256SUMS.txt`。
7. 先建／更新 draft，上传并核对 GitHub 资产摘要；公开后推进对应组件渠道，再执行 Latest 维护。标签触发默认 publish；手动入口默认 draft。

当前组件 CD **不自动递进版本，也不自动分析差异**；它只校验已填写的数字、标签、说明与线上基线是否一致。关于「哪些改动影响哪些包」，目前仍由人判断。

辅助入口：

| 入口 | 当前职责／问题 |
| --- | --- |
| `package.yml` | 手动委托组件 CD，默认只形成 draft |
| `cd-recover.yml` / `recover_release.py` | 复用原作业已验收资产恢复发布；已公开但渠道失败时只恢复渠道，不覆盖公开资产 |
| `release-notes.yml` / `sync_notes.py` | 根据仓库 Notes 修改已发布标题和说明；若只在云端手改标题，后续同步可能改回旧命名 |
| `release-latest.yml` / `latest_release.py` | 强制 Latest 选择最高稳定 Full；所以手动把新独立 Release 标为 Latest 也可能被改回 |
| `cd-legacy.yml` | 仍监听 `v*` 标签并提供手动入口；政策上已退役，技术触发入口尚未关闭 |
| `pnpm release:publish` / `release:portable` / `release:installer` | 仍进入旧一体包脚本，省略版本时会分配 legacy patch；不是当前组件 Release 的统一入口。`publish` 在这里主要是本地打包编排，不应与 GitHub 公开动作混淆 |
| `pnpm release:macos-desktop` | 本地 Mac 独立出包，读取 Desktop 版本，不等于完成云端 Release |

现有 Guide、快速参考和构建规范中仍并列保留旧版本数字、旧推荐命令、Full 与 standalone 政策。较新的说明虽声明覆盖旧规则，但执行者仍可能进入错误链路。需要收敛成一份当前操作说明，历史内容明确归档。

### 3. 建议的目标模型

把发布批次与组件产品版本分开：**Release 代表一次发布，SemVer 代表具体组件的演进。** 合并 Release 容器不恢复 Full 安装器。

- 展示标题采用 `Curated YYYYMMDD`，日期按北京时间（Asia/Shanghai），不含时分秒、时区后缀或 Server/Desktop 产品版本。同日首个 Release 为 `Curated 20260930`，第二个为 `Curated 20260930-2`，第三个为 `Curated 20260930-3`，依此类推；次日从无序号标题重新开始。
- 序号按 Release 批次计算，不按附件或组件数量计算：同一 Release 同时包含 Server、Desktop 仍只占一个批次。
- 推荐独立批次 tag 对应为 `release-20260930`、`release-20260930-2`、`release-20260930-3`。此处是方案示例，未创建标签。
- 批次日期和序号在准备时固定，同一批次重试沿用原标识；分配时检查已有批次与标签，避免并发冲突，不能覆盖已有标签。记录 source commit、所选模块、各模块 before/after、各自已发布来源、变更理由与资产摘要。
- 包名、安装器版本、关于页和组件更新比较仍使用各自 SemVer，例如 `Curated-Server-Setup-1.7.7-windows-x64.exe`。
- 一个 Release 只上传本次有更新的组件包。未更新端保持版本与原下载地址，说明中标注 Unchanged 并链接最近已发布包，避免用户在 Server-only 最新 Release 中找不到 Desktop。

| 本次交付变化 | Release 数量 | Server | Desktop |
| --- | --- | --- | --- |
| 仅 Server | 1 | 递进并出包 | 版本、包、渠道保持 |
| 仅 Desktop | 1 | 版本、包、渠道保持 | 递进并出包 |
| 两端都有 | 1 | 递进并出包 | 递进并出包 |
| 两端都没有 | 0 | 保持 | 保持 |

建议以各组件**上次成功发布的 source commit**为差异基线，而不是上一个总 Release 或最近标签；否则连续 Server-only 发布可能漏算 Desktop 累积改动。先生成可审阅的变更分类和版本计划，再构建、验收、发布。默认实际修复递进 patch，minor/major 由明确的功能／兼容性决策指定。发布频率可按就绪变更组织批次，不必把每个提交都变成一次 Release。

变更归属必须覆盖实际依赖：Server 包含业务 Web UI；Desktop 本地 launcher 位于 `src/desktop-connection/`，还会引用共享 `src` 内容；共享锁文件、图标、安装器、随包 helper 和构建参数按实际影响归属，不能简单把所有 `src/` 都归 Server、所有 `backend/` 都只归 Server。纯文档、测试、CI 管理变化不自动进位；如果构建规则改变了交付行为则仍需算入。不要按 EXE/ZIP 字节差异决定是否有产品更新，时间戳和签名会造成噪声。

### 3.1 关于与更新：一个 Release 下独立检测两端

统一 Release 不合并组件的更新身份。保留 Server、Desktop 两份稳定更新清单，分别记录该组件最新成功发布的 SemVer、各平台／架构安装包 URL 和 SHA-256；来源可指向同一条或不同条 Release。客户端不解析 Release 标题中的日期／序号，也不以 GitHub Latest 的附件作为唯一更新来源。

当前独立包已有此基础：Electron `desktop-updates.ts` 读取 Desktop feed，按组件、平台、架构、安装格式筛选并比较数字版本；Server `internal/appupdate/component_feed.go` 读取 Server feed，交给 app-update 服务比较 Server 版本。`SettingsAppUpdateSection.vue` 的共用检查按钮在允许本机 Server 更新时并行检查 Server 与 Desktop；远程连接沿用现有边界，只检查本机 Desktop 更新，Server 版本可见但不开放远程更新操作。浏览器没有本机 Desktop 信息，不检查 Desktop。

目标发布规则：仅发布 Server 时只更新 Server 清单；仅发布 Desktop 时只更新 Desktop 清单；两端同时发布时在一个渠道提交中更新两份清单。未更新端继续指向自己的最近成功发布包，不能因当前 Release 没有它的附件就显示无更新。

示例（目标行为，不代表实际发布）：

| Release | 本次新增包 | 发布后 Server 清单 | 发布后 Desktop 清单 |
| --- | --- | --- | --- |
| `Curated 20260930` | Server 1.7.7、Desktop 0.2.3 | 1.7.7 → 本批次 Server 安装包 | 0.2.3 → 本批次 Desktop 安装包 |
| `Curated 20260930-2` | 仅 Server 1.7.8 | 1.7.8 → 第二批次 Server 安装包 | 保持 0.2.3 → 第一批次 Desktop 安装包 |

第二批次发布后，使用 Server 1.7.6 / Desktop 0.2.2 的本机用户检查更新，分别看到 Server 1.7.8、Desktop 0.2.3 可用；已经安装 Desktop 0.2.3 的用户看到 Desktop 已是最新版本。下载入口指向各自清单的确切资产，选中 Server 不下载／安装 Desktop，反之亦然。检查失败应保留为检查失败，不能当作已是最新版本。

关于页继续分别展示本机 Desktop 与当前连接 Server 的产品版本及更新结果；共用一个“检查更新”按钮不要求共用一个版本号。Desktop 当前仍是下载后手动安装，合并 Release 本身不增加自动安装能力。组件清单必须在资产验收并公开后才推进，失败恢复沿用下一节规则。

实施与验收需覆盖：最近 Release 只有另一端时仍能找到本组件更新、两端来自不同批次、同批两端更新、按平台选包、单端检查失败不掩盖另一端结果，以及原有本机／远程权限边界。Server 新标签格式与旧客户端的兼容迁移仍须按下一节落实。

### 4. 必须一起解决的迁移边界

**新 tag 对旧 Server 更新器不兼容。** `backend/internal/appupdate/component_feed.go` 的 `selectServerRelease` 只接受下载路径 tag 以 `full-v` / `server-v` 开头。直接把既有 `server.json` 指向 `release-YYYYMMDD` 或其带序号的批次 tag 会使旧客户端拒绝更新资产。Desktop 当前校验 HTTPS manifest 与组件版本，没有相同 tag 前缀限制，仍应回归验证。

推荐在实施前落实桥接路径：先用旧 tag 发布能识别新批次格式的 Server；若要支持迟到用户跨多版本升级，还需让旧 feed 持续提供这个桥接版，让桥接版读新 feed（例如版本化渠道），或采用同等可验证的兼容方案。仅「先发桥接版、随后覆盖同一个旧 feed」不能保证未及时升级用户有路径。手动安装可作为明确说明的替代。具体迁移方案尚未实施。

**Latest 需要重新定义。** 建议新模式下指向最近成功公开的批次；Full 1.7.3 保留为显式历史迁移链接。需同步改发布、恢复和维护入口的选择规则，并验证旧 all-in-one 客户端不会把新批次误当自己的安装包。最新批次只更新一端时，说明提供两端当前下载入口。

**失败恢复与产品版本分离。** 同一不可变提交的基础设施重试保留批次／版本；修正源码或测试需要新的不可变批次提交和 tag，但不应仅因失败次数自动递进产品版本。未公开候选产品版本的复用须明确只允许未对外分发的候选；已公开／已交付安装包保持不可变。保留失败记录及生产包文件，不移动旧标签、不覆盖旧资产。

**两端合并发布的一致性。** 建议所选模块及平台全部通过才公开这次 Release；其中一个失败则保持 draft、渠道不动。GitHub 公开与渠道更新不是单一事务：公开后渠道失败要保留恢复状态，复用已验收资产恢复；两端渠道可沿用一次 Git tree/commit 更新，避免分两次推进。不能发布后不断往同一公开 Release 追加其他模块。

### 5. 后续实施切分与验收

| 7. 执行安装 | 当前做什么、是否还能取消 | 释放文件、注册快捷方式/卸载项、清理旧资源 | 显示真实阶段，避免虚构进度/剩余时间。进入不可中断阶段时解释；检查重复安装、锁定、磁盘写入失败。失败恢复能力必须实测，不能把引擎自带回滚当作完整保证 |
| 8. 安装结果 | 已安装哪个模块/版本、下一步 | 成功、失败、需重启、安装成功但启动失败 | 区分“程序已安装”“Server 已启动”“管理页可访问”。退出码/文件复制成功不能替代服务健康检查。失败页给重试、日志与明确诊断 |
| 9. 首次启动 | 怎么开始使用、数据在哪里 | Desktop 无 Server、Server 首次建库、已有配置 | Desktop 打开本地连接页；Server 提供“启动并打开管理页面”，确认本地服务就绪后打开实际地址。已有资料库不重复初始化 |
| 10. 首次设置 | 接入现有服务或建立资料库 | 发现/添加/选择 Server；设置目录/PIN/网络 | Desktop 不配置 Server 存储；Server 在本机 Web 页面设置资料库。保持现有仅本机可修改全局设置的边界。局域网访问由用户在应用内开启 |
| 11. 日常更新 | 哪个模块更新、是否需要更新另一端 | 检查 → Release Note → 下载 → 验证 → 用户开始安装 → 重启目标模块 | 两端独立；无变化模块保持版本和安装状态。不能把 Desktop 的手动下载现状说成已有自动安装。记住升级前运行状态，恢复策略需确认 |
| 12. 同版本重装/修复 | 文件损坏能否恢复、会不会清数据 | 覆盖重装、运行恢复、数据恢复 | 首期可明确为“重新安装程序文件，保留数据”；只有验证程序文件/登记等恢复能力后才称“修复”。数据库损坏是独立备份恢复流程 |
| 13. 卸载 | 删除什么、保留什么、另一模块是否受影响 | Desktop 卸载、Server 卸载、运行中卸载、用户取消 | Windows 已安装应用中独立入口；请求退出目标模块；默认保留连接/资料库/配置，不删除媒体。清除数据应独立管理，不默认勾选或混入普通卸载 |
| 14. 卸载后再安装 | 原设置能否恢复、是否沿用原数据 | 数据仍在、程序换路径、配置损坏 | 明确发现已有数据并沿用；不能因原路径暂时不可用就悄悄创建空库。重新安装不是重置产品 |

### 3. 六条应单独设计的入口路径

1. **Desktop 首次安装**：下载 Desktop → 信任提示（若出现）→ 语言/安装信息 → 预检 → 默认或自定义目录 → 安装 → 完成并启动 → 本地连接页 → 发现/输入 Server → 成功连接。没有 Server 时给用途说明及 Server 下载入口，不在 Desktop 包内安装 Server，也不以连接失败判定 Desktop 安装失败。
2. **Server 首次安装**：下载 Server → 信任提示（若出现）→ 安装信息/预检 → 安装 → 完成页选择启动并管理 → 等待服务就绪 → 打开本机管理页面 → 配置资料库。首次建议开机启动默认关闭，用户在应用内显式选择；升级保留原偏好。“开机启动”在当前实现中是用户登录后启动，不是未登录即可运行的 Windows 服务。
3. **已有独立模块升级**：识别已安装版本/路径 → 显示 A → B 与更新内容 → 明确影响并确认 → 请求目标模块退出 → 如需 Server 数据迁移先完成可验证备份 → 替换程序 → 启动/健康检查 → 结果与恢复说明。应保留程序路径、配置和用户数据；是否有数据迁移决定备份要求，备份耗时/磁盘成本不可隐藏。
4. **同版本再次运行**：说明已安装同版本 → 重新安装程序文件（保留用户数据）或退出；不要显示“有新版本”。如果未来提供修复入口，须单独定义校验范围。对程序目录的调整不能假装成普通修复。
5. **运行更旧版本**：说明已安装 B，本包为 A → 阻止普通降级 → 退出/获取当前包。Server 数据可能不可逆迁移，若未来支持降级，必须与兼容性检查、备份恢复配套，不能只比较程序版本。
6. **检测到旧一体版**：清楚说明这是旧安装体系 → 显示数据保留与迁移步骤 → 跳转已发布 Full 1.7.3 的一次迁移指南或取消。后续可另立方案把迁移协调移入独立 Server 安装器；当前并未批准。停止发布新 Full 不等于已实现独立 Server 对所有旧一体版的直接迁移。

### 5. 建议先确认的页面框架

更新：用户随后明确要求独立的“选择安装位置”页面。本节原三段式为早期建议，当前页面顺序以第 11 节为准；安装路径不再折叠到高级设置。

**首次安装采用三段主界面**（不含系统安全提示、可选语言选择及应用首次设置）：

- 安装信息：图标、Curated Desktop/Server、版本、一句话用途、主操作“安装”、高级设置（程序路径、可选桌面快捷方式）。协议/第三方许可证保留清晰可访问入口；需单独评估是否有必须接受的条款，不为了固定页面数删掉必要授权。

**升级复用三段界面，但改为升级语义**：检测原安装 → 确认 A → B 及关闭影响 → 退出/必要备份/替换进度 → 完成与恢复使用。不要重复询问首次配置和重置启动偏好。

| 问题 | 用户可见反馈与期望处理 |

### 7. 本轮需要用户确认的决策

1. **主交互形态**：建议三段主界面（信息/高级设置 → 进度 → 完成），首次设置在应用内；也可保留传统多页向导并逐页打磨。
2. **安装范围**：建议继续仅当前 Windows 用户；全机安装/Windows 服务模式另立需求，不加入普通安装主流程。
3. **Server 的完成动作**：建议提供默认勾选“启动并打开管理页面”，手动启动也有明确管理入口；登录后台启动保持安静。Desktop 完成后进入连接页。
4. **启动偏好**：建议首装不自动开启登录启动，升级保留原设置；是否在高级设置中增加该选项需确认。
5. **旧一体版过渡**：建议第一轮明确引导现有 Full 1.7.3 完成一次迁移；是否本轮就要实现独立 Server 直接迁移，属于额外功能范围。
6. **修复与数据**：建议普通卸载默认保留数据，独立提供数据管理说明；首期同版本入口称“重新安装”，完善验证后才提供正式“修复”。

签名需要单列资源决策；用户确认交互流程不等于批准购买证书或改变信任/发布设施。两端安装器共享模板若均有实际行为变更，后续应分别评估 Desktop 与 Server 的版本递进；本轮文档调研不递进任何模块版本。

### 10. 安装版本确认与运行状态处理：多分支细化（待确认）

状态：proposed；2026-09-28 用户补充要求：先显示已安装版本和待安装版本并确认；仅在目标程序运行时提供关闭操作；发现旧版本必须明确确认覆盖安装。本节细化前述三段主界面的条件分支，不表示批准开始编码。

#### 10.1 交互原则

- “版本提示”和“是否覆盖旧版本”在同一页完成一次确认：同时展示当前版本、目标版本、原安装位置、保留哪些数据，主按钮写“覆盖安装并升级”。避免先问一次版本、关完程序后又重复问是否覆盖。
- 运行状态是第二层判断，发生在用户同意安装之后；未同意安装时不关闭任何程序。初始页面可只读显示运行状态，但关闭动作必须晚于安装确认。
- 仅当目标模块确实在运行时出现“关闭程序”步骤。停止运行不只指窗口消失；托盘和后台进程均算运行，真正退出并释放相关文件/数据锁才可继续。
- 正常路径检测到运行实例后，提供“关闭并继续安装”；安装器发起有序退出并显示等待状态。用户不必默认去任务管理器操作；自动退出失败才给手动关闭与重新检查。
- 安装 Desktop 只处理这个 Desktop 安装实例；安装 Server 只处理这个 Server 安装实例。Server 停止可能使本机/远程 Desktop 暂时断连，但不关闭它们。便携版、开发实例、其他账户或其他目录实例不能仅按进程名当成本次目标。
- 版本无法识别、安装路径存在冲突、退出结果未知均为明确异常，不按“未安装/未运行”放行。

#### 10.2 总体分支树

阅读说明：下列版本/运行状态分支继续适用；第 11 节补入独立安装位置页。实际顺序为版本信息 → 选择位置 → 汇总并确认安装/覆盖 → 按需关闭程序 → 安装。下列“确认”节点须在用户选定并校验路径后才执行，初始版本页的“下一步”不触发关闭或覆盖。

```text
│
├─ 基础预检失败 / 同模块另一个安装器正在操作
│  └─ 显示原因 → 重新检查 / 退出；不关闭程序、不覆盖文件
│
└─ 识别当前模块的安装身份、路径和版本
   ├─ 未发现已有安装，目标目录无冲突
   │  └─ 首次安装页 → [安装] / [取消]
   ├─ 已安装版本 < 安装包版本
   │  └─ 显示“已安装 A，本次安装 B，是否覆盖升级？”
   │     └─ [覆盖安装并升级] / [取消]
   ├─ 已安装版本 = 安装包版本
   │  └─ 显示“已安装此版本，是否重新安装程序文件？”
   │     └─ [重新安装] / [取消]；保留数据，不称有新版本
   ├─ 已安装版本 > 安装包版本
   │  └─ 提示已有较新版本 → [退出]；不提供普通降级，不关闭程序
   ├─ 旧一体版与本次目标存在迁移冲突
   │  └─ 说明需要迁移 → [查看迁移说明] / [退出]；不走普通覆盖
   └─ 版本/身份读取失败，或目录/多个安装来源有冲突
      └─ 说明无法安全确定目标 → [重新检查] / [查看详情] / [退出]

用户确认安装、覆盖升级或同版本重装
│
└─ 重新确认安装目标有效，并检测该实例是否正在运行
   ├─ 未运行
   │  └─ 不显示关闭提示 → 安装前最终检查
   ├─ 正在运行且可以处理
   │  └─ 关闭确认页：展示模块及影响
   │     ├─ [取消安装] → 退出，不覆盖文件
   │     ├─ 用户自行关闭 → [重新检查] → 已退出则继续，仍运行则留在本页
   │     └─ [关闭并继续安装]
   │        └─ 显示“正在关闭…” → 请求目标程序有序退出
   │           ├─ 已退出且锁已释放 → 安装前最终检查
   │           └─ 忙碌 / 拒绝退出 / 超时 / 权限不足
   │              └─ 失败说明 → [重试关闭] / [手动关闭后重新检查] / [取消安装]
   │                 └─ 未确认退出前不覆盖；不增加默认强制结束分支
   └─ 运行状态无法确定或属于其他账户/会话
      └─ 明确原因 → [重新检查] / [取消安装]；不按未运行处理

安装前最终检查
├─ 目标身份/路径/版本发生变化 → 返回版本确认，旧确认失效
├─ 目标重新启动 → 回到有条件的关闭处理，不直接覆盖
├─ 文件/数据锁未释放，空间或权限不满足 → 处理原因后重试 / 取消
├─ Server 本次需要数据迁移备份且备份失败 → 停止，不替换文件
└─ 可以安装 → 替换本模块程序文件
   ├─ 安装失败或中断 → 显示实际阶段、日志、重试/恢复入口
   └─ 安装成功 → 显示完成版本与运行选项
      ├─ 用户暂不启动 → 结束
      └─ 启动目标模块
         ├─ Desktop 成功启动 → 恢复连接或进入连接页；连接失败独立处理
         ├─ Server 健康检查通过 → 恢复运行；按用户选择打开管理页
         └─ 启动失败 → “程序已安装，但启动失败” → [重试启动] / [查看日志] / [完成]
```

未发现安装登记不代表目标目录可直接覆盖：遇到现存程序文件、便携实例或保留数据应先识别。仅保留了程序外用户数据、程序目录无冲突时，可走首次安装并提示沿用数据；不擅自清空配置。

#### 10.3 典型组合与用户实际看到的步骤

| 安装关系 | 目标运行状态 | 用户流程 |
| --- | --- | --- |
| 未安装 | 未运行 | 首装确认 → 安装 → 完成；不出现旧版或关闭提示 |
| 已装较旧版 | 未运行 | 显示 A → B 并确认覆盖 → 安装 → 完成；不出现关闭提示 |
| 已装较旧版 | 运行中 | 显示 A → B 并确认覆盖 → 关闭影响与操作 → 自动退出成功 → 安装 → 完成 |
| 已装同版本 | 未运行 | 确认重新安装 → 安装 → 完成 |
| 已装同版本 | 运行中 | 确认重新安装 → 关闭影响与操作 → 退出成功 → 安装 → 完成 |
| 已装较新版 | 任意 | 显示两个版本并拦截降级 → 退出；不影响现有进程 |
| 旧一体版冲突 | 任意 | 迁移说明 → 进入迁移指导或退出；不冒充独立模块覆盖 |

#### 10.4 关键页面文案草案

示例版本仅用来说明流程，不代表递进实际版本。

**覆盖确认页：**

> 检测到已安装 Curated Server 1.7.3。
>
> 本次将安装 Curated Server 1.7.4，并替换原位置的程序文件。
> 安装位置：<检测到的原安装路径>
>
> 现有资料库、配置和媒体文件将保留。是否继续覆盖安装并升级？
>
> [取消] [覆盖安装并升级]

Desktop 使用相同结构，保留说明改为“服务器连接、登录状态和客户端设置将保留”，只有确认实现能保留的项目才能进入最终文案；遇到必要的身份/认证迁移应另行准确提示。

**正在运行，Server：**

> Curated Server 正在运行。
> 继续安装需要先退出 Server。连接它的客户端将暂时断开，正在进行的播放、上传和后台任务可能中断。
> 请完成当前操作后继续。安装程序将尝试正常退出 Server。
>
> [取消安装] [重新检查] [关闭并继续安装]

如果系统能可靠识别活动任务，可补充具体任务信息；未具备检测能力时只能说明可能影响，不可声称“当前没有任务”。Desktop 提示“需要退出 Curated Desktop，请先保存未完成的编辑；Server 将继续运行”，并说明当前窗口/播放会关闭。

**关闭中：**

> 正在关闭 Curated Server，请稍候……
> 确认退出后将继续安装，程序文件尚未替换。

此时仍允许请求取消，但如果退出请求已经发出，取消不能保证应用维持运行；应等待关闭操作状态明确后结束流程，不与关闭操作并发启动旧程序。

**自动关闭失败：**

> 暂时无法关闭 Curated Server，尚未替换程序文件。
> 原因：<可理解的原因；详细错误保留在详情/日志>
> 请从托盘菜单退出 Server，再点击“重新检查”。
>
> [取消安装] [重新检查] [重试关闭]

窗口关闭但托盘仍在时，明确提示“关闭窗口不会退出程序，请使用托盘 → 退出”。其他用户/会话拥有的实例只能提示在对应会话退出，不反复尝试跨账户强制关闭。

#### 10.5 取消、恢复与再次检测

| 取消/异常时点 | 必须准确说明的结果 |
| --- | --- |
| 尚未确认覆盖 | 不关闭程序、不修改程序或数据 |
| 覆盖已确认，但尚未请求关闭 | 不修改程序文件，原程序继续运行 |
| 请求退出过程中取消 | 停止后续安装，等待退出请求结果；可能已经退出，不承诺仍在运行 |
| 程序已退出，但尚未替换文件时取消 | 提示“安装已取消，原版本仍在；程序已退出”，可提供“重新打开原版本”；只有确认原程序完整、数据未变更时才允许 |
| 已开始替换程序/迁移数据后失败或取消 | 按实际结果说明恢复状态；未证明程序和数据库均可回退时，不自动启动旧版本，不泛称“一切未改变” |
| 初次检测后程序重新启动 | 写入前复检、阻止同目标并发操作；检测到运行则回关闭步骤。仅做一次检测或复检不能消除竞争条件，实施时还需关闭与替换之间的互斥及文件锁处理 |
| 检测信息在确认后变化 | 重新识别版本和路径；如目标与原确认不同，重新确认，不能把旧授权套给新目标 |

升级完成建议依据升级前运行状态提供默认值：之前运行的模块默认勾选“重新启动”，之前未运行则不强制启动；Server 升级恢复后台运行不默认额外打开浏览器，“打开管理页面”独立可选。首次安装完成动作沿用上节建议。该默认值同样待用户确认。

#### 10.6 范围与下一步

本轮仅更新流程文档，不改安装器、不打包、不调整 Desktop/Server 版本。现有源码已经有退出 helper 和较新版本拦截，但不能据此宣称用户报告的关闭/提示问题已解决；后续获准实施时，先用真实运行中的两类安装实例复现，再验证上述多分支交互和取消/恢复结果。

本节确认后才能细化页面视觉、退出机制和验收实现。关键待确认点是：合并“版本提示+覆盖确认”为一次；运行中额外一步“关闭并继续”，未运行直接跳过；同版本只做重装、较新版阻止降级；升级结束按原运行状态建议重启。

### 11. 独立“选择安装位置”页面（用户确认的交互要求）

2026-09-28 用户明确要求：像常见 Windows 安装向导一样，提供一个可设置安装位置的独立页面，并预填默认地址。本项交互要求已确认；整体优化方案仍为 proposed，尚未授权开始修改安装器。此节取代早期“安装位置收进高级设置”和三段主界面的建议；具体路径迁移行为仍为下述待确认建议。

#### 11.1 页面顺序

1. **安装/版本信息**：首次显示模块用途和待安装版本；升级显示已安装版本与本次版本，并说明将更新已有安装。点击“下一步”进入目录页，不关闭程序、不替换文件。较新版本、旧一体版冲突等仍按第 10 节分流。
2. **选择安装位置**：显示可编辑路径和“浏览…”按钮；首次预填默认目录，升级/同版本重装预填检测到的原安装目录。建议这些场景均显示本页，升级不再因引擎默认行为而直接跳过。支持上一步、下一步、取消。
3. **准备安装 / 确认覆盖**：汇总模块、当前/目标版本和用户最终选定的安装路径，说明保留数据；首次按钮“安装”，升级按钮“覆盖安装并升级”，同版本按钮“重新安装”。版本与覆盖只在此做一次最终确认，不重复弹相同确认框。
4. **按需关闭程序**：确认后复检运行状态；未运行直接跳过，正在运行才显示“关闭并继续安装”及重试/取消分支。路径等可提前发现的问题先处理，避免无谓关闭正在使用的程序。
5. **安装进度**：写入前最终复检，执行已确认的安装目标。
6. **安装完成**：显示结果与启动选项，沿用第 10 节的首次启动/恢复运行区分。

简化表达：安装/版本信息 → 选择安装位置 → 安装/覆盖确认 →（仅运行时）关闭程序 → 安装进度 → 完成。

#### 11.2 目录页内容

- 标题：选择安装位置。
- 说明：选择 Curated Desktop / Server 的安装文件夹。使用默认位置可直接点击“下一步”，也可输入路径或点击“浏览…”更改。
- 路径输入框：展示完整的实际路径，不只显示环境变量占位符。
- 操作：浏览…；返回默认位置（升级时标为“使用原安装位置”）。
- 容量信息：所需空间、目标磁盘可用空间；安装所需临时空间另行纳入检查，不把包体大小当作所需空间。
- 数据说明：这里只设置程序位置；Server 数据库、配置和媒体位置在应用内另行管理，更改程序位置不会自动搬动资料库。
- 底部按钮：上一步 / 下一步 / 取消。

默认路径沿用当前用户安装的目录结构：

| 模块 | 首次安装预填值 | 已有安装预填值 |
| --- | --- | --- |
| Desktop | `%LOCALAPPDATA%\Programs\Curated\Desktop` | 检测到的 Desktop 原安装目录 |
| Server | `%LOCALAPPDATA%\Programs\Curated\Server` | 检测到的 Server 原安装目录 |

用户可以为首次安装选择其他可写位置，例如 `D:\Apps\Curated\Desktop` 或 `D:\Apps\Curated\Server`。自定义程序位置不自动将安装范围改成全机安装。不要默认把两个模块写入同一个目录。

#### 11.3 点击“下一步”的分支

| 条件 | 页面处理 |
| --- | --- |
| 默认或自定义路径有效、可写、空间足够且无冲突 | 进入准备安装页，展示最终完整路径 |
| 目标文件夹尚不存在，但父目录有效且可写 | 允许继续；在实际安装阶段创建文件夹 |
| 路径格式不合法、盘符不可用、权限不足或空间不足 | 留在本页，在路径附近显示具体原因，允许修改后重试 |
| 目标目录属于另一模块、另一实例，或包含无法确定归属的文件 | 说明目录冲突，要求选择独立目录，不把一般非空目录当作可随意清空的安装目录 |
| 用户返回修改目录 | 保留已输入值；更新空间和冲突检查；后续确认页必须显示新的路径 |
| 升级/重装保持原位置 | 普通覆盖安装，进入版本与覆盖确认 |
| 升级/重装改为新位置 | 识别为“更改程序安装位置”，显示原位置 → 新位置及数据不搬动说明；不能当成原位置覆盖，不能未经设计就留下两套程序或错误卸载登记 |

更换已有安装位置的完整支持范围仍待确认。建议若纳入本轮，就设计新目录安装、验证、快捷方式/卸载信息/登录启动路径更新、旧受管理程序文件清理及失败恢复的完整流程；安全退出也必须针对原安装实例，而不是只查新目录。若本轮不做迁移，应在目录页明确提示当前安装需要沿用原位置并允许一键恢复原路径，不可接受新地址后悄悄忽略它。不得删除旧目录中的用户自建文件。

#### 11.4 本轮变更范围

只更新待确认方案文档；未修改 Inno 模板、运行时或发布脚本，未打包，Desktop/Server 版本不递进。无需在此阶段把所有原生向导页数压缩到三页，优先满足独立目录选择、清楚确认和按需关闭的连贯流程。

- `internal/launchprofile` 让 Windows standalone Server 普通启动持续沿用原数据根目录和已保存 custom config，防止首次升级成功后重启误建空库。原配置只保存副本，不改写其内容；自定义文件系统路径须为绝对路径。
- 已实现默认/外置数据根、自定义安装目录与外置绝对路径配置。阻止数据/媒体根位于旧安装树、相对路径、程序树链接、同时安装旧版与 split Server、运行中的 Curated。用户仍需从托盘退出；不强杀进程，不自动迁移跨账户或程序目录内数据。
- 仅旧机器级卸载器通过 UAC 提升权限，其余新组件仍以 Full 的用户身份运行。旧 Desktop 连接文件仅在新文件不存在时复制，原认证数据库不合并。
- CD 新增真实 1.5.8 和 1.4.13 SHA-256 固定基线，覆盖 custom data/config、数据保留、普通启动恢复原端口、启动项接管、重试和卸载保留数据。现有 split 基线检查保留。
- 本地迁移/启动配置、备份、CLI 和版本测试通过，release-tag 测试及 go vet 通过，Windows helper/Server 交叉编译通过。Windows Inno 编译、真实安装器执行、UAC 交互未在本机执行，必须等待 Windows CD 验收；不把源码修改当成正式发布。
- 与原目标的差异：健康检查和新 Server 数据库实际升级由 Windows smoke 验收；安装器完成后启动失败仍由 Server 报错，不自动恢复旧程序。程序内数据搬移、自动关闭所有旧进程、任意历史包逐版认证仍待后续扩展。

### 目标与结论

可以实现：用户运行一次 Full 安装器，即完成旧一体版到独立 Server/Desktop 的升级，无须先到系统中手动卸载。Full 离线包含全部必需组件。安装器负责程序替换及旧安装登记、快捷方式、启动项的交接；原资料库和配置保留，完成后连接原 Server 数据。

“1.8 以下”需要按实际已发布版本建立兼容矩阵：1.6.x / 1.7.x 拆分版沿用现有升级路径；1.5.8 及更早一体版新增自动迁移。Full 1.7.2 不应降级任何已安装的较新组件；不能把尚未发布的未来 1.7.x 也承诺为可升级到 1.7.2。更早历史版的最低支持范围须根据真实安装包验收确定。

### 已确认的阻碍

- `scripts/release/windows/Component.iss.tpl` 的 `InitializeSetup` 检测旧 GUID 卸载项后直接阻止 Server 安装；并非已经证实数据库格式无法升级。
- `scripts/release/windows/Full.iss.tpl` 仅依次调用组件安装器，尚无旧版发现、备份、关闭、迁移、恢复编排。仅删除拦截会留下双程序、旧自启动和端口争用。
- 旧 `Curated.iss.tpl` 默认装入 Program Files、使用旧 GUID 和默认管理员权限；新组件使用当前用户目录与 `Curated.Server` / `Curated.Desktop` 身份。清理旧机器级安装可能需要 UAC，但数据和新组件必须仍归属原登录用户。
- release 默认数据根目录仍为 `%LOCALAPPDATA%\Curated`，具备原地复用基础；`CURATED_DATA_DIR`、自定义 `-config`、程序目录内配置、其他账户数据不能直接假定为默认布局。
- Electron 保留由包身份决定的 `userData`；旧一体版到独立 Desktop 的配置目录及会话兼容不能用 0.1.0 → 0.2.0 的拆分版验收代替。
- CD 会复用已发布的同版本组件产物。若修改 Server 安装器，必须增加 Server 版本，否则 Full 仍会嵌入含旧拦截逻辑的安装器；若修改 Desktop 迁移逻辑，也必须增加 Desktop 版本。

### 建议实施流程

1. **发现与预检**：识别 HKLM/HKCU、32/64 位旧安装项，定位真实程序、运行账户、数据库、配置和启动参数；验证目标组件版本和完整离线载荷。多个来源或数据位置不明确时在向导内要求选择，不自动创建空库掩盖迁移失败。便携版没有卸载登记，需要单独的目录选择与预检。
2. **停止与备份**：请求退出目标旧壳层和后端，确认实际进程及数据库锁已释放；只处理已识别的安装实例，不按同名进程全局终止。使用兼容旧数据的维护流程生成并校验备份，涵盖数据库、配置和必要身份文件，处理 SQLite WAL 一致性。备份失败时不进入程序替换。
3. **安装与接管**：Full 编排安装两组件且暂不启动；Server 的旧安装拦截只在经过有效迁移预检的路径下放行，单独安装仍防止冲突。迁移记录与校验必须真实存在，不能仅靠任意命令行开关跳过保护。保留数据位置，显式承接配置、端口及启动参数，避免安装目录变化改变相对路径含义。
4. **切换与验证**：停用旧自启动，按原启动偏好创建新入口，启动新 Server 并验证原库、配置和服务身份，再让 Desktop 连接。迁移保存的连接记录时保留已有新配置，处理来源冲突；旧认证会话是否可保留独立验收，必要时重新解锁不应导致资料库丢失。
5. **旧程序清理与恢复**：成功后处理旧快捷方式、程序和卸载登记；可由 Full 内部编排旧卸载程序，但必须先确认其删除范围不会包含仍使用的数据或配置。对含用户数据的旧程序目录不能递归直接删除。记录迁移阶段，组件部分成功、UAC 取消和中断均可重试；新 Server 已升级数据库后，不允许直接重启旧 Server，恢复须使用经验证的原备份。

Full 保持以原用户身份运行；仅确需处理旧机器级程序的受限步骤提升权限。不得把整个安装流程切到另一管理员账户后启动新 Server。自定义配置需要在后续快捷方式、自启动与升级重试中持续保留，而不只是首次启动传一次参数。

### 1.1.1 当前生效的生产包版本规则（2026-04-12）

- 生产包版本的唯一自动化来源是 `scripts/release/version.json`，当前基线为 `1.3.1`。
- `pnpm release:portable`、`pnpm release:installer`、`pnpm release:publish` 在未显式传入 `-Version` 时，都会自动把 `patch` 加 1。
- `pnpm release:publish` 只在入口处分配一次新版本，再把同一个版本号传给便携包、安装包与 `release/manifest/release.json`，避免一轮整机发布消耗多个 patch。
- `major` / `minor` 只允许人工调整，命令为 `pnpm release:version:set-base -- --Major <major> --Minor <minor>`；调整时必须把 `patch` 重置为 `0`。
- `package.json` 的 `version` 不再作为生产包版本来源。
- 同一次发布中，安装包文件名、便携包文件名、`release/manifest/release.json` 与 `docs/ops/2026-04-02-package-build-history.md` 必须保持一致。

当前推荐入口命令：

```powershell
pnpm release:publish
```

如需固定构建戳，可显式执行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/release/publish.ps1 -BuildStamp <yyyyMMdd.HHmmss>
```

以下段落保留为 2026-04-12 之前的链路说明；当前生效规则以上一节 `1.1.1 当前生效的生产包版本规则` 为准。旧流程里，正式整机安装包需要显式传入 `-Version`：

### 主链路

当前完整发布入口是 `scripts/release/publish.ps1`，执行顺序如下：

```text
  -> build-backend.ps1
  -> assemble-release.ps1
  -> package-portable.ps1
  -> package-installer.ps1
  -> write release/manifest/release.json
```

### 运行态链路

当前 release 二进制的运行态关键点：

- `-tags release` 使后端默认 HTTP 地址从 `:8080` 切到 `:8081`。
- `-tags release` 使 `version.Channel` 为 `release`，健康名为 `curated`。
- Windows + release build 默认启动模式为 `tray`：启动本地 HTTP 服务、托盘图标、单实例互斥，并打开浏览器。
- 后端 `webui.FindDistDir()` 会优先从可执行文件旁查找 `frontend-dist/` 或 `dist/`，因此安装目录中的 `curated.exe + frontend-dist/` 可以直接服务前端页面。
- 前端生产构建未设置 `VITE_API_BASE_URL` 时，`src/api/http-client.ts` 默认请求同源 `/api`，由 release 后端的 8081 静态托管入口接住；局域网客户端访问 `http://<host-ip>:8081` 时也会请求同一主机的后端。
- release build 的默认数据根目录为 `%LOCALAPPDATA%\Curated`，可通过 `CURATED_DATA_DIR` 覆盖；默认派生：
  - `config/library-config.cfg`
  - `data/curated.db`
  - `cache/`
  - 日志目录在托盘菜单中按配置解析，未显式配置时基于数据根目录的 `logs/`。

## 3. 生产发布的核心原则

### 3.1 程序文件与可写数据分离

生产版必须将以下内容分开：

- 程序本体
  - `curated.exe`
  - 内嵌前端静态资源
- 可写数据
  - 配置文件
  - SQLite 数据库
  - 缓存目录
  - 日志目录

推荐目标不是“所有内容都封进一个可执行文件内部再原地修改”，而是：

**单二进制分发 + 外置数据目录**

### 3.2 升级不覆盖用户数据

生产版升级应满足：

- 替换程序文件即可升级
- 不覆盖用户配置
- 不清空数据库
- 不删除缓存和日志

### 3.3 首次启动自动初始化

生产版应尽量做到：

- 首次启动自动创建数据目录
- 首次启动自动创建默认配置文件
- 数据库不存在时自动初始化
- 即使还没有配置任何资料库路径，也能先正常启动

### 3.4 版本信息必须稳定可见

由于项目已有“程序里必须显示版本”的约定，生产方案必须满足：

- 程序 UI 中必须能显示版本信息
- 后端 API 仍必须返回版本信息
- release 产物中的版本号必须是可追踪、可复现、可区分渠道的
- 安装器版本、绿色版 zip 版本、程序运行时显示版本必须保持一致

## 16. 预览包可行性补充（2026-04-16）

### 16.1 当前状态结论

当前仓库对“预览包”是**部分具备基础，但还没有完整支持**。

已经具备的基础：
- `-tags release` 构建默认把可写数据放到 **`%LOCALAPPDATA%\Curated`**，即：
  - `config/library-config.cfg`
  - `data/curated.db`
  - `cache/`
  - `logs/`
- 这意味着：**只要还是 release 语义的构建，天然就能复用正式版已经存在的数据库、配置和缓存目录**。

当前缺失的部分：
- 发布脚本当前只有 **`release`** 通道，没有 **`preview`** 通道。
- 安装器模板当前固定写死：
  - `AppId={{8C9E9E66-7058-4D09-9F9A-8AFD060A7E1B}`
  - `AppName=Curated`
  - `DefaultDirName={autopf}\Curated`
  - `AppMutex=Local\Curated.Tray.Singleton`
- 这表示当前如果直接“再打一份预览安装包”，它不会是一个真正独立的 preview 安装身份，而更像同一个正式版产品的另一份安装产物。

### 16.2 是否能支持

**能支持。**

但要先明确一个边界：你说的“预览包”其实包含两个不同层面的诉求：

1. **安装身份**
   - 是覆盖正式版安装，还是作为 `Curated Preview` 并存安装。
2. **数据身份**
   - 是继续共用 **`%LOCALAPPDATA%\Curated`**，还是使用独立的 preview 数据目录。

### 16.3 三种可选方案

#### 方案 A：预览包覆盖正式版安装，共用正式版数据

特点：
- 改动最小。
- 安装器仍沿用同一个 `AppId`、安装目录和快捷方式。
- 数据继续使用 **`%LOCALAPPDATA%\Curated`**。

优点：
- 实现成本最低。
- 升级/回滚路径简单。

缺点：
- **不能与正式版并存安装。**
- 用户体验上更像“候选正式版”，不是真正独立的 preview。

#### 方案 B：预览包独立安装，共用正式版数据

特点：
- 安装器使用独立身份，例如：
  - `AppId=Curated Preview`
  - `AppName=Curated Preview`
  - `DefaultDirName={autopf}\Curated Preview`
- 但运行时**仍然指向**正式版同一份数据根：
  - **`%LOCALAPPDATA%\Curated`**

优点：
- **可以和正式版并存安装。**
- 预览包可以直接读取现有数据库、配置、缓存，满足“无缝接上正式版数据”的目标。
- 最符合“预览包是整机包，但又不重新建一套库”的诉求。

缺点：
- 必须认真处理**并发访问同一份 SQLite / 配置**的问题。
- 预览包和正式版不能被允许同时运行并同时写同一份数据。

补充约束：
- 如果 preview 与 release 共用同一份数据目录，建议它们也共用同一把全局互斥锁，或者显式做“跨通道单实例”控制。
- 否则两个安装实例同时打开同一个 `curated.db`，风险不可接受。

#### 方案 C：预览包独立安装，独立数据目录

特点：
- 安装身份独立。
- 数据目录也独立，例如 **`%LOCALAPPDATA%\CuratedPreview`**。

优点：
- 最安全，互不影响。
- 不存在共用 SQLite 的运行时竞争。

缺点：
- **不满足“无缝复用正式版数据库/配置”的核心诉求。**

### 16.4 推荐方案

**推荐方案 B：独立安装身份，共用正式版数据目录。**

这是最符合“预览包是一个可安装的整机包，同时又能直接接上正式版已有数据库和配置”的方案。

但必须附带两个硬约束：
- **硬约束 1：preview 与 release 不能同时运行。**
- **硬约束 2：preview 默认不自动接管正式版的自启动、系统集成和默认打开行为。**

### 16.5 为支持方案 B 需要补的实现点

1. **新增打包通道/风味（flavor）**
   - 当前只有 `release`。
   - 需要新增一个例如 `preview` 的打包风味，但它的数据目录策略要继续复用 release 的用户数据根。

2. **脚本参数化**
   - `build-backend.ps1`
   - `assemble-release.ps1`
   - `package-installer.ps1`
   - `publish.ps1`
   - 这些脚本都需要支持 `-Channel` 或 `-Flavor`，不能再把 `release` 写死。

3. **安装器模板参数化**
   - `AppId`
   - `AppName`
   - `DefaultDirName`
   - `DefaultGroupName`
   - 输出文件名
   - 让 preview 包拥有独立安装身份。

4. **运行时版本/渠道显示**
   - 当前 `version.Channel` 只有 `dev` / `release`。
   - 需要新增可显示的 preview 标识，至少让健康检查和 UI 能看出这是 preview 包。

5. **开发态功能开关**
   - 不能直接把 preview 做成 dev build。
   - 正确做法应是：**仍然是 production packaging / release-style runtime**，但通过显式的 feature flags 打开部分开发态能力。

6. **共享数据下的互斥策略**
   - 如果 preview 共用正式版数据目录，建议复用正式版 mutex，或单独增加一个“共享数据根互斥”。
   - 目标是防止 preview 和 release 双开。

7. **自启动与系统集成策略**
   - preview 不建议默认写正式版相同的开机自启项。
   - 是否允许 preview 修改正式版的系统自启配置，需要单独定规则。

### 16.6 一句话结论

**支持，但不能只靠“再打一份 release 安装包”解决。**

如果要满足：
- 可安装到本机
- 保留 preview 独立身份
- 无缝复用正式版数据库与配置

则需要把当前发布体系从“单一 release 通道”扩展为“release / preview 两种 packaging flavor + 共享数据策略 + 跨安装实例互斥策略”。

## 17. 打包历史补充：记录相对上一包的 Git 变更内容（2026-04-16）

### 17.1 目标

在 `docs/ops/2026-04-02-package-build-history.md` 的表格中新增一列：

- `变更内容`

用于记录**本次打包相对于上一条打包记录**之间的 Git 提交历史，直接来源于 `git log --oneline`，不做智能归类、不做自然语言总结。

### 17.2 适用范围

本规则适用于所有会自动写入打包历史的打包类型：

- `release:publish`
- `release:installer`
- `release:portable`

也就是说，不区分打包类型；只要脚本调用 `Add-PackageBuildHistoryEntry` 追加台账，就要同时写入 `变更内容`。

### 17.3 对比基线定义

`变更内容` 的生成范围定义为：

- **上界**：当前写入打包历史时的 Git `HEAD`
- **下界**：打包历史文件中**上一条记录**的 `提交 / 分支` 列里记录的 commit short SHA

等价于执行：

```powershell
git log --oneline <previous-commit>..<current-commit>
```

注意点：

- 这里的“上一条记录”指打包历史文件里时间上紧邻当前追加位置的上一行有效记录。
- **不是**“上一条同类型打包记录”。
- 这样可以保证在“所有打包类型都写历史”的规则下，对比基线始终唯一且稳定。

### 17.4 写入内容格式

`变更内容` 列直接写 `git log --oneline` 的结果，保留原始提交标题，使用 Markdown 单元格安全编码后写入：

- 多条提交之间使用 `<br>` 换行
- 不做 `feat/fix/revert/docs` 分类
- 不额外改写成“新增 / 修改 / 回退”中文摘要

示例：

```text
abc1234 feat(player): add external player settings<br>
def5678 fix(release): keep installer close-app behavior<br>
9876abc docs: update release packaging notes
```

### 17.5 特殊情况规则

#### A. 同一提交重复打包

如果上一条记录和当前记录指向同一个 commit，则写：

```text
无代码差异（同一提交重复打包）
```

#### B. 历史中没有上一条记录

如果当前要写入的是第一条打包记录，没有可对比的上一条记录，则写：

```text
首条打包记录，无上一包可比对
```

#### C. 无法解析上一条记录中的 commit

如果上一条记录里的 `提交 / 分支` 列格式异常，或 short SHA 无法在当前仓库解析到真实 commit，则写：

```text
无法解析上一条打包记录对应 commit
```

#### D. 范围内没有新提交

如果 `git log --oneline <prev>..<current>` 返回空，等价处理为：

```text
无代码差异（同一提交重复打包）
```

### 17.6 文档表头调整

`docs/ops/2026-04-02-package-build-history.md` 的历史表格表头需要从：

```text
| 日期 | 版本 | 提交 / 分支 | 打包类型 | 产物路径 | 状态 | 操作人 | 备注 |
```

调整为：

```text
| 日期 | 版本 | 提交 / 分支 | 打包类型 | 产物路径 | 状态 | 操作人 | 变更内容 | 备注 |
```

同时需要把已有历史记录补一个占位值，避免 Markdown 表格列数不一致。历史旧记录的 `变更内容` 可统一补为：

```text
历史记录补齐前未采集
```

### 17.7 脚本实现边界

实现应集中在 `scripts/release/release-common.ps1` 中，围绕 `Add-PackageBuildHistoryEntry` 补齐，避免把同一套逻辑分散到：

- `publish.ps1`
- `package-installer.ps1`
- `package-portable.ps1`

推荐新增两个辅助函数：

- `Get-LastPackageHistoryCommit`
  - 从历史文件中解析上一条记录的 short SHA
- `Get-PackageHistoryChangeSummary`
  - 基于 `git log --oneline <prev>..<head>` 生成要写入 `变更内容` 的文本

然后由 `Add-PackageBuildHistoryEntry` 在最终拼接 Markdown 行时统一写入。

### 17.8 不做的事情

本次规则明确**不做**以下能力：

- 不按 `feat/fix/revert` 自动归类
- 不生成中文“新增了什么 / 修改了什么 / 回退了什么”的总结句
- 不按“上一条同类型打包记录”作为比较基线
- 不跨版本号或 manifest 再做二次推断

目标只保留一个：

**在打包台账中稳定记录“上一包到当前包之间的原始 Git 提交标题列表”。**
