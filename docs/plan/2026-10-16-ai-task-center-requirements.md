# 任务中心：原始需求与通用 Task 定义

状态：implemented（首版源码与本地验证完成，未发布）
日期：2026-10-16
更新：2026-10-17
范围：用户已批准按稿实施；首版接入 AI 字幕与 AI 整理，后续旧操作接入仍为独立范围。

## 1. 原始诉求

AI 字幕识别与 AI 整理耗时较长。用户希望在状态栏附近提供统一任务中心：发起后能找到任务、持续查看进度，点击某一任务进入详情，了解确切进展。需要定义 AI 任务的共同概念与详情信息。

用户已明确的是统一入口、任务展示、进度和任务详情。用户随后批准按 UI 稿实施。下文保留需求与设计推导，实际交付及差异以 §14 为准。

## 2. 当前基础

源码已有独立的字幕与 AI 整理任务，以及 SidebarSubtitleEntry、SidebarTagOrganizationEntry 两个侧栏入口；分别打开业务弹窗。AppShell 已观察任务，业务任务并不依赖弹窗保持打开。AI 整理还会写入消息中心。

因此本需求主要是统一任务的产品表达与查看体验。是否合并执行队列、任务存储或调度，应在后续技术设计中评估，不能从“统一入口”直接推导出重建所有后台任务。

核对依据：src/components/jav-library/SidebarSubtitleEntry.vue、SidebarTagOrganizationEntry.vue；src/composables/use-subtitle-jobs.ts、use-tag-organization.ts；src/layouts/AppShell.vue；现有字幕及 AI 整理规划文档。旧文档中“字幕尚无侧栏入口”的描述已被后续实现更新。

## 3. AI 任务的产品定义

建议定义：一次有明确处理对象、目标和结果，执行过程可能跨越页面停留时间，且需要独立跟踪状态的 AI 后台作业。

- 一次任务对应一次用户可理解的目标，具有稳定身份、创建时间、输入范围、状态与结果。
- 任务可以包含多个阶段；阶段可以处理多部影片或多个音频分段。这些内部步骤默认归属于同一个任务。
- AI 字幕任务建议以一个具体视频文件及所选音轨为对象，包含识别、翻译和保存成果等阶段。
- AI 整理任务建议以一次确定的影片集合为对象，包含题材词汇归纳、逐片分类及应用结果等阶段。
- 一次任务内部的模型调用、轮询、分段和自动重试，不直接形成多个用户可见任务。
- 即时聊天、短小的同步 AI 操作不必全部登记到任务中心；今后需要脱离页面执行时再纳入。

## 4. 三层信息结构

| 层级 | 需要回答的问题 | 建议内容 |
| --- | --- | --- |
| 状态栏入口 | 现在有没有任务？有没有需要处理的问题？ | 运行数量、排队数量、需处理提示；不同任务的百分比不相加 |
| 任务中心列表 | 哪些任务在做什么？ | 类型与名称、处理对象或范围、状态、当前阶段、带单位的进度、时间；点击定位具体任务 |
| 任务详情 | 做到哪一步？完成了什么？接下来能做什么？ | 共用概览、阶段进展、业务明细、结果、问题原因及适用操作 |

建议保留现有业务发起入口；用户发起后任务进入中心，离开原页面仍可追踪。中心可先采用轻量面板，详情具有稳定的任务定位与返回路径。完整页面或抽屉等具体承载形式后续再定。

## 5. 任务详情的共同结构

1. **任务概览**：名称、类型、对象与范围、当前状态、创建/开始/结束时间、已耗时。模型与本次任务参数可收在次级信息中；不必把技术信息放在首屏。
2. **当前进展**：当前阶段、已完成/总量及单位、正在处理的对象、最近一次状态更新时间。
3. **阶段列表**：每阶段待开始、执行中、完成或异常；显示关键事件，原始日志仅作辅助诊断。
4. **处理明细**：批量任务显示成功、失败、跳过或未处理的项目，支持定位问题项。不同业务的计数含义必须明确。
5. **成果**：生成了哪些文件，或更新了哪些影片/标签；提供查看成果和回到关联影片的入口。执行结束与成果仍可用应分别表达。
6. **问题与操作**：失败或等待原因、是否还在自动处理、用户可以采取的下一步。仅显示该任务实际支持的操作。

## 6. 两类任务的专属详情

| 类型 | 特有信息 | 结果信息 |
| --- | --- | --- |
| AI 字幕 | 影片、实际文件/分部、音轨、源语言/目标语言、识别与翻译模型、当前音频分段及阶段进度 | 原文字幕、译文字幕、文本等实际成品；若仅部分阶段成功，明确已有成果和缺失部分 |
| AI 整理 | 本次选择范围及影片数量、词汇归纳进度、分类/应用进度、问题影片与原因 | 已整理、无匹配、失败、跳过等具有明确含义的结果，标签变化与依据，以及业务支持的撤销入口 |

以上是展示需求，具体字段和阶段应依据业务真实可提供的数据设计；不承诺所有字段当前已具备。

## 7. 状态与进度表达

建议统一用户能理解的状态：排队中、执行中、等待中、已完成、部分完成、失败、已取消。等待应说明是在自动等配额/外部服务，还是需要人工修复。取消中的任务应显示正在取消，只有实际停止后才显示已取消。

- 状态说明“任务处于什么情况”；阶段说明“正在做什么”；数量说明“这一阶段完成多少”。三者分别呈现。
- 优先显示可信的阶段进度，例如“翻译第 8/12 段”“分类已处理 126/300 部”。这些仅为示例。
- 外部服务不提供百分比时，显示正在等待结果、已等待时间与最近状态；不虚构百分比或剩余时长。
- 阶段数不等于耗时比例，不把完成三个阶段中的一个直接写成整体 33%。
- 客户端断线属于观察状态，不能据此把后台任务判为失败；保留最近快照并标记更新时间和同步状态。
- 任务完成后保留可回看的记录；历史保留周期与清理规则后续明确。

## 8. 操作与生命周期建议

首版建议支持查看详情与成果，以及业务已支持的取消、重试。暂停、继续、撤销均依赖具体业务能力，不作为所有 AI 任务的默认承诺。

取消的含义是停止后续处理，必须说明已有成果如何处理；撤销是恢复已经应用的变更，两者分开表达。重试应说明继续失败部分还是完整重新执行，并保留与原任务的关联，避免用户误判重复处理和费用。

关闭面板、切页和刷新后应能重新找到任务。Server 停止后任务无法继续运行；重启后的恢复、等待或失败应有明确状态，不承诺无限后台运行。任务列表建议限定当前连接的 Server，跨 Server 聚合留待后续讨论，查看与控制权限沿用业务权限。

## 9. 与消息中心的关系

建议任务中心负责持续查询任务状态、明细、结果与操作；消息中心负责完成摘要、失败或需处理的提醒，并链接到同一任务详情。每次进度变化不生成消息。现有消息中心曾规划承担部分系统状态展示，实施前需要确定入口分工，避免维护两个独立的任务列表。

## 10. 建议首版范围与后续决策

首版覆盖 AI 字幕和 AI 整理：统一入口与列表、进度和状态规范、两类详情、近期历史，以及实际支持的取消/重试/成果入口。

扫描、刮削、下载、转码等可作为未来任务类型；首版不因此扩张为全站任务迁移。并发设置、任务优先级、定时任务、工作流编排、精确费用估算和统一调度引擎均留待独立需求。

后续需要确认：入口最终位置及与现有状态区的关系；详情用页面还是抽屉；是否将暂停列为业务改造目标；历史保留与重试记录方式。这里列为设计决策，不阻碍本次原始需求梳理。

## 11. 产品验收场景草案

- 发起字幕任务后离开影片页，仍能从统一入口找到该任务，点开后看到对应文件和真实阶段。
- 两类任务同时存在时，能分清各自运行、等待或排队情况，不展示混合百分比。
- 发生翻译失败或部分影片整理失败时，详情能说明已完成内容、问题范围和可行的下一步。
- 刷新或短暂断线后能重新定位任务；同步中断不会误报任务失败。
- 任务完成后能从历史查看成果；消息提醒可进入同一任务详情。

本轮仅保存需求讨论稿，没有修改业务实现，也未登记为已批准的开发任务。

## 12. 通用 Task 方向确认（2026-10-17）

用户认可任务中心方向，并提出后续定义通用 Task，将已有的一些操作也纳入任务。此处确认产品方向，不等同于批准全部旧操作迁移；具体定义与接入清单仍需细化。前文的 AI 任务作为通用 Task 的首批类型理解。

建议定义：Task 是一次具有明确目标、处理范围、执行生命周期和可回看结果，需要被独立跟踪的作业。AI 是任务类型的特征，不是成为 Task 的必要条件。

### 纳入标准（建议）

先判断操作是否有明确的开始、结束和结果，再判断是否有独立追踪的价值，例如耗时较长、需要排队、批量处理、离开页面后仍需查看，或需要保留失败明细和重试入口。不以固定耗时阈值机械划分，较快完成的同类任务仍保持一致的任务身份。

| 操作类别 | 候选判断 | 理由 |
| --- | --- | --- |
| AI 字幕、AI 整理 | 首批接入建议 | 已有长时任务及独立状态 |
| 扫描、批量刮削、导入、转码 | 后续评估 | 有明确处理范围、阶段和结果，用户有跨页面追踪需求 |
| 下载、备份、健康检查 | 按具体业务评估 | 是否需要独立追踪、结果回看及失败处理决定接入价值 |
| 收藏、评分、保存普通设置 | 通常不纳入 | 当场反馈即可，任务记录价值较低 |
| 播放会话、常驻目录监听 | 本身通常不纳入 | 属于会话或常驻服务；监听触发的一次扫描可以是 Task |

以上为产品候选分类，不代表已审计全部旧操作或承诺接入。

### 统一内容与业务差异

共用身份、类型、目标/范围、状态、进度语义、关键时间、结果摘要及详情入口。业务自行提供阶段、处理明细、成果和实际支持的操作。取消、重试、暂停、恢复、撤销不是所有 Task 的必备能力。

一次用户目标默认对应一个主任务，阶段和处理项收在详情中。例如一次批量整理以一个主任务承载，逐片结果作为明细；只有确有独立调度或独立操作需求时，再讨论子任务。后台自动触发的作业也可成为 Task，但并非每条内部请求都进入用户任务列表。

建议后续先盘点旧操作，逐项记录触发方式、处理对象、耗时特点、现有状态与历史、可用操作，再确定接入清单。优先统一用户体验与任务描述，是否整合执行引擎另行评估。

### 13.3 统一模型与状态契约

TaskSummary 建议最小字段：

- `key`：类型加业务 ID 的稳定身份；客户端缓存再按当前 Server 隔离，避免两种任务或多个 Server 撞 ID。
- `kind`、`title`、`subject`：任务类型、名称、影片/文件/批量范围引用，显示名缺失时使用安全回退。
- `state`：queued / running / waiting / blocked / cancelling / succeeded / partial / failed / cancelled；同时保留业务状态以便追溯。blocked 表示需要处理，waiting 表示可自动等待。
- `stage`、`progress`：阶段标识、进度作用范围 phase/overall、单位、completed/total；unknown 明确表示不可测，不以 0 冒充。
- `createdAt`、`startedAt`、`updatedAt`、`finishedAt`：无真实开始/结束记录则为空，不用创建时间伪装实际运行时间。
- `resultSummary`、`issueSummary`：结构化统计及问题，计数互斥关系由业务定义；AI 整理无匹配是成功分析的结果，不自动计为失败。
- `capabilities`：当前状态和权限允许的 cancel/retry/undo 等能力，含不可用原因；后端仍需独立校验。
- `attempt` / `retryOf`：记录重试关系与范围；既有同 ID 重试保留原语义，新增尝试记录后才能展示多次执行历史。

TaskDetail 由共用概览、阶段快照/关键事件和按 kind 区分的业务详情组成。字幕输出按资产查询；整理明细分页查询。不要让中心解析临时检查点文件、任意 metadata 或模型原文日志。

首版统一查询状态，不改变任务自身生命周期：业务没有 cancelling 时不能仅因用户点击取消就假报已取消；需等执行方确认。部分完成须有可验证的成果；进度完成不等于成果已经发布可用。

### 13.4 技术接入方式

建议增加独立任务查询服务（拟名 `TaskCenterService`），在后端以类型适配器读取两类业务记录，输出统一摘要、详情、筛选与汇总。业务表与现有 worker 仍是事实来源，中心不保存一套可与业务冲突的可写状态。

拟新增只读接口，路径在契约阶段最终确定：

| 接口草案 | 用途 |
| --- | --- |
| GET /api/task-center/summary | 当前 Server 的执行中、排队、等待、需处理数量，不受列表分页影响 |
| GET /api/task-center/tasks?kind=&state=&cursor=&limit= | 两种持久来源统一过滤、排序与分页；游标以创建时间及稳定 key 排序，更新进度不打乱历史翻页 |
| GET /api/task-center/tasks/{taskKey} | 共用详情及类型化业务信息；记录不存在/过期与网络错误分开 |

统一服务的 action 方法按 kind 转调现有取消/重试/撤销接口；第一版不新增能绕过原业务权限的通用写接口。发起任务仍使用原业务接口，提交请求沿用幂等 requestId。

补齐缺失字段时，在对应业务存储中保存阶段时间、尝试和可公开参数；需要迁移才新增 migration。不迁移既有成功结果、不重新运行历史任务、不倒推不存在的日志。旧记录显示可得字段和「历史记录未提供」。

前端：`src/services/contracts/task-center-service.ts`、Web/Mock 适配、`use-task-center.ts` 共享观察；`TaskCenterView` / `TaskDetailView` 仅装配；领域组件包含 SidebarTaskEntry、TaskList、TaskProgress、TaskStageList、SubtitleTaskDetail、OrganizationTaskDetail。名称均为拟定。

观察策略：首版由 AppShell 统一观察当前 Server；有活动任务时每约 2 秒更新摘要和可见详情，空闲时降低频率，页面不可见时退避，重新可见/重连后完整对账。请求取消与 Server 身份校验防止旧响应写入新连接。原业务弹窗订阅同一状态，避免中心与弹窗各自轮询。SSE 可在既有 `task.updated` 增加持久来源投影后替换轮询，不作为首版依赖；事件丢失仍需查询对账。

历史首版只展示现有业务仍保留的真实记录，不额外承诺永久保存，不增加统一删除入口。任务记录、临时检查点与成品有独立生命周期；重试仅在检查点/配置/源文件仍符合业务条件时可用，否则提供重新发起入口。删除过的 AI 整理记录不被中心重新复活。
