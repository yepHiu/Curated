# Desktop / Server 拆分、连接管理与 SSDP：需求及实施计划

状态：已开始实施，核心连接链路可运行；三包安装、旧版迁移与正式发布验收尚未完成。日期：2026-09-25。第 1–9 节保留需求讨论及实施前调查，第 10 节为分阶段目标，第 11 节记录实际实现、验证和剩余工作；判断当前状态以第 11 节为准。

## 1. 需求与当前事实

用户希望桌面端能够独立连接其他机器上的 Curated 服务端：首次未连接时填写地址和端口，之后能够更换服务器，并增加 SSDP 自动发现。以下为开始实施前的调查快照。

实施前代码核对（不是当前实现）：

- `electron/main.ts` 先等待 `startBackend()`，成功后才创建主窗口；启动失败会退出，因此目前没有独立于后端的连接入口。
- `electron/backend-process.ts` 支持 `CURATED_ELECTRON_BACKEND_URL` / `CURATED_BACKEND_URL`，生产默认 `http://127.0.0.1:8081`。健康探测失败后仍会启动本机 Go 进程，这条流程不适合直接承担远程连接模式。
- 生产桌面窗口加载后端托管的 Web UI，业务 API 默认同源；`src/api/http-client.ts` 的显式地址来自构建环境，尚不是运行时连接管理。
- Electron preload 当前暴露本机目录选择。服务端位于另一台机器时，本机目录路径不等于服务端可访问的目录。
- 当前存在 LAN 开关和 PIN 会话体系；SSDP 与用户可操作的服务器切换尚未发现实现。

## 2. 已明确的产品模型

用户已明确：Desktop 不再内置本机 Server；提供 Desktop + Server 完整包、仅 Server 包、仅 Desktop 包三种安装包。常规 Server 安装体验通过完整包默认安装 Desktop，专用纯 Server 包只安装服务端。桌面端负责连接与交互，服务端持有数据库、媒体目录、扫描与转码任务。本机与远程仅是连接目标不同：

| 模式 | 桌面端行为 | 服务端生命周期 |
|---|---|---|
| 连接本机 Server | 连接已经独立安装和运行的本机服务 | Server 独立运行，不随 Desktop 退出而停止 |
| 连接远程 Server | 手动地址或发现列表选择 | Server 独立运行；连接失败不启动本机后端 |

Desktop 作为独立客户端发行，不携带 Go 服务端、服务端数据库或 FFmpeg 转码运行时。Server 发行物包含后端与 Web UI；完整包组合 Server 和 Desktop 两个独立组件，默认同时安装。服务端独立部署衔接既有容器部署规划，NAS/无桌面容器使用纯 Server 形态，不要求安装 Desktop。

首次启动展示本地连接页，包含已知本机 Server（如有）、局域网发现结果及手动连接。没有本机 Server 时仍正常进入连接页，不自动安装或启动服务端。手动入口接受主机/IP 与端口，并支持完整 HTTP/HTTPS URL；生产默认端口可提示 8081，不硬编码为唯一端口。当前实现明确拒绝反向代理子路径，不静默丢弃路径；子路径支持另列后续。

选择服务器后依次检查可达性、Curated 身份、版本/能力及认证要求；需要 PIN 时进入已有解锁流程。成功后记住连接。发现一台服务器也不自动选择或自动信任。

## 3. 连接管理与异常流程

- 设置内提供“当前服务器”和“更换服务器”；桌面托盘或应用菜单也提供入口，保证远程页面无法加载时仍可操作。
- 下次启动自动尝试上次连接；连接中即可取消或更换，超时/断线展示重试与更换入口，不出现空白页或直接退出。
- 不自动回退到本机空资料库，以免用户误以为远程数据丢失。
- 第一版可保存最近连接，一次仅连接一个服务器；不做资料库聚合与多服务器同时工作。
- 切换时停止旧页面请求、SSE、播放器与上传等客户端活动，隔离新旧服务器缓存及会话。前台上传/播放需明确提示影响；已经提交的服务端扫描等后台任务继续执行。
- 连接配置保存于桌面端用户数据目录，不能放在远程 `library-config.cfg`，否则未连接时无法读取。认证会话与普通地址配置分开存放，并按服务器隔离；端口不同也可能共享浏览器 Cookie 主机范围，不能仅依赖 origin 默认隔离。
- 服务端稳定 ID 用于去重和识别地址变化，但 SSDP 声明的 ID 不是认证凭据；地址变化后重新验证，不向未经确认的候选端点转发旧凭据。

## 4. SSDP 的职责与边界

SSDP 仅用于发现可连接的 Curated 服务，业务流量继续使用 HTTP/HTTPS。建议由 Go 服务端发布和响应发现，由 Electron 主进程发送查询并收集结果；普通浏览器不直接执行 UDP 发现。

协议草案：IPv4 SSDP 使用 `239.255.255.250:1900/UDP`，定义 Curated 专属服务类型与稳定 UUID；客户端发送 M-SEARCH，服务端返回 USN、LOCATION、缓存有效期等标准信息，通过 HTTP 描述取得名称、版本与连接端点。服务端可发送 alive/byebye；UI 不应依赖 byebye 一定送达，应按有效期过期并支持刷新。

- 按稳定 ID 合并多网卡结果，但保留可达地址候选；公告地址必须是客户端可访问地址，不能是 `127.0.0.1`、`0.0.0.0` 或容器内部地址。
- 局域网发现随服务端对外访问开启，建议另提供发现开关。只开放 loopback 的实例不向局域网公告不可达服务。
- 发现信息限名称、ID、版本和连接信息，不携带媒体列表、目录、PIN 或会话。
- 将发现响应视为未验证输入，限制描述请求的协议、重定向、响应大小和超时；点击连接后再执行身份/能力验证。
- SSDP 通常只覆盖同一局域网多播范围；跨 VLAN、访客 Wi-Fi、VPN 与 Docker bridge 不保证可发现。NAS/容器部署需明确多播网络与 HTTP 公告地址；手动地址始终可用。
- 发现失败不等于服务器离线，不能阻止已保存或手工地址连接。SSDP 不承担公网穿透，也不意味着增加 DLNA 媒体服务。

## 5. 当前选定的架构方向

用户明确倾向“Desktop 连接后加载服务器提供的 Web 界面”，采用“本地连接页 + 服务端 Web UI”。该方向已经实现并完成本机真实链路验证，详见第 11 节。业务 API、图片、视频、SSE 继续同源，可以减少客户端与服务端前端版本错配。

本地连接页及更换入口必须由安装包提供，不能依赖任何服务端响应。将其拥有的连接管理 IPC 与远程内容可用的桥接能力隔离，校验调用来源与导航/重定向。远程网页不应获得任意本机文件或进程能力；不能为跨域关闭 Electron 安全机制。服务端版本与桌面桥接版本仍需能力协商。

Desktop 随包提供连接、发现、连接失败与更换服务器等本地界面；资料库业务界面由当前 Server 提供。不随 Desktop 另行打包完整业务前端作为本期方向。

Desktop 在加载页面失败、网络中断或服务器重启时保留本地连接管理入口；短暂断线先显示连接状态，避免立即销毁尚有未提交输入的页面。提供重试和返回连接页，不承诺离线浏览远端资料库。实际故障展示方式仍待交互设计。

## 6. 必须定义的操作归属

| 操作 | 远程模式下的归属 |
|---|---|
| 添加媒体库、备份输出目录 | 服务端文件系统；第一版可输入服务端路径，后续按授权范围提供服务器目录浏览 |
| 上传本机文件 | 客户端选择文件，经 HTTP 上传 |
| 扫描、刮削、转码、整理 | 服务端执行 |
| 打开文件所在目录 | 明确服务器目录与本机目录区别；远程模式不可把服务器路径交给本机文件管理器 |
| 外部播放器 | 使用客户端可访问的媒体 URL，并明确认证方式，不传远端磁盘路径 |
| 更新、开机启动、退出 | 分开定义桌面端与服务端行为，不能沿用同机假设 |

现有 PIN 可作为第一版认证起点，但发现成功不代表已授权。若目标包含公网，需要另外确定 HTTPS、访问控制及部署要求；不将已有 LAN/PIN 直接描述为完整公网产品能力。

## 7. 建议切片与验收

执行顺序以第 10 节为准：先明确组件和合约，完成 Server 独立运行与 Desktop 手动连接，补齐远程操作边界，再加入 SSDP，最后完成三种安装包、升级迁移与发布验收。组件划分先定，三包交付在运行链路验证后完成。

关键验收：Desktop 包不含服务端运行时；无本机后端也能显示连接页；远端不可达不会启动本机后端；切换 A/B 不串数据和认证；重启记住上次连接；多台服务器可选择；禁用多播仍能手动连接；PIN 锁定不影响更换入口；旧服务端缺少发现能力仍有明确的手动连接兼容策略；退出客户端不停止本机或远端 Server 任务；添加库目录始终指向正确机器；组合安装可正常连接本机 Server，且不覆盖已有 Desktop 的连接偏好。

## 9. 补充讨论：产品命名与发行边界

用户提出：拆分之后需要考虑 Web 端与桌面端的产品关系，服务端可能命名为 servers 或 core，桌面端命名为 desktop。当前已明确界面交付及安装组合方向；下列对外名称仍为建议。

### 9.1 同一品牌下的两个发行产品与一个浏览器入口

| 名称建议 | 定位 | 交付内容 |
|---|---|---|
| Curated Server | 资料库服务端，部署在 NAS、服务器或本机 | Go 服务、数据库与媒体管理、API、SSDP 发布，以及配套 Web UI |
| Curated Desktop | 安装在用户电脑上的桌面客户端 | 本地连接管理、SSDP 搜索、桌面集成，连接后加载 Server 的资料库界面 |
| Curated Web | 浏览器访问入口 | 随 Server 提供的 Web 界面，初期无需第三套独立安装产品 |

推荐对外使用单数 Server：表示可安装的服务端产品；Servers 更适合作为界面中的服务器列表名称。Core 更适合未来确有必要抽取的内部业务核心模块，对普通用户而言不如 Server 直接。无需为命名提前重排源码目录或新增空的 Core 层。

Web 前端与 Server 不是同一个技术组件，但作为同一发行物交付。Desktop 和浏览器加载同一份服务端业务界面；该界面通过能力检测适配桌面功能，普通浏览器正常工作，无需维护两套业务页面。本地连接页可以复用设计组件，但加载与运行不依赖 Server。

### 9.2 产品分离后的职责

- Server 持有资料库配置、数据库、扫描与转码任务、访问策略；Desktop 持有连接记录和本机偏好。
- Server 独立运行，本机和远程遵循相同生命周期边界，Desktop 不负责拉起或结束 Server 进程。Server 的启动、停止和开机运行由自身的安装及运行机制负责，具体机制待设计。
- Desktop 是连接已有 Server 的客户端，不内置 Server。“本机一体使用”由完整包默认同时安装 Server 和 Desktop 提供，安装组合不改变独立运行关系。
- 设置区分“此设备”和“服务器”；更新入口分别显示桌面版本和服务器版本，更新 Desktop 不隐式更新远端 Server。
- Server 与 Desktop 可独立发布；初期可以同步版本号降低维护成本，但连接兼容性由明确的 API/桥接协议与能力范围决定，不能永久要求产品版本号完全一致。

### 9.3 对界面交付方式的影响

用户倾向已明确，采用第 5 节的服务端托管 UI 方向：Desktop 独立发布连接页、Electron 运行时和桌面能力，资料库业务 UI 随 Server 更新。更新 Server 后，浏览器和 Desktop 在重新加载界面时获得配套版本；涉及长期打开页面与旧资源缓存时需给出刷新提示，不强制丢弃未保存输入。

业务功能更新通常只需更新 Server；连接管理、SSDP、本机集成或 Electron 运行时的变化才需要更新 Desktop。仍需维护 Server Web UI 与 Desktop 桥接协议的兼容：可选桌面能力缺失时隐藏或降级相关功能；确有必需能力不兼容时明确提示所需 Desktop 版本，保留连接管理入口。版本不必完全一致。

产品名称仍建议为 Curated Server / Curated Desktop / Curated Web；最终命名及远程网络覆盖范围仍待确认。界面交付方式与安装组合方向不再列为未决选项。

### 9.4 三种安装包与默认安装体验

用户已明确以下三种可分别下载的安装包，完整包安装 Server 时默认安装 Desktop：

| 安装包 | 组件内容 | 默认安装行为 | 典型用途 |
|---|---|---|---|
| 完整包（Desktop + Server） | Server、Web UI、Desktop | 同时安装 Server 与 Desktop | 单机用户、本机管理资料库 |
| 纯 Server 包 | Server、Web UI 及服务端运行依赖 | 仅安装 Server，不附带或自动下载 Desktop | 专用服务器、浏览器访问、NAS 部署 |
| 纯 Desktop 包 | Desktop 与本地连接管理界面 | 仅安装 Desktop，不附带或自动安装 Server | 连接本机已部署服务或远程服务器 |

建议下载页将完整包作为有桌面环境的普通用户默认推荐，明确标注三个包的组件，避免把“Server 默认安装 Desktop”错误应用于纯 Server 包。完整包若提供组件选择，“安装 Desktop”默认勾选；是否允许取消可在安装器交互阶段确定，不影响三个独立包的要求。

三种包是两个组件的不同组合，不形成三套业务实现。完整包复用与独立包一致的 Server / Desktop 构建产物，并记录各组件版本。容器/NAS 发行物保留纯 Server 形态；具体平台支持及安装文件命名仍待发布设计，不表示每个平台均需生成三种图形安装器。

建议组合安装在新装 Desktop 且无连接记录时提供本机实际服务地址，作为明确的连接候选；启动后仍执行身份、可达性及认证检查。此本机入口不依赖 SSDP 多播，服务端只监听 loopback 时也应可用。若已有 Desktop，保留上次服务器与用户偏好，不强制改连本机。

两个组件分别管理更新、安装检测和卸载。完整包安装器复用受支持的 Desktop 发行物；检测到已安装 Desktop 时避免无条件覆盖或降级。卸载 Desktop 不删除 Server 和资料库；卸载 Server 后 Desktop 仍可连接其他服务器。Server 数据保留与删除按独立、明确的卸载策略处理。

安装验收增加：完整包在新机器默认装好两个组件；纯 Server 包不安装 Desktop；纯 Desktop 包不安装 Server；先装任一独立组件后再运行完整包不会创建重复实例、降级已有组件或覆盖连接记录；组合安装后退出 Desktop 不停止 Server。

旧版一体包迁移需要单独设计：保留数据库、媒体路径、配置、会话及现有连接体验，调整快捷方式与进程管理，不在本轮直接实施迁移或重命名。

以上为需求讨论记录；用户随后要求创建 worktree 并开始实施，执行结果见第 11 节。

## 10. 实施计划（已启动，验收目标保留）

### 10.1 本轮实施目标与范围

已确定的交付目标：

1. Desktop 不携带、不启动、不停止 Server；同机与远程使用同一连接模型。
2. Desktop 自带首次连接、手动地址、服务器发现、切换及失败恢复界面，连接后加载 Server Web UI。
3. Server 独立运行，提供 Web、API 和 SSDP 公告；Desktop 搜索并由用户选择连接。
4. 产出 Full（Server + Desktop，默认同时安装）、Server-only、Desktop-only 三种可独立下载的安装包。
5. 两组件独立设置、更新与卸载，保留旧一体包用户的数据与正常使用路径。

建议首期发布范围：沿用现有 Windows x64 安装链，覆盖同机和同一局域网。协议接受 HTTP/HTTPS 与自定义端口；公网部署、自动 HTTPS、穿透、跨网段自动发现、完整 NAS/FPK 发布和新增 macOS/Linux Desktop 安装链不纳入本轮交付。这是用于控制实施范围的建议，不是用户已经确认的限制。代码保持跨平台边界，不把 Windows 安装细节放入业务层。

继续使用当前仓库、Vue 业务前端及 Go 分层，不因产品命名立即拆仓库或大规模重排目录。完整包不会产生第三套业务实现。

### 10.2 代码核对发现与对应改动

| 现状 | 实施动作 |
|---|---|
| `electron/main.ts` 必须先启动/探测后端才能建窗口，失败退出 | 改成先开本地连接页，再建立连接；退出仅清理 Desktop 自有资源 |
| `electron/backend-process.ts` 探测失败会 spawn Go 进程 | 从生产 Desktop 移除这条路径；健康探测抽为纯连接能力，开发编排另放脚本 |
| `pnpm dev:electron` / `build:electron` 包含后端构建 | 拆开客户端开发与全栈开发入口，客户端构建不依赖 Go 或 FFmpeg |
| `backend/cmd/curated` 已有 `http` / `tray` 模式 | 复用并整理为独立 Server 启动入口，避免重写服务运行层 |
| release 数据目录默认在当前用户目录 | 首期保持运行账户和数据根，避免误读空库；服务账户转换不混入默认迁移 |
| `/api/health` 当前包含数据库路径 | 不用于 SSDP 描述；新建最小公开身份端点，另评估并迁移 health 中不必要的路径暴露 |
| preload 仅提供本机目录选择，未区分本机/远端库路径 | 拆分本地连接管理桥与业务页桥，按操作归属提供能力 |
| `assemble_release()` 将 Go、Web、FFmpeg 放入 Electron 的 `resources/app` | 拆成 Server 和 Desktop 两个组件目录，再组合为三种发行产物 |
| `Curated.iss.tpl` 只有一个安装身份和整包复制逻辑 | 建立独立组件身份与安装目录，完整包协调两者安装 |
| `appupdate.resolveInstallerAsset()` 优先选择含 setup/installer 的 EXE | 更新必须按组件、平台、架构精确选择，禁止继续猜测首个安装程序 |

### 10.3 阶段 0：冻结组件边界和连接合约

**产出：合约、配置归属、连接状态及安装身份设计。** 该阶段先完成评审性设计与最小合约切片，不修改资料库主流程。

- 约定组件标识 `server` / `desktop`，包类型 `full` / `server` / `desktop`；展示名称暂按 Curated Server / Curated Desktop。
- 拟新增 `GET /api/server-info`：返回产品标识、稳定 `serverId`、展示名称、Server 版本、连接协议版本和必要能力摘要；未解锁也可读，但不含数据库路径、资料库内容、PIN 或令牌。具体 DTO 和错误码先定义在现有 contracts 层。
- 稳定 ID 存于 Server 数据根，不能每次重启生成。备份恢复/克隆到另一独立实例时需有重新生成身份的规则，避免两台机器被发现列表错误合并；ID 用于识别，不代替认证。
- Desktop 本地配置保存地址、上次连接与非敏感偏好，认证 Cookie 存在每个连接档案独立的 Electron session partition；同主机不同端口也隔离，禁止把凭据放入 URL 或普通配置 JSON。
- 地址首期接受 HTTP/HTTPS、主机/IP、端口，默认根路径部署；不支持的反向代理子路径明确提示，不能静默截断。规范化、DNS/连接超时、证书错误与重定向策略统一处理，不忽略 TLS 错误。
- 定义状态：未配置 → 探测中 → 加载界面 → 已连接；需要认证由 Server Web 锁屏处理；失败/不兼容/断线均保留本地连接入口。
- 旧 Server 缺少 server-info 时，仅在既有 health 明确识别为 Curated 后提供受限手动连接；标注旧版、禁用不支持的发现/桥接能力，不把任意 HTTP 页面当作 Curated。

**验收：** 合约不依赖具体地址或产品版本号相等；能区分不可达、非 Curated、旧版、证书错误与能力不兼容。

### 10.4 阶段 1：Server 独立运行

**主要落点：** `backend/cmd/curated/`、`backend/internal/desktop/`、`backend/internal/config/`、版本身份及服务端资源定位。

1. Server 自身提供启动、退出和日志入口，HTTP、静态 Web、数据库和转码资源不依赖 Electron 的目录或环境变量。
2. 建议首期 Windows 复用已有 Go 托盘及当前用户登录启动机制，托盘明确显示“Curated Server”；关闭 Desktop 不影响 Server。纯 HTTP 模式继续可供无桌面运行环境管理。
3. “登录后自动运行”与“用户未登录也运行的系统服务”明确区分。首期不默认改成 LocalSystem 服务，避免改变 SQLite 目录、网络盘凭据及媒体访问权限；若需要无人登录常驻，应先补充服务账户、数据目录和权限设计，再调整阶段工作量。
4. Desktop 的开机启动属于本机客户端偏好；Server 原有 `launchAtLogin` 继续归 Server，拆清 UI 标签和持久化位置。
5. 保留默认 loopback 与显式 LAN 开关。独立包安装不自动开放局域网；Server Web 网络设置仍可通过浏览器配置。自定义监听端口要用于后续安装连接提示。
6. 保留单实例、数据锁、正常退出和后台任务恢复机制；端口冲突时给出错误，不启动第二份同库实例。

**验收：** 不安装 Electron 也能运行 Server，并通过浏览器完成浏览、播放与任务操作；停止/启动 Desktop 不改变 Server PID 或任务状态；旧数据根读取正常。

### 10.5 阶段 2：Desktop 本地连接管理与手动连接

**主要落点：** `electron/main.ts`、`desktop-shell.ts`、`preload.cjs`；建议新增连接配置/探测/状态模块与独立本地连接页构建入口，复用现有 UI 组件与样式令牌。

1. 启动立即显示随包本地页，不等待 Go 或网络；手动地址/端口、最近服务器、重试、更换入口可离线使用。
2. 连接成功后加载目标 Server Web UI，业务 API、海报、媒体、SSE 继续同源；不为这项功能全面改写 `http-client.ts` 为跨域代理。
3. 移除生产 Desktop 的后端 spawn/kill 与 Go/FFmpeg 构建依赖。全栈开发可由显式开发脚本启动多个独立进程，不能回流进客户端生产启动逻辑。
4. 记住上次连接；首次成功后再持久化有效目标。保留可取消的连接与有限重试，失败不退出、不创建本机空库。
5. 切换服务器前提示正在播放/上传或有未保存输入的影响；切换后销毁旧业务页面及请求上下文，隔离 Cookie、缓存和 localStorage。已提交的服务端任务继续执行。
6. 本地菜单/托盘的更换入口始终可用，不能只放在远端设置页。短暂断线保留页面与本地恢复入口，重试不创建重复窗口或事件监听。
7. 对本地页与远程业务页使用不同的权限边界，校验 IPC sender、顶层 frame 和当前授权来源；保持 sandbox、contextIsolation、禁用 Node integration。跨来源导航不自动继承桌面桥接权限。

**验收：** 在没有 Go、Server 或开发工具的机器上 Desktop 能启动；手动连接 A/B、重启记忆、同主机不同端口隔离、锁屏时更换服务器、断网恢复都通过真实 Electron 验证。

### 10.6 阶段 3：远程模式的设置与操作归属

**主要落点：** 设置页面、`src/lib/pick-directory.ts`、服务契约和运行能力摘要、更新入口。

- 资料库与备份路径第一版输入 Server 可访问的绝对路径，由 Server 校验；远程模式不调用本机目录选择器来配置服务端目录。授权的服务器目录浏览留作后续增强。
- 上传仍通过本机文件选择和 HTTP 上传。梳理播放器、媒体链接、SSE、Agent 流、导出与下载是否存在硬编码 localhost 或本机路径假设。
- “打开文件位置”与外部播放器按能力隐藏或使用明确支持的方式；本轮若无安全可用的媒体 URL 认证方案，则不承诺远程外部播放器，内置 Web 播放必须可用。
- 设置/关于页区分 Server 版本与 Desktop 版本、“服务器设置”与“此设备设置”。普通浏览器不显示仅 Desktop 可用的控制。
- 桌面桥接协议做版本/能力探测；可选能力缺失可降级，不能让业务页面整体打不开。

**验收：** 两台机器有不同磁盘路径时，添加库、备份和上传不会操作错机器；媒体/HLS、SSE 与认证不残留本机地址假设；浏览器体验保持正常。

### 10.7 阶段 4：SSDP 发现闭环

**主要落点：** 建议新增 `backend/internal/discovery/` 与 `electron/discovery.ts`；Server 配置、设置网络页及本地连接页。

1. 定义 Curated 服务类型、USN、LOCATION 与设备描述格式，使用标准 SSDP 报文；拟由 `GET /discovery/description.xml` 提供最小设备描述，实际命名在合约切片定稿。
2. Go 在可供 LAN 访问且发现开关开启时监听 M-SEARCH、发送 alive/byebye；HTTP 服务就绪后公告，退出时关闭 socket。发现开关状态与 LAN 访问关联，但关闭发现不关闭手动 HTTP 连接。
3. Electron 主进程在进入发现页或点击刷新时执行有界扫描；结果展示名称、地址和版本。第一次发现不自动连接，不携带旧 Cookie 探测候选服务器。
4. 按 ID 合并多网卡响应并保留候选地址，处理超时、缓存过期、重复报文、地址变化与名称相同的不同服务器。公告不能使用 loopback、通配监听地址或容器内部地址。
5. 首期实现 IPv4 局域网发现；普通浏览器不调用 UDP。多播被拦截、Docker bridge 或跨网段失败时显示未发现并保留手动连接，不误报 HTTP 服务离线。
6. 描述请求限制协议、大小、超时及重定向；发现信息不执行为代码。配合 LAN 设置说明实际 HTTP 端口和 UDP 1900 的防火墙需求，不全局关闭防火墙。

**验收：** 两台真实机器可发现并连接；多网卡不重复成多个服务器；两台同名 Server 可区分；关闭发现或阻断多播后手动连接仍正常；服务重启与地址变化不会串凭据。单元测试采用假时钟/报文夹具，CI 不依赖实际组播环境。

### 10.8 阶段 5：三种安装包与组件更新

**主要落点：** `scripts/release/release_cli.py`、`release_lib/build_steps.py`、`models.py`、Inno Setup 模板、版本/manifest、`backend/internal/appupdate/` 和 Desktop 本地更新入口。

**构建与安装：**

- CLI 拟增加 `--variant full|server|desktop`；一次发布分配一次版本，分别构建两个组件，再组合三包，不能打三次包递增三次 patch。初期同批版本，manifest 保留组件版本，为将来独立发布留边界。
- Server 组件包含 Go、Web UI、FFmpeg 与必需资源；Desktop 组件包含 Electron、本地连接页与桥接资源。建立包内容清单和自动断言，防止纯 Desktop 带进 Go/FFmpeg、纯 Server 带进 Electron。
- 建议产物名称为 `Curated-Full-Setup-<version>-windows-x64.exe`、`Curated-Server-Setup-<version>-windows-x64.exe`、`Curated-Desktop-Setup-<version>-windows-x64.exe`；最终名称需和旧更新器迁移一起确定。
- 两组件各自固定安装身份、安装目录及卸载入口；推荐完整包作为离线组合安装器调用同版本独立安装器，避免三个不同安装身份重复写同一组文件。验证提权后仍保留原用户上下文，用户数据不能落入另一管理员账户。
- 完整包默认安装两者，检查已有版本，不无条件降级；部分安装失败明确报告已装/失败组件，重试幂等。不得为回滚本次失败删除用户原有组件。
- Server 安装启动就绪后向新装 Desktop 提供实际本机地址，不覆盖已有连接；桌面快捷方式与 Server 管理入口区分。已出产的 installer/portable 包保留，新增产物不以清理旧包为前提。

**更新：**

- manifest 为每个资产明确 `component/variant/platform/arch/version/url/sha256`。Server 更新只取 server 包；Desktop 在本机连接管理界面提供自身更新/下载入口，不依赖远程 Server 可用。
- 远端 Web 页面中的“更新服务器”仅操作 Server；客户端更新通过可信本地流程执行，不接受远程网页传入任意安装 URL/路径。组件更新不自动触发另一组件更新。
- 保留现有校验和验证与下载状态；缺少匹配资产时明确不支持，禁止回退到第一个 EXE。第一版 Desktop 可先采用本地入口打开精确匹配的官方下载，不要求立即实现静默安装。
- **旧更新器为发布阻断项：** 老版本不知道包类型且会选择首个 setup EXE。不能仅升级新版解析器就把三包放入所有旧客户端可见的同一 Release。应先验证旧客户端实际可见的 feed，再选择“旧 feed 保留唯一兼容完整包，新组件 feed 承载三包”或等效隔离方案；桥接版本可引入新 feed，但不能假设所有旧用户都会先安装桥接版本。未证明旧客户端不会选错包之前不公开切换发布结构。

**验收：** 三包分别在干净 Windows 环境安装；混合已有组件/高低版本时无重复、覆盖或降级；Server 更新不下载 Desktop 包；Desktop 更新不在远端执行；安装失败可恢复；完整包与独立包使用同一组件身份和产物。

### 10.9 阶段 6：旧一体包迁移与发布验证

1. 检测旧安装身份及 `resources/app` 布局、运行进程、自动启动项、数据根和自定义配置。迁移前展示目标组件与实际资料库位置，停止旧托管链并等待数据锁释放。
2. 首选保留现有数据目录，备份配置/数据库后迁移程序布局与快捷方式；禁止将 Server 移到另一运行账户后悄悄创建空库。自定义 `CURATED_DATA_DIR`、媒体路径及旧 Cookie/localStorage 的兼容边界均需测试。
3. Desktop 新连接档案优先指向原本机端口。已有认证会话可安全迁移则保留，否则明确要求重新解锁，不能把旧令牌无条件复制到新发现地址。
4. 撤销旧 Electron 托管和旧启动路径，避免双 Server、双自启；拆分旧卸载登记时不得触发删除新组件或资料库。
5. 回滚区分程序和数据：保留旧安装包/配置备份；如数据库结构已升级，禁止直接用旧程序打开新库，恢复按现有离线备份流程执行。
6. 完成 release notes、三包下载说明、版本兼容说明和首次迁移操作手册。先在测试数据及内测机器验证，不将主资料库作为首次迁移试验。

**验收矩阵：**

| 场景 | 通过标准 |
|---|---|
| 干净机器装 Desktop | 本地连接页可用，没有 Server 进程或服务端依赖 |
| 干净机器装 Server | 浏览器可用，没有 Electron，Server 自身可管理 |
| 干净机器装完整包 | 默认两个组件，本地连接顺畅，退出 Desktop 后任务继续 |
| Desktop → 远程 Server | 认证、浏览、播放、上传、任务、切换及断线恢复正常 |
| 浏览器 → 同一 Server | 既有业务能力无回归，不要求 Desktop |
| A/B 同主机不同端口 | Cookie、缓存、偏好及异步结果不串库 |
| 发现不可用/旧 Server | 手动连接或明确兼容提示，连接页不被阻塞 |
| 单独包 → 完整包/组件升级 | 组件被复用，无重复注册、降级和连接偏好丢失 |
| 旧一体包升级 | 原库与设置可用，无双进程和双自启，认证变化有明确提示 |
| 卸载其中一组件 | 另一组件和 Server 数据不被误删 |
| 旧更新客户端看新发布 | 不会自动下载错误组件安装包 |

### 10.10 依赖顺序、检查与交付节点

执行顺序：**阶段 0 → 1 → 2 → 3 → 4 → 5 → 6**。安装身份与旧更新 feed 的设计在阶段 0 提前摸清，阶段 5 实施，不等到发包时才发现无法迁移。

| 可审阅节点 | 用户可以验证什么 | 发布状态 |
|---|---|---|
| M1：阶段 0–2 | Server 独立运行，Desktop 无后端启动依赖，可手动连接并切换 | 开发验证，不作完整远程版交付 |
| M2：阶段 3–4 | 远程目录/设置归属正确，SSDP 发现及手动兜底可用 | 功能内测 |
| M3：阶段 5–6 | 三种安装包、组件更新、旧版迁移及卸载全部通过 | 满足发布条件，实际发布另按用户指令 |

各行为切片独立提交：合约 → Server 运行 → Desktop 连接/隔离 → 远程操作边界 → SSDP → 组件构建 → 安装器 → 更新路由 → 迁移。避免一次提交全部改动；不自动 push。

验证沿用 `docs/ops/2026-04-08-agent-build-and-test.md`：开发中运行对应 Electron/Vitest/Go 包测试；阶段集成完成后执行根目录 `pnpm typecheck`、`pnpm lint`、`pnpm test`、`pnpm test:electron`、`pnpm test:e2e`，`backend/` 下 `go test ./...` 与 `go vet ./...`；发布脚本执行 `python -m unittest scripts.release.tests.test_build_steps`，有其他脚本改动时按 CI 范围补测。生产 Web API 前端和 Electron 分别构建验证；新增本地连接页纳入独立构建及包内容检查，不改变原 Web 体积统计口径来掩盖增长。

真实 Electron、Windows 安装/卸载、两机组播、媒体播放与旧版升级属于必需人工/集成验收，不能以单测通过代替。实际实施已执行下述常规检查，不运行 display-scaling 专项套件。

实施新增端点/配置/架构后同步 `.cursor/rules/project-facts.mdc`、`architecture-boundaries.mdc`、必要的 `workspace-quick-reference.mdc`、README 短入口及对应语言版本、`docs/guide.md`、`CLAUDE.md` API 列表和 `docs/reference/architecture-and-implementation.html`；新增 library-config 键时同步 `docs/reference/2026-03-21-library-organize.md`。本计划仅记录目标，不提前把这些事实文档改成“已实现”。

### 10.11 审阅时需要关注的建议

无需重新讨论已明确的三种包和服务端托管 Web UI。影响工作量的剩余选择主要是：

- 首期是否按现有 Windows x64 发布链交付，NAS/其他平台安装包另列后续计划。
- Windows Server 首期是否接受现有“当前用户托盘 + 登录启动”；若要求未登录常驻，则系统服务及账户迁移必须进入本期。
- 网络范围是否先验收同机/LAN；异地 HTTPS 地址可手动输入，但公网部署能力不在本轮自动承诺。

当前实现沿用既有 Windows x64 发行链、用户托盘运行和同机/LAN 验收范围；这不代表已经补齐其他平台安装器、无人登录系统服务或公网部署能力。

### 11.2 已交付的行为

1. Server 安装身份持久化在 `<databasePath>.server-id`，不进入数据库备份；提供不含目录/凭据的公开 `/api/server-info`。身份损坏会明确失败，不静默创建新身份。
2. Desktop 先打开随包连接页，支持 HTTP/HTTPS 根地址、自定义端口、最近连接、自动重连、取消、忘记和菜单更换；业务页加载成功后才保存。身份改变需确认，Cookie/cache/localStorage 按地址和身份隔离。客户端构建及生产包不含 Go/FFmpeg，生命周期不管理 Server。
3. 本地连接管理与远程业务桥分离；IPC 校验窗口、顶层 frame 与来源。业务窗口 sandbox/contextIsolation 开启、Node 关闭，跨来源导航受限。资料库与备份目录按 Server 路径输入，远程宿主文件管理器/原生播放请求返回 403；Desktop 原生播放器入口暂禁用。
4. Server 在 LAN 和发现开关启用后发布 IPv4 SSDP；Desktop 有界扫描并用 server-info 验证候选，按 ID 去重、按期限清理。网络设置支持 `discoveryEnabled`，重启 Server 后生效；手动连接不依赖发现。描述 XML 已提供；当前客户端直接验证 server-info，不额外解析 XML。
5. Full 使用与独立安装包相同的组件安装器和固定身份，默认安装两者；程序安装与资料库目录分离。Full 启动组件读取登记的实际安装路径，兼容已有自定义目录。Desktop 不覆盖已有连接记录，仅对首次连接提供本机 Server 地址建议。
6. Server 更新只选精确命名的 Server 包，并拒绝旧整包/Desktop 缓存；Desktop 本地页只打开匹配的官方 Desktop 下载地址。构建 manifest 标记组件、平台、架构、版本和 SHA-256。没有 Inno 编译器时返回 `scripts-only`，不会报告 EXE 已完成。
