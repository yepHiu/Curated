## 结论

MiMo 文档里的「流式调用」不能直接当成实时翻译字幕服务。

它是一次 HTTP 请求：客户端先把整段 wav/mp3 做成 Base64 放进请求体，服务端再以 SSE 逐段吐出识别文本。音频不能边录边送，响应里没有时间戳，也没有译文。语种契约只有中文、英文和中文方言。

Curated 片源以日语对白为主，播放器目前只在诊断里显示字幕轨数量，没有字幕渲染。现有 AI 客户端只发文本 chat completion，不能提交 `input_audio`。

因此这套模型至多覆盖「中/英音频、整段或短切片转写」。播放中的日语实时翻译要另选识别模型；翻译本身还要第二次文本模型调用。

## 模型实际能力

| 项 | 契约 |
|---|---|
| 模型 | 仅 `mimo-v2.5-asr` |
| 地址 | `POST https://api.xiaomimimo.com/v1/chat/completions` |
| 认证 | 请求头 `api-key` |
| 音频 | 仅 wav、mp3；整段 Base64。Data URL 的 MIME：wav 为 `audio/wav`，mp3 为 `audio/mpeg` 或 `audio/mp3` |
| 体积 | Base64 字符串上限 10 MB |
| 语种参数 | `asr_options.language`：`auto` / `zh` / `en`，默认 `auto`，只允许单一语种 |
| 宣传语种 | 中英双语、中英混说，以及粤语、吴语、闽南语、四川话 |
| `stream=true` | 文本用 SSE 增量返回（`chat.completion.chunk` 的 `choices[].delta.content`） |
| 非流式 | `choices[].message.content` 为整段纯文本 |
| 上下文 / 输出 | 8k / 2k token |
| 限流 | 100 RPM，10k TPM |
| 计费 | 按输入音频时长，精确到秒再折算小时。国内 ¥0.5/小时，海外 $0.074/小时 |
| 用量 | `usage.seconds`、`usage.prompt_tokens_details.audio_tokens` |
| 结束原因 | `stop`、`length`、`content_filter` |

官方示例即使勾了流式，也是先读完整本地文件再 Base64。没有 WebSocket、没有分块音频上传、没有预连接。响应字段里没有词级或句级时间戳，没有说话人，没有译文。

采样率、声道和单次时长上限官方未写。10 MB Base64 约等于 7.5 MB 原始音频，粗算上限：

- 16 kHz、16-bit、单声道 WAV：约 4 分钟
- 24 kHz、16-bit、单声道 WAV：约 2.7 分钟
- 64 kbps MP3：约 16 分钟
- 128 kbps MP3：约 8 分钟

输出上限 2k token。超长对白会以 `finish_reason=length` 截断，不能把整部影片一次送入。

社区实现 `mimo-asr-vllm` 称单次超过约 2 分钟后字错率明显变差，并会重采样到 24 kHz、按静音切成不超过 60 秒的片段。这不是小米 API 的承诺，只能当作切片实验的参考。

## 和「实时翻译」差在哪里

本地点播不必做成麦克风式 WebSocket。文件已经在磁盘上，可以按播放时钟提前切出后面几秒音频，在播放头到达前提前识别。MiMo 的文件进、文本出形态在这一点上能用，但只解决「整段上传后的文本更快出现」，不解决下面四件事。

```
播放时钟
    │  提前切 [t, t+W)
    ▼
FFmpeg 抽出单声道 mp3/wav
    │  Base64，须 < 10 MB
    ▼
mimo-v2.5-asr          ← 只有原文，时间只能借用切片窗口
    │
    ▼
文本模型翻译            ← ASR 接口不翻译
    │
    ▼
字幕 cue 叠加到播放器   ← 当前没有这条渲染路径
```

1. **语种。** 资料库对白主要是日语。官方语种表和 `language` 枚举都没有日语。未用日语音频实测，不能断言模型完全无输出，但不能按日语识别服务来设计。
2. **翻译是第二跳。** ASR 只回原文。译文需要另一次文本模型（平台上有 `mimo-v2.6-pro` / `mimo-v2.6-flash`，与 ASR 计费和限流都不同）。延迟、失败和费用叠在识别之后。
3. **没有时间轴。** 一句对白落在哪一秒，只能等于这次切片的起止，或者再接强制对齐。窗口太长，字幕整块出现；窗口太短，词被切断，重叠部分会按全长再计费。
4. **延迟下限是窗口长度。** 服务端要等这一小段音频到齐才开始识别。SSE 只缩短「文本逐字出来」的时间，缩短不了「等音频 + 上传 + 识别 + 翻译」。体感实时通常要求落后人声 2–3 秒以内，所以窗口本身就要落在这个量级，并靠预取把等待藏到播放头前面。

暂停、拖动、倍速、换片、换分部都会使在途请求作废。迟到结果不能写进新的时间轴。

成人对白还有 `content_filter` 风险。接口会整段拦截，但是否拦截这类语音没有样本，不能事先当成可用或不可用。

## Curated 现状

- 播放描述符已有 `audioTracks` / `subtitleTracks`，`PlayerPage` 只在诊断里显示数量，没有字幕轨选择，也没有 cue 叠加。
- Web 播放走直连或 HLS；Windows / macOS 原生播放走 mpv。原生窗口的音轨、字幕仍是后续项。截图明确不包含字幕。
- Server 已有 FFmpeg，能按时间切音频，但没有 ASR 任务或字幕产物。
- `backend/internal/llm` 的消息是文本。MiMo 的 Base URL 虽是 OpenAI 兼容形态，现有客户端不能带 `input_audio` 和 `asr_options`。
- 现有 `aiProvider` 服务于 Agent 文本。语音识别的密钥、模型、按秒计费和内容审核不应复用这套配置。
- 音频离开本机才会到达小米云端。这和本地资料库的默认边界不同，必须由用户显式打开，密钥只留在 Server。

## 若继续做，服务要满足的需求

这些是产品需求，不是本模型已经具备的能力。

**识别与翻译**

- 源语言至少包含日语；目标语言为简体中文。中/英仅作为附加源语言。
- 同一时间轴上同时保留原文和译文，用户可只看译文、只看原文或双语。
- 每条 cue 有起止时间。误差目标需要单独定，建议先以「一句对白落在所说的那几秒内」为验收，而不是词级卡拉 OK。
- 背景音乐、喘息和非语言声音应可跳过或标成无对白，避免把噪声译成句子。
- 识别失败、审核拦截、超时和空结果不中断播放，字幕区显示可理解的失败，并允许重试这一段。

**跟随时钟**

- 以当前 `movieId` + `fileId` 和媒体时间为准，不跟墙钟。
- 播放前预取播放头之后一个短窗口；暂停停止新请求；seek 丢弃旧窗口结果。
- 倍速变化后，预取范围按媒体时间重算。
- 同一文件再次播放优先用已保存 cue，避免重复计费。

**边界与费用**

- 单次音频遵守供应商体积、时长和输出上限；超限由切片解决，不把截断文本当成完整一句。
- 切片重叠只为避免切词，重叠策略要可计算重复计费。
- 密钥、原文、译文和用量只在 Server 持久化。渲染进程不接收密钥，不接收完整音频。
- 远程客户端默认不能把 Server 上的影片音频转发给第三方，除非以后单独定义这项权限。
- 用量至少能按次看到音频秒数和失败原因，便于对账 ¥0.5/小时。

**播放器**

- Web 与原生窗口用同一份 cue，而不是各做一套识别。
- 字幕层不挡住圆形控件的命中区，窄窗口可隐藏或收成一行。
- 切换 Web / 原生播放时，已生成的 cue 仍然可用。

## 采用该模型前必须先测的样本

未做这些试验，不应进入方案或 PRD。

1. 一段清晰日语对白、一段中英对白，各 10 秒和 60 秒，看 `language=auto` 的原文是否可用。
2. 一段明确成人对白，看是否返回 `content_filter` 或空文本。
3. 3 秒、8 秒单声道 MP3 的端到端时间：上传完成、首个 SSE 字、全文结束。确认能否压进播放预取。
4. 同一句切在两个重叠窗口里，是否重复计 `usage.seconds`，译文是否互相打架。
5. 16 kHz 与 24 kHz、单声道与立体声，确认哪种输入被接受以及质量差异。官方未写采样率。

日语样本不可用时，换识别引擎；翻译模型可以之后再选。中/英样本可用、日语不可用，则该模型只适合资料库里的中英片段，不能作为默认实时字幕。

## 日语识别可选方案（2026-10-15）

Curated 要的是本地点播字幕：指定日语、句级时间戳、播放头前预取，音频默认不出本机。按这个条件，本机 Kotoba-Whisper 优先；要托管流式接口时用通义 Fun-ASR-Realtime。翻译仍是识别之后的另一次文本调用。

| 方案 | 日语 | 时间戳 | 调用形态 | 和本需求的关系 |
|---|---|---|---|---|
| Kotoba-Whisper v2.0 / v2.2 | 专为日语，教师模型是 Whisper large-v3，训练语料为 ReazonSpeech 电视音频 | 分段时间戳；v2.2 管道另含标点和说话人分离 | 本机整段或按 15–30 秒切片 | 首选。音频留在本机，无内容审核拦截 |
| Whisper large-v3（faster-whisper / whisper.cpp） | 多语种，日语可用 | 分段时间戳 | 同上 | 对照基线。Kotoba 官方称域内字错率更低，速度约 6.3 倍 |
| Fun-ASR-Realtime `fun-asr-realtime`、`fun-asr-realtime-2026-02-28` | `language_hints=ja` | 句级和字级，毫秒 | WebSocket，可边送 PCM | 云端首选。适合真流式；音频离开本机 |
| Qwen-Audio-3.1-ASR-Flash-Streaming | `language_hints` 含 `ja` | 句级和字级 | WebSocket | 与 Fun-ASR 同类，作备选 |
| 千问 `qwen3-asr-flash` | `language=ja` | 文件转写 `qwen3-asr-flash-filetrans` 有字级时间戳 | HTTP，整段或 URL | 适合离线转写，不适合边播边出 |
| `qwen3-asr-flash-realtime` | 含日语 | 官方写明当前不返回时间戳 | WebSocket | 字幕对齐不够用 |
| SenseVoice `sensevoice-v1` / 开源 SenseVoice-Small | `ja` | 云端为句级毫秒；开源模型按静音切段 | 录音文件 HTTP，非双向流 | 速度好。第三方比较里日语字错率略高于 Whisper large-v3 |
| MiMo-V2.5-ASR | 契约无日语 | 无 | 整段 Base64 后文本 SSE | 不采用 |

Kotoba-Whisper v2.0 保留 large-v3 编码器，解码器压成两层，16 kHz。官方评测写明：ReazonSpeech 留出集优于 large-v3，JSUT 与 Common Voice 日语子集与 large-v3 接近。v2.2 在同一识别结果上加标点和说话人分离。权重是 Hugging Face Transformers 格式；放进 faster-whisper 或 whisper.cpp 前要做对应转换，不能把未核对的第三方转换包当成官方产物。

公开可下载的是权重，不是按量调用的识别服务：

- `kotoba-tech/kotoba-whisper-v2.0`、`kotoba-tech/kotoba-whisper-v2.2` 在 Hugging Face，用 Transformers 在本机跑。
- 公司另有一套实时语音 API，文档在 <https://docs.kotoba.tech>，状态为私有 alpha，联系 `kotoba_product@kotoba.tech` 申请。能力是 WebSocket 流式识别、REST 文件转写（可要分段时间戳）、语音到语音翻译和日语 TTS。输入语种写明英、日、韩、中。SDK 为 `kotoba-sdk`。文档没有把这套接口写成 Kotoba-Whisper v2.2 的托管版。
- `kotoba-sdk` 还列出 fal 上的 `Kotoba-Technologies/kotoba-stt` 与 `kotoba-streaming-stt` 部署地址，并写明 fal 不支持其批量任务接口。这是自备密钥后的部署目标，不是打开即用的公开价目页。

Fun-ASR 实时主版本和 `2026-02-28` 快照都接受日语提示，默认返回句子起止和字级时间。8 kHz 的 `fun-asr-flash-8k-realtime` 只有中文，不能拿来识别日语。

云端接口仍要单独用成人对白样本看是否被审核截断。本机 Whisper 系没有这条拦截，但会把音乐、喘息和非语言声音听写成句子，字幕前需要按置信度或静音丢掉这类片段。

## 今晚实验记录（2026-10-15）

当晚的目标从「边播边出实时翻译」改成了验证一条更稳的离线链路：音频文件 → 带时间戳的日语文本 → 同一时间码的简体中文。实时接口只作为对照，没有拿来出整片字幕。Curated 播放器仍没有字幕渲染，这些实验没有接入产品。

### 样本

本地文件 `D:\asr-test\EBWH-273.mp4`。时长 02:01:28.45（7288.4485 秒），约 6.6 GB，H.264 1920×1080 59.94 fps，AAC 48 kHz 立体声。对照段是 42:00–45:00，因为这里有课堂讲解、人名、拉面和香水等可核对的对白；片中其它 12 秒抽查大多只有「あ」「うん」。

音轨处理：FFmpeg 只映射音轨，压成 16 kHz、单声道、64 kbps MP3，约 56 MB。整片再按约 5 分钟切成 25 段。MP3 容器起点约有 69 毫秒偏移，分段时长用 ffprobe 累加，不假设每段正好 300 秒。

### 试过的调用

| 顺序 | 接口 | 样本 | 结果 |
|---|---|---|---|
| 1 | `qwen3-asr-flash-realtime` | edge-tts 合成的一句日语 | 原文完全正确 |
| 2 | 同上，服务端 VAD | 片中若干 12 秒窗口，以及 42:00–45:00 | 有对白的窗口能出日语；非对白被写成「あ」「うん」。180 秒约 56 秒返回。没有时间戳 |
| 3 | `qwen-audio-3.1-asr-flash-filetrans` | 同一段 180 秒 | 约 7 秒返回。句级和字级时间戳。任务 `0d6dd1c7-de4f-419e-aae0-2606ac30eb2e` |
| 4 | `qwen-plus` 文本翻译 | 第 3 步的句子 | 时间码保持不变。未加译名约束时「佐々木」被译成佐藤 |
| 5 | 3.1 文件转写 + `qwen-plus` | 整片 25 段 | 25 段全部成功，660 句。转写加翻译约 199 秒。0 句未译 |
| 6 | `qwen3-asr-flash-filetrans` | 同一段 180 秒 | 约 5 秒返回。用量 90 秒。任务 `647b5929-a8dc-43b0-8fc4-ea34453b867b` |

实时地址用的是公开北京入口 `wss://dashscope.aliyuncs.com/api-ws/v1/realtime`，模型 `qwen3-asr-flash-realtime`。密钥前缀是工作空间受限的 `sk-ws-`，没有从密钥里猜测 WorkspaceId；这个公开入口可以直接用。音频为 16 kHz、16-bit、单声道 PCM。手工模式要 `commit`，VAD 模式不要。该模型官方说明不返回时间戳。

文件转写地址是 `POST https://dashscope.aliyuncs.com/api/v1/services/audio/asr/transcription`，请求头必须有 `X-DashScope-Async: enable`。本地路径不能放进 `file_urls`。做法是先 `GET /api/v1/uploads?action=getPolicy&model=<与后续调用相同的模型>`，把文件 POST 到返回的临时 OSS，得到 48 小时有效的 `oss://` 地址，调用时再加 `X-DashScope-OssResourceResolve: enable`。上传凭证按主账号加模型限流 100 QPS，文档写明不适合生产。3.1 的字段是 `input.file_urls`（数组，一次一个）和 `parameters.language_hints`；千问 3 的字段是 `input.file_url`（单个字符串）和 `parameters.language`。结果地址也不同：3.1 在 `output.results[].transcription_url`，千问 3 在 `output.result.transcription_url`。下载到的 JSON 里有带签名的临时文件地址，落盘前已抹掉。

同一密钥还能调用兼容接口 `POST https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions` 的 `qwen-plus`。翻译要求逐行对齐；行数不符就对半重试，单句失败才保留原文并标「未译」。整片这次没有走到单句失败。

3.1 的模型卡用 token 标价，看起来比「每秒不到两毫」贵。这段实测输入大约每秒语音 45 个 token，所以 3.1 更便宜。两边都只计被判定为语音的时长，不把整段 180 秒都算进去。若整片语音占比接近这段，外推大约是 3.1 ¥0.12、千问 3 ¥0.80。这不是整片账单，整片也没有再用千问 3 重跑。

### 敏感词过滤

3.1、Fun-ASR 和 Paraformer 在不传 `special_word_filter` 时启用百炼内置词表，命中词替换成等长 `*`。`system_reserved_filter` 默认 `true`。设为 `false`，并把 `filter_with_signed` 与 `filter_with_empty` 的词表留空，即可关掉系统词表、也不追加自定义词。当晚已经生成的 180 秒原文和整片原文里没有 `*`，说明默认词表没有改写这些结果。还没有用 `system_reserved_filter: false` 重跑，所以只确认了文档开关，没有做开关前后的差异对照。

千问 3 文件转写的文档没有把这套默认过滤写成它的能力。它另有固定开启的 7 类情绪。

### 留给后续需求设计的事实

这些是当晚已经看到的约束，不是已批准的方案。

- 离线「整段音频 → 时间戳原文 → 时间戳译文」在这部日语片上跑通了，比实时识别更适合做可保存、可重放的字幕。
- 实时模型能识别日语，但没有时间戳，并且会把非对白写成「あ」「うん」，不适合直接当字幕源。
- 识别和翻译是两次调用。听写错会进入译文；人名要有稳定译名，不能让模型每次重猜。
- 3.1 在这段样本上又好又便宜：句子边界和数字更适合字幕，费用约为千问 3 的六分之一。千问 3 的优势是个别同音词更准，以及自带情绪字段。
- 音频会离开本机，进入百炼临时空间，48 小时后失效。正式使用要换成自有存储上的稳定地址，不能依赖上传凭证接口。
- 密钥不能进渲染进程，也不能复用现有 `aiProvider`。语音按秒或按 token 计费，和 Agent 文本不是同一笔账。
- 播放器还没有字幕层。Web 与原生窗口要共用同一份 cue。已生成的字幕应能再次播放时直接用，避免重复计费。
- 5 分钟硬切会拆句。以后如果改切片，重叠部分的重复计费要单独算。
- 这部片的云端调用没有被内容审核截断，但不能据此写成「成人对白永远不会被拦」。3.1 的系统敏感词表仍默认开启。
- 本机 Kotoba-Whisper 当晚没有跑。它仍是音频不出机器时的候选，和这次云端实验是两条路。

**打开弹窗**

- 第一次打开只检查配置、当前文件和已有结果，点击「开始生成」才执行上传和付费调用。
- 顶部显示影片与实际文件名。多文件影片默认当前选中文件，无明确选择时使用影片的默认文件；允许从现有文件列表改选。第一版一次处理一个文件，不能把 CD1 字幕应用到 CD2。

- 显示本次翻译来源，默认跟随设置。普通任务不要求重复填写 API Key、模型或存储参数。

**运行中**

- 阶段为排队 → 提取音频 → 上传 → 日语识别 → 中文翻译 → 保存字幕。
- 进度基于真实数据：提取按媒体时长，上传按已发送字节，识别/翻译按已完成分段和句子统计。
- 云任务不返回细粒度进度时显示「识别中，已完成 8/25 段」与不定进度，不伪造匀速百分比，不承诺 199 秒固定耗时。
- 显示阶段、已完成量与错误摘要。低频状态同步复用任务事件/查询，重连读取数据库快照。
- 关闭弹窗不取消任务；重新打开恢复同一任务。提供明确的「取消任务」。停止后不再发新请求，已经提交的云任务可能继续完成和计费；此事实放在取消动作处说明。
- 后台任务可投影到现有任务/消息系统。完成、失败各记录一次，不重复弹 Toast，遵守现有播放静默规则。

**完成与失败**

- 主结果为可播放的中文字幕 `.zh-CN.srt` 与便于阅读的中文 `.zh-CN.txt`；建议同时保留日语 `.ja.srt` 作为原文字幕成品，支持原文/双语播放及以后重新翻译。双语显示运行时解析日语和中文 SRT，不依赖永久保存的结构化对白表；首期导出的两轨使用相同时间边界，若文件被外部修改后无法配对，应提示并回退单轨，不能只按序号错配。
- 文件名基于实际视频文件 stem 加语言与生成版本；例如 `EBWH-273.CD1.zh-CN.srt`，服务器目录使用 ID 隔离，下载名可友好命名。
- 完成区域列文件名、语言、格式、字幕数，提供「播放」「下载」「在文件夹中显示」。下载默认主结果，其余格式可从结果列表选择。
- 「在文件夹中显示」在 Server 本机打开文件管理器并选中成品。远端浏览器/Desktop 无法打开 Server 磁盘，提供下载；Server 没有图形桌面时同样使用下载。不能向远端 Desktop 发送一个服务端路径让它尝试打开。
- ASR 已完成、翻译失败：保留日语结果，展示「重试翻译」，不再上传音频或重复识别。
- 有句子最终未译时标记部分失败并统计数量；中文轨不静默混入日语，用户仍能选择日语轨或重试缺失项。
- 重新生成是明确动作，旧的完整版本在新版本保存成功前保持可播放；缺文件、被源文件替换等情况不能显示假成功。

建议在现有 AI 设置增加「字幕识别与翻译」区块，不改当前 Agent 的模型用途。

| 配置 | 第一版建议 |
|---|---|
| 启用云端字幕生成 | 默认关闭，用户在设置中启用 |
| 识别服务商 | 阿里云百炼，固定协议 |
| 识别模型 | 固定 `qwen-audio-3.1-asr-flash-filetrans`，显示为只读信息 |
| 地域 | 首期北京，与 Demo 一致；其它地域须验证同模型与接口后再开放 |
| 百炼 API Key | 独立凭证，仅 Server 保存，读取只回是否已配置，支持替换/清除 |
| 翻译方式 | 「使用现有 AI」或「使用千问」 |
| 现有 AI 翻译 | 复用当前 `aiProvider` 文本调用客户端、用量与现有治理能力，不复用 Agent 对话历史、工具执行或输出格式 |
| 千问翻译 | 使用百炼兼容文本接口，默认 `qwen-plus`，可在明确范围内选文本模型；默认使用识别的百炼 Key |

模型、翻译模式和提示词版本在任务开始时冻结；凭证通过 Server 配置引用读取，不复制进任务、前端、日志或字幕文件。配置变化后，已完成分段仍保留；恢复时校验兼容性，不能静默把同一版本混成不同模型结果。凭证更换允许重新鉴权后继续，模型/翻译方式变化应创建新的翻译修订并尽量复用原文。

识别与翻译分别显示校验结果。普通保存不自动上传影片。鉴权探测不能被包装为完整识别验证：真正验证 ASR 需使用随程序准备的短测试音频，明确它是一次小额调用。生产实现前核对现有 AI 治理中哪些限额只适用于 Agent 写操作，字幕属于派生文件生成，不应为了翻译要求开启 Agent 修改标签等权限。

远端第一版默认允许读取、播放、下载已生成字幕；发起云端识别暂限定 Server 本机。后续如需要远端发起，由本机设置单独开放「允许远端创建字幕任务」，不能因远端已有播放权限就自动允许上传 Server 音频。

### 4. 文件上传：实施前验证关卡

昨晚 Demo 使用百炼 getPolicy 临时上传。10 月 15 日已直接核对官方[上传文件获取临时 URL](https://help.aliyun.com/zh/model-studio/get-temporary-file-url)：上传后的文件有效期为 48 小时，凭证接口按「阿里云主账号 + 模型」限流 100 QPS 且不支持扩容；文件不可查询、修改或下载，只能用于对应模型调用。官方原文是「请勿用于生产环境」及「生产环境建议使用阿里云 OSS 等稳定存储」。

这里的 48 小时是每次上传文件的寿命，不是账号/API 只能使用 48 小时；当前文档未说明该接口只能调用一次或仅有几天试用期。技术上可在每次任务时重新上传，对于本地低并发、短时间完成识别、结果立即持久化的场景，这两项限制通常不是直接障碍。但这不构成供应商对长期正式使用的支持承诺，也不能把官方警示解释成接口必然无法运行。

结合用户追问，开发集成和自用测试可先沿用临时上传，不把开通 OSS 作为开始集成的前置要求；只将其作为模型输入中转，不存放字幕成品。上传策略封装在 Server 适配器内部，保留后续接 OSS 的能力。正式发布时明确采用了供应商不建议用于生产的路径，并根据届时支持情况决定是否切换；本次讨论未批准发布。

实施第一步应查当前官方模型、输入地址和上传契约，确认：准确模型 ID、日语参数、时间戳、大小/时长、任务轮询/取消/保留期、限流、词表过滤参数，以及当前是否提供适用于正式应用的上传方式。

优先选择供应商支持的正式文件上传方式。若模型必须拉取 URL 且没有合适的应用上传入口，使用用户的阿里 OSS 私有桶与短期签名 GET：

- Server 只上传提取出的音频，使用随机对象键，不暴露影片名；凭证限定桶/前缀，支持生命周期清理。
- 签名有效期覆盖排队、拉取和合理重试；任务结束清理对象，清理失败用生命周期兜底。URL 过期允许重签，不必重新识别已完成片段。
- 阿里 ASR 与对象存储权限是两套配置，不能假定百炼 API Key 可以上传 OSS。
- ASR 回传签名 URL 只在受控供应商边界内使用，不记日志/数据库/前端；规范化结果后抹掉临时地址，限制重定向、大小与下载超时。
- 不要求开放本机 HTTP 服务到公网，不发送整部视频，也不从浏览器上传完整音轨。

OSS 凭证、桶/地域/前缀可能成为额外用户配置。这是当前方案中最需要先消除的不确定性；本节没有宣称已查证生产接口或已选定存储 SDK。

### 5. Server 任务与数据结构

推荐抽出独立字幕业务服务（例如 `internal/subtitles` 与百炼适配器），由 App 生命周期拥有后台 worker。Go 原生实现正式调用，Demo Node 脚本保留为实验，不由产品通过 shell 启动。

现有 `backend/internal/tasks/manager.go` 是内存任务注册表，虽有 `Restore`，本身不保存分段。可复用其事件和任务投影；SQLite 持久任务、检查点和重启恢复要在字幕业务实现。现有 AI 整理持久任务提供模式参考，不能直接借其标签业务表。

建议结构：

- `subtitle_jobs`：任务 ID、requestId、movieId/fileId、源文件修订、源音轨索引、模型/语言/翻译配置版本、阶段/状态、错误、用量、当前产物版本。
- `subtitle_job_parts`：切片起止、音频指纹、云端 taskId、提交/完成状态、用量和临时检查点引用。云端 taskId 收到后立即持久化，恢复优先查询原任务；任务归档后不保留对白正文。
- 不新增永久 `subtitle_cues` 对白表。执行时结构化 cue 包含稳定 cueId、beginMs/endMs、原文、译文和翻译状态，逐条匹配；恢复所需正文放 Server 任务工作区的临时检查点文件，通过原子替换保存，不能只放内存。
- `subtitle_assets`：关联 fileId 与生成版本、语言、格式、受控相对路径/哈希、大小、完整性与发布状态。关系和查询索引在迁移时定稿。

恢复与幂等原则：

1. requestId 防止重复点击；同 fileId/源修订同时最多一个活动生成任务。建议起步全局一个任务、片段有限并发（例如 2），避免与 HLS 转码争抢磁盘和 CPU。
2. 源修订至少校验文件身份、大小、mtime、时长与选定音轨；无需先读完整 6 GB 视频计算哈希。源替换或重新绑定后字幕标过期，不能只按番号复用。
3. 提交前持久化意图、收到 taskId 后持久化；提交成功但响应丢失时，若供应商没有幂等/查询能力，标记提交结果未知，不盲目再次付费提交。明确提示重试可能重复计费，保留人工重试路径。
4. 重启恢复已存在 taskId 的轮询，复用已完成 ASR 与翻译。没有音频且上传已过期才重新提取/上传未完成部分。
5. 网络、429、5xx 有界退避；凭证、余额、审核或参数错误阻塞并给出具体原因，不无限自动重试。
6. 保存采用临时文件、校验、原子发布；文件系统与 SQLite 用准备/发布状态及启动对账处理跨资源中断。成品全部就绪后才切换当前版本。
7. 取消持久化状态，终止本机 FFmpeg、停止新提交与翻译；迟到响应不得发布为当前版本。失败/取消任务的检查点短期保留用于显式恢复，建议默认 24 小时，过期清理且显示需从成品或源视频重新处理；有效的排队/运行任务不按该期限误删。

### 6. 切片、翻译质量与费用

- 沿用已验证的 16 kHz 单声道压缩音频作为起点，确认正式接口允许。音轨索引需冻结；多音轨首期默认实际播放音轨，无法确定时选择默认音轨并在弹窗可改，不能识别错语言的配音轨。
- 大片仍需有界分段；先验证 3.1 实际输出上限。建议约 3–5 分钟，尽量在临近静音处切；保留精确媒体起止及编码延迟修正，不用「段号×300秒」推算。
- 若增加小范围重叠，必须依据绝对时间与文本去重，并记录额外上传/计费秒数。没有证据前不承诺完全避免跨段断句。
- 翻译输入使用 cueId + 原文，仅给少量相邻上下文及任务级译名表；模型返回 cueId + 译文，由服务端保留原始时间码。
- 校验漏 ID、重复 ID、空句、超长行和源文异常；失败缩小批次，最后只重试失败句。文本长度限制应避免截断实义，必要时将同一 cue 的译文换行。
- 人名词表在任务内稳定复用，无法核对的读音不强行猜汉字。音乐/喘息过滤只使用可验证信号，不能靠简单过滤「あ」「うん」删除真实对白。
- 系统词表、审核与无对白空结果分别处理。默认不宣称关闭供应商审核；支持的词表参数在供应商能力确认后明确设定并记录版本。
- 临时原文检查点尚在，或已有日语 SRT 成品时，允许只重新翻译；已生成字幕再次播放零模型调用。只有中文 SRT/TXT 且原文已清理时，不能承诺无需再次识别。
- 用量分别记录 ASR 输入/输出 token 或语音秒数、文本翻译 token、重试和已知重复提交。价格作为带日期的参考单价，识别、翻译和 OSS 分别展示，不能把样本 ¥0.12 当整片承诺。

### 7. 保存位置、导出与备份

用户后续明确最终产物跟随影片保存，可以专门创建文件夹，并提出结构化原文、译文和时间轴属于中间产物。本节据此修订：正式 SRT 与可阅读 TXT 放视频所在目录下的专用子目录，作为字幕内容的最终持久来源；用户指定目录名 `sub`，第一版固定命名，无需新增用户路径配置。Server 的现有 SQLite 数据库仅长期保存任务记录、文件关联、模型/用量、状态及成品完整性元数据，不长期保存重复的对白正文。音频、结构化识别/翻译结果和恢复检查点放 Server 任务工作区，不放入最终产物目录。第一版不新增字幕专用数据库文件。

目录示例（以实际视频文件名为前缀，多分部同目录时不会混用）：

```text
EBWH-273/
  EBWH-273.CD1.mp4
  EBWH-273.CD2.mp4
  sub/
    EBWH-273.CD1.ja.srt
    EBWH-273.CD1.zh-CN.srt
    EBWH-273.CD1.zh-CN.txt
    EBWH-273.CD2.ja.srt
    EBWH-273.CD2.zh-CN.srt
    EBWH-273.CD2.zh-CN.txt
```

用户已明确专用目录名为 `sub`。目录存在则复用，不清空目录，也不覆盖其中非 Curated 管理的文件。Server 保存相对视频目录的成品关联，视频路径重绑定或重扫时按目录及实际文件名重新核对；Web 和原生播放器显式加载此子目录中的对应字幕，不依赖外部播放器是否自动搜索。外部播放器可能需要手动加载 SRT，不承诺统一自动发现。「在文件夹中显示」定位到该目录内的选定成品。

现有默认数据库路径已核对 config 源码：Windows 正式版为 `%LOCALAPPDATA%/Curated/data/curated.db`（本机用户对应 `C:/Users/wujiahui/AppData/Local/Curated/data/curated.db`）；开发版为仓库 `backend/runtime/curated.db`。这是默认路径，实际运行可由 `CURATED_DATA_DIR`、`databasePath` 或迁移启动档案改变，不能据此声称已检查正在运行的数据库。字幕能力实现后新增表，数据跟随实际使用的数据库持久化。

- SRT/TXT 默认写 `<视频所在目录>/sub/`，文件 stem、分部和语言对应；同名用户文件不覆盖，发生冲突使用受控版本名。只读/NAS 创建目录或写入失败时保留任务工作区中的待保存成品和检查点，显示「生成完成、保存失败」，可重试保存或下载；清理前展示过期时间，不能按完成任务立即删除。媒体扫描应排除该生成目录，不将其文件作为影片、元数据来源或待导入对象。
- 正式成品发布并校验成功后清理音频、结构化结果及检查点。清理失败记录待回收并在启动时对账，不影响已保存成品；数据库只留任务与成品元数据。播放器从 SRT 解析为内存 cue，按 fileId/版本/文件修订缓存，换片或修订变化即失效，不再永久落一份对白表。
- 数据库备份保留任务与文件关联，不包含字幕正文；`sub` 目录必须跟媒体一起搬移和备份。只有数据库备份不能恢复字幕内容。恢复后校验成品存在性，文件缺失则标记缺失，提供从其它成品重建可重建的格式或重新生成；不能宣称从任务记录还原对白。
- 取消、失败和重启留下的工作文件设清理策略；清缓存不删除正式字幕。影片/文件删除与孤立资产回收走明确生命周期，不能误删用户视频或外置字幕。
- 显示文件只接收 assetId；Server 根据数据库解析并校验路径，不接受客户端提交任意绝对路径。

### 8. 播放器显示与设置

Web 与原生共用同一套 cue、语言轨、设置语义和文件版本；渲染实现根据引擎选择。

| 设置 | 第一版建议 |
|---|---|
| 显示模式 | 关闭 / 中文 / 日文 / 中日双语；有字幕默认中文 |
| 字号 | 小 / 标准 / 大，随视频显示区域缩放，窄窗换行 |
| 位置 | 底部，提供少量垂直位置调整；控制栏出现时避让 |
| 样式 | 白字黑描边，提供半透明背景开关；不做任意字体/颜色编辑器 |
| 时间偏移 | ±0.5 秒步进和归零；正值定义为字幕更晚出现 |

样式偏好按设备保存；轨选择和偏移按 fileId/字幕版本保存。换文件重置对应偏移；切换引擎保持所选字幕，偏移不改写导出的时间码。字幕切换、生成完成后的轨刷新都不应重建播放会话或暂停视频。

**Web**：以媒体 `currentTime` 加时间轴原点换算为源文件时间，显式处理从非零时间启动的 HLS 会话。建议隐藏原生 TextTrack 并读取 active cues，以共享字幕层绘制中日文本；直连/HLS、seek、暂停、倍速、页面全屏和控件显示都保持同步。字幕纯文本渲染，不用 `v-html`。字幕无交互区域不截获点击。

**Desktop 原生**：建议让 mpv 负责字幕时间调度与绘制；Server 的同一套 cue 派生为原文/中文/双语字幕资源，由 main 通过当前认证 Session 获取并受控缓存，使用收敛命令加载/选择，样式映射到 mpv。renderer 只发送当前 sessionId、轨 ID、枚举样式与有界偏移，不能发送任意文件路径、URL 或 mpv 命令。换服务器、换片、认证锁定及关闭时清理旧资源，沿用 session/revision 防迟到结果。实际 mpv SRT/ASS 字体、双语、边距和 Win/Mac 渲染应在小样中确认；若 libmpv 的当前渲染方式限制字幕，再验证 DOM 层方案，不能只根据低频进度快照宣称句级同步。

截图沿用现有「视频原画面、不含字幕」语义，必须验证 mpv 截图模式没有随字幕加载发生变化。

浏览器系统画中画通常只显示 video，不带 DOM 字幕层；第一版明确不承诺 PiP 自绘字幕。页面全屏属于第一版；PiP 若需支持需独立验证原生字幕轨或合成视频方式。

### 9. 拟议接口与代码落点

以下均为建议契约，实施时先定义 DTO、错误码与权限，再接 Web/Mock；尚未新增实际端点。

| 行为 | 建议 API |
|---|---|
| 读取/保存配置 | 扩展现有 GET/PATCH `/api/settings`，增加独立 `subtitleProvider` 配置与可用能力摘要 |
| 配置测试 | POST `/api/subtitles/provider/test`，识别/翻译分别返回验证结果，仅本机 |
| 创建任务 | POST `/api/library/movies/{movieId}/subtitle-jobs`，body 包含 fileId、requestId 和已支持的选项 |
| 查影片任务 | GET `/api/library/movies/{movieId}/subtitle-jobs`，按 fileId 过滤 |
| 查询、取消、重试 | GET `/api/subtitle-jobs/{jobId}`；POST 子路由 `/cancel`、`/retry`，重试范围由 Server 检查 |
| 字幕列表 | GET `/api/library/movies/{movieId}/subtitles?fileId=...` |
| 播放/下载内容 | GET `/api/subtitles/{assetId}/content`；规范化 cues 与导出格式通过受控参数/资源区分 |
| 文件夹定位 | POST `/api/subtitles/{assetId}/reveal`，仅 Server 本机且有文件管理能力 |

错误应区分未配置、能力不可用、无音轨、源变更、源丢失、提交结果未知、鉴权/额度、审核、超时、翻译部分失败与成品丢失。读取与下载延用现有认证，所有服务端操作再次验证 movieId/fileId/assetId 的关联和可访问性。

后端涉及 config/contracts、字幕 provider/worker、storage/migration、server handlers、backup。前端涉及 LibraryService 契约、Web/Mock 适配、详情弹窗、AI 设置、Web 播放字幕层与共享设置。Desktop 涉及 playback contract/preload/coordinator、受控字幕缓存与 native mpv adapter。业务 UI 不直接导入具体 Web adapter。

### 10. 实施切分与验收

1. **供应商与原生小样验证**：核对当前生产上传契约；短样本跑通 3.1 时间戳、中文翻译，以及 Win/Mac mpv 加载字幕与视频原画面截图。产出调用契约和依赖选择，防止在上传/渲染未定时扩写整套 UI。
2. **后端完整链路**：配置、持久任务/分段、上传识别、翻译、成品、重试取消、幂等和备份；fake provider 测故障，人工短样测真实调用。
3. **详情入口与弹窗**：按当前 fileId 创建/恢复任务，展示真实阶段，完成后下载/定位，补齐远端/无桌面/Mock 状态。
4. **播放器接入**：Web 直连/HLS 与 Windows/macOS 原生全部支持中文、原文、双语、样式和偏移，确保切换引擎和换片不串字幕。
5. **整片与交付验收**：复杂对白、长静音、跨段句子、多音轨、CD1/CD2、断网、重启、429、余额不足、取消、源替换和备份恢复；同步手册与实现事实。

以上是交付切片，最终第一版应形成「生成 → 获取文件 → 播放显示」闭环，不能只完成服务端后宣称需求完成。

关键验收：

- 详情点击入口后可明确开始；同文件重复点击只有一个活动任务；关闭弹窗或刷新不丢任务。
- ASR 成功后翻译失败，只重试翻译；Server 重启复用已有云 taskId 与完成结果，不静默重新计费。
- 两段影片、同一影片多文件、重新绑定文件以及换服务器不会串字幕；旧完整版本在新版本失败时可用。
- Web 非零 HLS 起点、seek、暂停、倍速与 Win/Mac 原生按同一 cue 正确显示；偏移正负方向一致，控件无遮挡。
- 本机可定位成品，远端/无桌面可下载；凭证、签名 URL 不出现在日志、任务 DTO 或产物中。
- 无对白产生合法空结果，不报成平台异常；部分未译和审核有准确状态，不包装成完整成功。
- 清缓存后仍可播放影片旁字幕；数据库与媒体字幕一起恢复后可查询与播放。只有数据库备份时准确显示成品缺失，不制造空白成功；成功清理中间产物后仍可从 SRT 加载原文/中文/双语。

验证遵循 `docs/ops/2026-04-08-agent-build-and-test.md`：根目录 pnpm typecheck/lint、相关 Vitest 与 build；backend 目录运行相应 Go tests 与要求的编译/vet，Desktop 合约/native adapter 测试和 Win/Mac 实机验证。重点测试恢复、隔离、时间原点与付费幂等，不为普通静态文案增加镜像测试。本次仅文档方案，无需运行业务构建或模型调用。

实现后同步 `.cursor/rules/project-facts.mdc`、必要时 quick-reference、README 短入口、`docs/guide.md`、`docs/reference/2026-03-21-library-organize.md`（配置变动）、`CLAUDE.md` API 清单和 `docs/reference/architecture-and-implementation.html`，更新前端 UI 规范中形成的稳定播放器规则。当前不把拟议 API 写成实现事实。

### 11. 建议默认决策与待验证项

建议默认：离线生成；日语 → 简体中文；一份实际视频文件一个任务；识别固定千问 3.1；翻译默认现有 AI、可切千问；按用户后续要求，SRT/TXT 放视频所在目录下的专用子目录（用户指定 `sub`），Server SQLite 长期仅保存任务和成品元数据；音频、结构化原文/译文/时间轴及检查点为临时产物，成功保存后清理，失败/取消短期保留；本机可生成，远端首期播放/下载；Web 与原生均纳入第一版。

### 13. 翻译模型选择修订（2026-10-16）

用户澄清「字幕翻译」实际是选择翻译模型，「现有 AI 服务」指用户在 AI 设置中配置的模型。最新交互覆盖第 3 节及原型初版中的二级选择建议：只提供一个「翻译模型」下拉框，包含「用户配置的 AI 模型」「千问 Flash · 经济」「千问 Plus · 均衡」。千问选项分别映射 `qwen-flash`、`qwen-plus`，不再先选「使用千问」后另选模型。默认保留用户已配置模型；希望全部使用千问时建议 Plus 起步，Flash 作为低成本备选。任务弹窗默认继承设置，可为本次任务改选，实际执行时冻结模型；配置变更不改变进行中的任务。

10 月 16 日直接核对阿里官方[模型价格](https://help.aliyun.com/zh/model-studio/model-pricing)、[qwen-flash](https://help.aliyun.com/zh/model-studio/qwen-flash)、[qwen-plus](https://help.aliyun.com/zh/model-studio/qwen-plus)：北京地域、单请求输入不超过 128K token、标准在线调用、不使用思考模式时，Flash 输入/输出为每百万 token ¥0.15/¥1.5，Plus 为 ¥0.8/¥2。以总输入 10 万 token、输出 10 万 token 举例，翻译分别约 ¥0.165、¥0.28；不包含 ASR/存储，且不是按影片时长报价，超过输入档位或使用思考模式应重新计价，不计免费额度、缓存或 Batch 折扣。

选择依据：两者可用于自定义提示词的文本任务，适合 cue ID 对齐、译名与上下文约束；Flash 成本更低，Plus 已有本项目整片翻译实测。Plus「均衡」是产品定位，不构成同样本质量胜出的结论；Flash 当晚未实测，实施验收应进行同一段日语对白的 A/B 对照。调用时使用非思考模式以控制延迟和费用，参数需在适配器中按模型契约设置。本文未新增真实调用。
