# Android 与 Server 媒体获取性能评估与优化计划

日期：2026-11-23。状态：已实施第一批核心优化并完成两端相关测试；部署和前台性能验收尚未完成。原评估数据与后续计划保留，当前结果见文末实施记录。下文“详细实施计划”中的接口、参数与指标属于拟定设计，不代表当前已支持。

用户反馈：首页/列表、图片和点击播放都偏慢；手机通过同一局域网 Wi-Fi 直连服务端。

## 结论

两端均有优化空间。优先处理跨端请求形状、图片传输量和播放能力协商，而不是统一增大并发、缓存或超时。当前本机列表查询较快，尚无证据证明 SQL 执行是用户所有慢体验的主因。手机网络探测观察到较高且不稳定的延迟、大图传输明显慢，但设备处于息屏 Dozing，不能直接等同于 App 前台表现。

初次评估阶段未修改业务代码、数据库、服务器设置或手机设置，也未安装应用、创建播放会话、推送或发布。服务端工作区原有播放器/字幕及文档修改保持原样。

## 范围与测量边界

- Android 源码：`curated-droid`，当前 Curated 页面、API client、repository、Coil 与 Media3 播放路径。
- Server 源码：`jav-lib/jav-shadcn`，审查时 HEAD 为 `ecca0c36`，另有既有工作区修改。
- 运行实例：本机 `:8081` 的 release Server 1.8.0，buildStamp `20261017.175547`，返回 755 部影片；这是实际运行版本，不代表与当前源码完全一致。`:8080` 开发实例只有 43 部，未用它代替正式资料库做性能结论。
- 手机：ADB 已连接 Android，Wi-Fi 频率 2462 MHz、链路速率报告 144 Mbps、RSSI -20 dBm；电脑通过以太网连接。链路速率不是 HTTP 有效吞吐量。
- 测量时 `mWakefulness=Dozing`。未唤醒或操作手机 UI，也未测量实际 App 首屏、图片解码、首帧或持续播放卡顿。
- 小样本、顺序执行、连接和文件缓存状态未统一控制，不构成 P50/P95 或冷启动基准。

## 代码确认的优化点

### 1. 首页请求多、最慢详情阻塞首屏（优先级 P1）

Android `app/phone/src/main/java/dev/curated/app/presentation/curated/CuratedHomeViewModel.kt`：先读推荐 ID，再以 `Semaphore(4)` 请求每部影片完整详情，最后 `awaitAll()` 一次性发布内容。Server `backend/internal/app/homepage_daily_recommendations.go` 目前上限为 8 个 Hero 和 6 个推荐 ID；去重后最多 14 个详情，连推荐快照最多 15 个 JSON 请求，详情最多分 4 轮。

完整详情还会加载预览图、演员头像及文件列表，并检查本地媒体资产。首页只显示卡片却承担了详情开销；单个慢请求可以拖住整个首页。Android 现在已经有有界并发，不能再按旧评估称其为串行加载。

建议：

- 服务端在兼容旧客户端的前提下提供推荐卡片摘要，或有上限的按 ID 批量摘要查询；数据库关联与本地封面处理按批次进行。具体接口尚未确定，当前不宣称已有该能力。
- Android 优先发布 Hero/第一屏，后续区域独立补齐；保持推荐顺序、去重、鉴权失败清空和取消语义。
- 复用按服务器与认证状态隔离的摘要/详情缓存和进行中的相同请求；定义容量、有效期及元数据变更失效，不能永久缓存。
- 历史页 `CuratedHistoryViewModel.kt` 同样对全部进度逐项拉详情并等待整批完成，应优先最近一屏，再分页/渐进补全。

### 2. 卡片图片大小不统一，预览缩略图使用同一原图 URL（P1）

Android 列表优先 thumb，缺失时回退 cover；详情预览的小图和全屏图使用相同 URL。Coil 可按显示约束缩小解码尺寸，但这不减少服务器发送的原始字节。

Server `backend/internal/server/movie_poster_local.go` 中影片封面/预览资源通过 `http.ServeContent` 发送已有文件，该入口没有按展示尺寸生成派生图片。现有 thumb 是资产类型，不保证统一的移动端像素尺寸或字节预算。抽样已出现 12 KB 与 364 KB 的卡片图片差异。

建议：为封面、预览图生成固定尺寸档位的派生图，按实际卡片尺寸及屏幕密度选档；格式、质量、宽度与方向先对照视觉质量和字节数再定。后台生成、并发合并、文件版本失效、鉴权和缓存边界一并设计；全屏仍取大图。优先限制无缩略图时的整张 cover 回退成本。

本地缺失预览时，`proxyMoviePreviewAsset` 可实时请求远端，超时上限 20 秒，响应 `private, no-cache`，当前代理分支没有将图片写入本地缓存。对于实际走该分支的图片，可做有容量限制的落盘缓存与请求合并；不要把第三方源站的等待归于局域网。

### 3. 文件检查在 SQLite 单连接持有期间执行（P1）

`backend/internal/storage/sqlite.go` 设置 `SetMaxOpenConns(1)`。`BatchMoviePosterLocalReady` 在遍历未关闭的查询 rows 时同步 `os.Stat` 每张封面；因此慢磁盘检查期间其他数据库请求可能排队。列表已有批量关联查询，不能误诊为列表所有关联都逐行 SQL。

建议先把必要行读到内存并关闭 rows，再做文件检查；按测量结果补资产状态/版本缓存和失效机制。这样可缩短占用数据库连接的时间，但不自动消除当前请求自身的所有 stat 耗时。以慢文件系统下并发列表、进度写入和图片请求的延迟验证收益。

不要直接把单连接改成大连接池：WAL、事务、每连接 PRAGMA、迁移与写并发需要成套验证。已有排序与资产索引，不应未经 EXPLAIN 就重复添加索引。

### 4. Android 播放能力与浏览器决策混用（P1）

Android `CuratedApiClient.getPlaybackDescriptor()` 只发送影片路径，没有上报设备容器/音视频解码能力；虽带 `X-Curated-Client: android`，当前播放路由没有据此建立原生播放器能力分支。`CuratedPlayerViewModel.kt` 在 descriptor 返回后才准备 ExoPlayer。

Server `backend/internal/app/playback_decision.go` 使用浏览器容器/编解码规则。部分 Android/Media3 可解复用且设备可解码的文件可能因此进入不必要的 HLS，但必须按具体设备与源文件确认，不能假设所有 MKV/HEVC 都可直接播放。

进入 HLS 时，descriptor 会等待启动队列、FFmpeg 和首片段可用。`backend/internal/playback/manager.go` 对 libx264 转码还允许最多 12 秒的额外预缓冲等待（期待第 4 段）；整体启动使用 24 秒 context。这些是等待上限和条件分支，不是每次必耗时。

建议加入明确的原生客户端能力协商，支持时优先 direct，需要时 remux，再转码；保留用户强制推流设置及错误后的受控 fallback。分别记录 descriptor、会话排队、探测、首片段、Media3 准备、首帧耗时，再决定是否调整软件转码预缓冲。降低预缓冲要同时检验后续重缓冲率。

当前已有媒体探测内存缓存和 SQLite 持久缓存，按文件 size/mtime/schema 校验；不能按“每次播放都会重跑 ffprobe”解释慢启动。未实测任何影片首帧，播放问题仍是源码证据，未锁定用户具体慢片。

### 5. 请求取消与媒体流超时策略（P1，稳定性一起处理）

Android API 通过 IO dispatcher 调用同步 `Call.execute()`，协程取消未主动连接到 `Call.cancel()`。快速搜索、返回或刷新时，旧网络请求可能继续占用资源；现有 `ensureActive()` 能防旧结果发布，但不能替代底层请求取消。

建议用可取消的 suspend HTTP 桥接，并确保取消异常不被普通错误处理吞掉。播放器当前复用 API OkHttp client，默认有 30 秒整体 call timeout；应单独创建共享认证和连接池的媒体 client，保留合理 connect/read 超时并避免把完整长媒体响应限制为短 JSON 总时限。该项是可靠性风险，尚无证据表明用户每次慢启动由它导致。

## 已有能力，不重复建设

- Android：首页最多 4 路详情请求；历史详情最多 6 路；影片每页 50 条；搜索 300ms 防抖；影片首屏不再等待播放进度。
- 图片：Coil 内存/磁盘缓存，默认磁盘上限已为 256 MiB；独立图片 dispatcher 每主机最多 8 路；本地图片 URL 有版本且可缓存 7 天。
- Server：列表关联按批次查询、既有索引、视频 Range/ETag、媒体探测持久缓存、HLS 启动队列和编码器预热。

因此，不以扩大图片缓存、去掉分页、无限并发、盲目降低缓冲或统一拉长超时作为主要解决方案。

## 推荐实施与验收顺序

1. **建立前台基线**：同一 APK/Server/资料库，手机亮屏且 App 前台；对比当前 2.4 GHz 与可用的 5 GHz 接入。记录列表 JSON、首张封面、首页首屏可用、详情可用、点击到视频首帧；区分冷缓存/热缓存，重复采样后计算 P50/P95。
2. **首屏与图片**：先完成首页摘要批量获取/渐进展示、统一派生缩略图和取消传播；预期减少请求轮次、传输字节及被最慢项阻塞的时间，不预先承诺百分比。
3. **服务端文件检查**：释放 SQL rows 后检查磁盘，再依据测量补状态缓存；验证慢盘情况下其他请求不被长时间阻塞。
4. **播放协议**：选实际慢片做 direct/remux/transcode 对照，落实 Android 能力协商、媒体 client 和 fallback；再调整 HLS 启动缓冲。用首帧与后续卡顿共同验收。
5. **进一步优化**：若仍存在数据库等待，再评估读写分离/WAL；若远程/大响应场景有收益，再加 JSON 压缩、游标分页等。当前 755 部本地列表样本不足以把它们排在首位。

涉及新 API/架构的实施必须同步 Server 合约与项目入口文档，以及 Android `doc/API.md`、DTO、调用方和 `doc/AGENT_MEMORY.md`；本评估没有新增接口。

## 详细实施计划

### A. 范围、交付原则与依赖

目标是减少“打开页面到看到内容”“滚动到图片出现”“点击播放到第一帧”三段实际等待，同时保持续播、鉴权、缓存隔离、取消和旧版本兼容。

首轮覆盖 Android 首页、影片库、详情预览、观看历史，以及 Server 对应摘要、图片和播放路径。保持现有界面布局、配色、分页及用户设置。演员独立页面、精选帧、漫画/照片资料库不扩展为本轮功能范围；共享组件变化需要回归验证。

实施依赖：

| 阶段 | 主要交付 | 依赖 | 发布批次 |
| --- | --- | --- | --- |
| M0 | 前台性能基线与分段计时 | 无 | 内部验证 |
| M1 | HTTP 取消、连接策略、数据库连接占用修复 | M0 | 第一批 |
| M2 | 首页批量摘要与渐进显示 | M1，先 Server 后 Android | 第一批 |
| M3 | 移动端派生缩略图与首屏资源优先 | M0/M1；与 M2 使用同一摘要模型 | 第一批 |
| M4 | 详情缓存、历史首屏分批补全 | M1/M2 | 第二批 |
| M5 | Android 能力协商、直播放优先与错误恢复 | M0/M1 | 第三批 |
| M6 | 组合回归、性能对比、版本兼容验收 | 每一批对应阶段完成 | 每批必做 |

M1 的 Android 网络修复与 Server 文件检查是两个独立修改单元；M2/M3 的服务端与客户端也分别提交。每完成一个行为单元就运行对应验证并提交，不混入当前工作区既有字幕/播放器修改。发布、推送另按用户指令和现有发布流程执行。

### B. M0：建立可复现的前台基线

**任务 M0-1：固定环境与样本。**

- 使用同一手机、同一 APK 构建类型、同一 Server 构建与同一资料库快照。主验收采用 release 或与 release 优化一致的 staging 包；Debug 数字只用于排查。
- 手机亮屏、App 前台，关闭本轮测试人为施加的限速；分别记录当前 2.4 GHz 和可用的 5 GHz，不能以切换网络后的结果冒充代码收益。
- 分开定义：应用进程冷启动、客户端内容/图片缓存冷、Server 派生图片未生成、Server 媒体探测缓存未命中。使用隔离测试 profile 或样本清理测试缓存，不清除用户设置与生产资料库。
- 数据集包括实际 755 部库；另用隔离的 5,000/20,000 条合成库检查算法扩展性，不修改生产数据。图片覆盖小图、大封面、竖横图、透明图、缺失/损坏图与远端预览。
- 视频选择 MP4 H.264/AAC、设备支持的 HEVC、MKV、仅音频不兼容、必须视频转码、历史续播及多文件影片。标注分辨率、码率、容器和设备解码支持。

**任务 M0-2：增加分段计时。**

- Android：通过 OkHttp EventListener 记录请求排队/连接/首字节/响应结束/取消，区分 JSON、图片、视频；记录页面内容首次提交、首张图片完成、首屏实际显示及 Media3 `onRenderedFirstFrame`。`STATE_READY` 不作为首帧替代。
- Server：记录请求总耗时、SQL 执行、资产 stat、摘要组装、图片命中/排队/生成；播放记录探测缓存命中、会话排队、FFmpeg 启动、首片段就绪及 descriptor 返回。
- 可在开发诊断下使用请求 ID/Server-Timing 关联两端；请求 URL、Cookie、PIN、文件路径和影片标题不作为性能日志内容。日志有采样与容量上限，避免测量本身影响性能。
- `database/sql` 的 WaitCount/WaitDuration 可记录区间增量，但它们是进程聚合值，不能冒充单个请求的数据库排队耗时。

**任务 M0-3：输出基线表。**

关键首页/图片/直播放组合每个条件至少 50 次；次要格式和异常组合先做 20 次探索，接近门槛时扩样。交错执行改前/改后样本，记录 P50/P95、错误率、字节数、请求数、CPU/内存及缓存命中率。记录息屏恢复作为独立场景。

完成条件：能区分等待来自网络、请求串联、磁盘、图片传输/解码或播放准备；所有后续优化均可用相同场景复测。

### C. M1：清理无效等待与共享资源阻塞

**任务 M1-A：Android 可取消 HTTP。**

- 将 Curated API 的同步 `execute()` 改为 suspend 的异步调用桥接；协程取消立即关联 `Call.cancel()`，响应体在成功、错误及取消竞态下均正确关闭。
- API、repository 及 ViewModel 调用保持结构化协程；解析大响应放在合适 dispatcher，不把 JSON 解码转移到主线程。
- 所有普通异常捕获先传播 CancellationException；旧搜索、旧服务器和旧页面请求不能再发布状态。
- 明确共享请求取消规则：相同请求合并后，一个页面退出只取消自己的等待；最后一个订阅者退出时才取消非后台刷新任务。
- 先保留当前 API/图片并发上限；不要将同步 execute 的行为错误归因于 OkHttp 异步 dispatcher 的每主机限额。

验证：MockWebServer 延迟响应，覆盖搜索连续变更、退出页面、切服、取消与响应同时发生、401/403、单项失败。验收为取消事件可观测、资源释放、旧结果不覆盖新页面。

**任务 M1-B：隔离媒体流超时。**

- 建立明确限定的 API、image、media client 注入，避免错误注入播放器。媒体 client 从基础 client 派生，复用 CookieJar、认证头与连接池。
- API 保留现有短请求超时；媒体流不使用 JSON 的 30 秒整体 call timeout，保留 connect/read 超时及播放器取消/错误恢复。
- 图片是否需要单独整体超时由 M0 的大图样本确定，不把所有客户端统一设为无限等待。

验证：超过 30 秒且持续有数据的媒体响应不中断；真正断流、退出播放器及鉴权过期仍能终止并给出有效状态。

**任务 M1-C：Server 在文件 I/O 前释放 SQL rows。**

- `BatchMoviePosterLocalReady` 先读取 movieId/type/path，检查 rows 错误并关闭，再执行文件检查；核查演员头像等相同实现模式，按相同行为边界处理。
- 文件路径许可规则不变；不使用过期的“文件存在”缓存替代实际打开时的权限/路径校验。
- 首步保留 SQLite 单连接及现有索引。仅在 M0/M1 复测仍显示 stat 明显耗时时增加有界状态缓存：拟定正缓存 30 秒、缺失缓存 3 秒，结合入库、刮削、搬移、删除、资料库根变更主动失效。具体 TTL 由外部修改可见性要求校准。
- 超时/无权限/I/O 失败不能无限缓存为“缺失”。缓存键包含资料库/策略代次，不能跨资料库复用。

验证：使用可控制阻塞的文件检查夹具，在 stat 未完成时，另一个列表/进度 SQL 请求仍可完成；同时覆盖文件删除、版本变化、非法路径及取消。真实慢盘验证单独计时。

主要文件：Android `CuratedApiClient.kt`、`CuratedRepositoryImpl.kt`、`CuratedOkHttpClientFactory.kt`、`ApiModule.kt`、`CuratedPlayerViewModel.kt`；Server `movie_asset_file.go` 及相关资产查询。

### D. M2：首页直接获取卡片摘要

**任务 M2-S：Server 摘要契约及批量查询。**

拟定协议，实施前在 contracts 与 Android API 文档中同时定稿：

| 拟定接口/字段 | 用途与边界 |
| --- | --- |
| `GET /api/homepage/recommendations?include=cards` | 保留原有日期、推荐 ID、推荐理由，额外返回 `cards`；一次响应满足首页卡片展示 |
| `POST /api/library/movies/summaries`，body `{movieIds:[...]}` | 只读批量摘要，供历史等按 ID 查询；最多 50 个输入 ID，限制 body，重复 ID 去重 |
| `MovieCardSummaryDTO` | ID、标题、番号、片商、卡片需要的演员/年份/评分/收藏状态，以及图片 URL/变体；不含简介、预览图全集、完整演员头像与文件列表 |
| `server-info.capabilities` 新能力标识 | 复用已有能力列表声明支持摘要/图片变体；标识名称在接口实施时固定，不新增独立探测系统 |

补充约定：

- 保留推荐 ID 的业务顺序，不依赖 SQL IN 的返回顺序；摘要数组按去重后的请求 ID 顺序返回，包含有限的 `missingIds`。影片不存在或已回收时跳过，不使整批失败；数据库错误与鉴权失败仍使请求失败。
- `cards` 缺省/缺失表示旧协议，`cards: []` 表示新协议下确实为空；Android DTO 必须区分，不能因空列表触发重复请求。
- 首页卡片从推荐快照中的 ID 取当前摘要，不把完整详情写进每日快照。已删除 ID 可跳过，但不能仅因加载卡片而重新随机生成推荐。
- 使用独立的摘要 SELECT 与批量关联查询。响应变小但服务器仍循环调用 GetMovieDetail 不算完成。
- 首页摘要不扫描所有预览文件，不读取完整文件列表；获取卡片必要数据后再处理本地封面。
- 新协议请求常态为 1 次首页 JSON；如果需要能力探测，复用连接阶段结果，不在每次页面加载前新增一次串行探测。

**任务 M2-A：Android 渐进显示与兼容。**

- 首页 UI 使用卡片摘要模型，点击详情后才请求完整详情；Hero/推荐的顺序和交互不变。
- 有缓存时先显示合法缓存并后台更新；无缓存时显示现有结构占位。拿到摘要立即显示文字/可点击卡片，图片独立加载，不等待整批图片。
- 新 Server 返回完整摘要时一次提交即可；旧 Server 路径继续最多 4 路详情，但首屏/Hero 优先，按区域/节流增量发布，避免等最慢详情。
- 独立区分首次加载、刷新、局部失败和整页错误；一个失效影片或图片不挡其他内容。AUTH_LOCKED 清空相关内容并进入解锁流程。
- 能力缺失走旧路径；已声明支持但返回 500、超时或鉴权失败时按实际错误处理，不静默重试旧路径放大请求。

验证：新/旧 Server、空推荐、跨区域重复 ID、缺失影片、乱序完成、首个详情很慢、切服与认证失效；断言新路径最多 1 次首页业务 JSON 请求、0 次逐片完整详情请求。HTTP 总数另计已有启动/鉴权请求，不能把它们从整段用户耗时中隐去。

主要文件：Server `contracts.go`、`homepage_daily_recommendations.go`、`library_repository.go` 和对应 server handler；Android `CuratedDtos.kt`、domain mapping、repository、`CuratedHomeViewModel.kt`、`CuratedHomeScreen.kt`。

### E. M3：统一派生图片，减少传输字节

**任务 M3-S1：派生图片服务。**

- 新增职责明确的图片派生模块；可复用已有缩放实现经验，但不把影片封面硬套精选帧的 320×180 PNG 规则。
- 首版拟定按宽度 320/640 像素提供卡片与预览小图，Hero 可选 960；保留原始比例、不放大小图、不预先裁掉海报内容。Android 按实际布局像素选择最小合适档位。
- 照片类默认先使用可稳定构建的 JPEG，质量候选 80；保留透明图的适当格式，正确处理 EXIF 方向及源格式。WebP 仅在编码依赖、安装包兼容与实测收益满足时纳入，不为格式引入本轮不必要的原生依赖。
- 缓存键包含资产身份、源文件版本（size/mtime 或现有资源版本）、尺寸、格式、编码策略版本。写临时文件后原子替换，同一键的并发生成合并。
- 有界队列、有限 worker，初始 1–2 个；限制解码像素/输入体积并验证异常源，防止生成任务耗尽内存。实际限值依据资料库样本确定并记录。
- 扫描/刮削写入资源后异步生成；历史图片按首页、首屏、近期访问顺序渐进回填。先预热目标页面再启用客户端新 URL；不在 Server 启动时阻塞全库生成。

**任务 M3-S2：资源响应及生命周期。**

- 在摘要、列表和详情里新增可选图片变体字段，旧 coverUrl/thumbUrl/previewImages 保留；预览变体按稳定资产 ID/序号关联，避免数组缺项错位。
- 拟定媒体资产派生图 GET 路由使用固定尺寸枚举；来源仅能是已登记媒体资产，不接受任意文件路径或任意远程 URL。
- 只有完成生成的派生图才对外声明为 ready URL。未就绪时返回已有图片 URL并安排后台生成；原图不能以“派生图已经生成”的地址和 7 天 immutable 缓存对外返回。
- ready URL 包含版本并使用 private 长缓存；源更换后 URL 改变。生成失败保留原图能力，不阻断 JSON。
- 缓存是可再生数据，有明确容量与淘汰策略。初始评估 1 GiB 派生图预算、LRU 和旧版本回收；M0 样本确认后定稿。清理不删除原始图片，正在写入/读取的文件需受保护。
- 远端预览代理单独按既有来源缓存，合并同源重复获取；保留来源限制、容量上限与短暂失败退避。其优化不阻塞本地缩略图首批交付。

**任务 M3-A：Android 图片调度。**

- 小卡片和预览条请求小图，全屏请求大图；使用布局约束/density 选档，避免原图预取。
- 保留单例 Coil 与现有用户缓存偏好，不重设 256 MiB。确保请求尺寸、URL 版本和认证范围能稳定复用缓存。
- 可见区域优先，预取最多下一屏，快速滚动及时取消离屏预取；播放器前台时停止无关页面预取。
- 8 路图片并发仅作为当前起点，用相同条件对比 4/6/8 路的首屏 P95、错误率和带宽，再固定策略。首版不增加复杂自适应算法。
- 核查屏幕锁定/退出账号/切服下的私有图片命中：内存展示与磁盘读取必须服从当前授权状态；无需为了重新解锁而盲目删除全部可再用资源。

验证：横竖图、方向、透明度、损坏/超大源、首次回填、冷/热命中、源替换、并发请求、磁盘空间不足、缓存淘汰、鉴权失效。检查一批真实海报的画质，统计各档字节 P50/P95。

### F. M4：重复访问缓存与历史首屏

**任务 M4-A：按服务器复用结构化内容。**

- repository 按服务器身份及 origin/认证代次复用，避免每次访问创建孤立的数据缓存。共享 OkHttp 已经存在，不把新缓存的收益称为新建连接池收益。
- 首版采用容量有界的内存缓存：卡片摘要候选 300 条/TTL 2 分钟、详情候选 50 条/TTL 5 分钟；由实际对象大小与内存曲线校准。暂不新增 Room 持久化内容库。
- 同一 key 请求合并；只缓存成功内容，不缓存取消或认证错误。显示缓存后重新验证，鉴权失效立即清理可见内容与相关内存缓存。
- 收藏/评分/元数据修改定向失效；播放返回更新对应进度；服务器切换隔离内容；每日推荐跨 UTC 日期失效。进度不固化在详情 TTL 中。

**任务 M4-B：历史按需补全。**

- 首版复用现有全量 progress 接口，排序后先补最近 20 条摘要，再按滚动每 20 条补齐，不对所有历史创建 async。
- 新 Server 使用批量摘要，旧 Server 使用现有受限详情并渐进显示；单条缺失不阻塞其他条目，认证失败不能被 runCatching 吞掉。
- 不声称此步骤已实现服务端历史分页。若 progress 响应本身在 M0 显示成为瓶颈，再增加 `(updatedAt, movieId/fileId)` 等稳定游标的正式分页接口；按现有多文件身份规则定稿。
- 校验列表页与 ON_RESUME 的进度刷新合并，重复生命周期事件不会产生重叠全量请求。

验证：上千条历史仍只请求首屏所需摘要；返回列表不丢滚动位置；同电影跨页复用；TTL/容量生效；删除、切服、解锁、并发订阅取消及续播进度正确。

### G. M5：缩短播放启动，保留可恢复性

**任务 M5-1：定义原生能力协商。**

- 复用现有播放描述与显式 playback-session 机制；拟定在播放请求中增加版本化的客户端能力描述，包含播放器类型、容器解复用能力、音/视频 codec 与必要的 profile/level/位深/分辨率边界。
- Android 容器支持来自当前 Media3 版本能力，解码能力结合设备 MediaCodec；声明 MIME 支持不等于支持所有码率/HDR/profile，未知情况保守处理。
- 若能力 payload 超出简单 query 的范围，使用现有 POST 会话契约的可选能力对象；不能把大段设备能力塞进 User-Agent。具体路由在 M0 样本与 contracts 设计时固定。
- 旧客户端仍走现有规则；新 Android 连接旧 Server 也走原 descriptor。只有 Server 声明理解该协议才发送并依赖新能力。

**任务 M5-2：选择 direct / remux / transcode。**

- 对设备实际可解码且容器可播放的源选择 direct；仅容器不匹配且音视频能复制时 remux；音频不兼容优先评估仅转音频；视频不兼容才视频转码。
- 当前 HLS 的输出 codec 约束必须保留验证。不能因为手机可解 HEVC 就自动认定当前 HLS remux 输出链路支持该 HEVC 源。
- 保留用户强制推流设置、文件选择、源校验、起播位置与进度；同一影片不同文件不能共享错误的能力/探测结果。
- descriptor 返回稳定的决策原因；记录实际使用模式和编码器，便于定位个别慢片。

**任务 M5-3：Android 播放状态机。**

- 将初始化分为获取描述、准备、首帧、播放、恢复、失败、释放；初始化失败后允许重试，不因提前写 initializedMovieId 而永久跳过。
- 解码/容器不支持可执行一次受控服务端 fallback，沿用实际 position；认证、404、取消不触发无意义转码。服务端已降级的请求不得在客户端形成循环。
- 退出、切片与新会话替代时取消旧请求、关闭旧 HLS session；保留服务端过期清理兜底，播放进度写回绑定原服务器和 fileId。
- 能力支持不代表网络能满足原码率。直播放持续缓冲时提供明确的较低码率策略或后续受控切换，但不因一次短抖动自动创建多个转码会话。

**任务 M5-4：按证据调整 HLS 预缓冲。**

- 先消除不必要转码，再对仍需 libx264 的样本比较首段/多段启动策略。
- 保留首片段和 init 完整性验证；根据编码速度、网络吞吐与重缓冲数据选择预缓冲，不能直接删除现有第 4 段等待规则。
- 首次版本不增加整个视频预下载；会话并发与生成队列有界，不用更多 FFmpeg 进程换首帧。

验证：受支持 direct、remux、音频不兼容、转码、续播、seek、重复点播放、退出、锁定、断流、30 秒以上持续响应、多文件与旧 Server。每种主要模式进行至少 10 分钟稳定性播放，记录首帧、重缓冲、CPU、丢帧和进度写回；当前实际慢片必须列入验收。

### H. 候选性能目标与硬性正确性门槛

以下性能数字是规划目标，M0 完成后基于同一参考网络/设备校准并记录原因；不代表已经达到，也不以换网络、降低画质或排除慢样本来达标。

参考条件：手机前台、稳定局域网、无其他大流量任务、正式等价构建、755 部库；图片区分派生图已生成与首次生成，播放区分探测冷/热。

| 指标 | 候选目标 / 硬门槛 |
| --- | --- |
| 首页新协议业务 JSON 请求 | 1 次，逐片完整详情请求 0 次（硬门槛） |
| 首页摘要可用 | P95 ≤ 1 秒；计时从打开页面到所需文字/卡片可交互，不计骨架为完成 |
| 首张封面 / 首屏图片全部完成 | 派生图就绪、客户端冷缓存下，P95 分别 ≤ 1.5 / 2 秒；首屏按固定 viewport 的实际可见项定义 |
| 再次打开同页面 | 合法内存缓存内容 P95 ≤ 300 ms；网络刷新单独计时，不能跳过鉴权失效处理 |
| 图片体积 | 320 档候选 P95 ≤ 80 KB，640 档 ≤ 180 KB，960 档 ≤ 300 KB；视觉检查不过关时调整预算并说明 |
| 首屏图片总字节 | 同一画质验收样本争取减少 ≥ 50%；原本已小的图不强求再次压缩 |
| Server 50 条列表 | 本机正常磁盘 P95 ≤ 100 ms；慢文件检查不占住唯一 SQL 连接（后者为硬门槛） |
| 已支持 direct 的视频首帧 | 热探测、参考网络下 P95 ≤ 2.5 秒；重缓冲单独验收 |
| remux / 视频转码首帧 | remux 候选 P95 ≤ 4 秒；软件转码按基线争取降低 ≥ 30%，不设跨设备统一绝对门槛 |
| 播放稳定性 | 同样本重缓冲率不得出现明确回归；静音、续播错位、会话泄漏均不允许 |
| 取消与鉴权 | 取消能终止底层请求；旧请求不发布；AUTH_LOCKED 不保留可见私有内容（硬门槛） |
| 缓存正确性 | 不跨服务器/认证代次误用；源修改后在已定义失效窗口内更新；容量有界（硬门槛） |

### I. 验证命令、文档与回退

每个行为单元运行相关测试，批次集成时执行受影响模块完整验证；无新增失败或疑点时不反复跑全仓库。

Server 工作目录为 `jav-lib/jav-shadcn/backend`：相关 storage/server/app/playback 包测试，批次完成后 `go test ./...`、`go vet ./...`。图片新模块加入测试范围。Go 缓存保持系统默认目录。若新增 Web 调用方，再按统一构建文档运行 pnpm 对应检查。

Android 工作目录为 `curated-droid`：按变更运行 `./gradlew.bat :data:testDebugUnitTest`、`:app:phone:testLibreDebugUnitTest`，批次运行 `:app:phone:assembleLibreDebug`、`:app:phone:lintLibreDebug`；格式检查使用项目已配置的 ktfmt 任务。性能测量使用 release 等价包及真机。开始实施时核对实际 Gradle/JDK 与任务可用性；本次计划没有执行构建或声明测试通过。

兼容矩阵必须覆盖：旧 Android＋新 Server、新 Android＋旧 Server、新 Android＋新 Server；旧 Web/Electron 的推荐响应与图片字段不变。新 Server 先交付兼容能力，Android 后接入；不要求用户同时升级两个端。

回退按行为边界执行：

- 摘要协议：保留旧请求路径，服务端撤销对应能力后客户端回退；网络/鉴权错误不作为隐藏回退理由。
- 派生图：撤销变体声明并继续原图片 URL；派生数据可保留，不碰原始资源。版本化 URL 防止错误图长期污染缓存。
- 内容缓存：关闭新增内存缓存策略即恢复原请求路径；不依赖不可逆数据库迁移。

1. Server 封面/演员头像资产查询在磁盘检查前关闭 SQL rows；回归测试在文件检查过程中执行另一个 SQL 查询，确认不占住单连接。未直接增加 SQLite 连接池或引入状态 TTL。
