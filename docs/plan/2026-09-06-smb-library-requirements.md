# Curated SMB 影片库需求、实现方案与实施计划

日期：2026-09-06  
状态：产品范围已确认，新增“SMB 不在线时不展示对应影片”；本文件为待实施技术方案，所有新增接口、字段和时间参数均非现状。尚未实现或进行真实 SMB 联调。

## 1. 原始需求与理解

用户原话：“有个需求是需要支持 smb 目录，请你理解我的原始需求，并告诉我需要做什么需要确认什么”。

用户后续明确：Curated 可能运行在 Windows 电脑，共享由飞牛 NAS 的 SMB 服务提供；接受系统中连接共享，也接受应用内填写地址和账号密码；需要完整读写、多种设备观看、新影片自动发现；数量不定，典型单片 4–6 GB。

用户进一步确认：首版仅支持局域网观看，外网后续考虑；删除 NAS 影片先移入共享内的回收目录，之后可清理。

用户最新明确：SMB 不在线时，不展示对应的视频文件。此前“离线时浏览已保存影片资料”的建议被本条替换：资料仍在数据库保留，但正常浏览入口隐藏对应影片，在线恢复后自动重新显示。

需求定义：以 Windows 为首个验证平台，将飞牛 NAS 的 SMB 共享作为正式影片库，支持扫描、资料管理、播放、导入、整理移动/重命名、删除源文件和 NFO/海报写回。自动发现其他设备写入 NAS 的新影片，并处理网络离线、权限变化和恢复。

两种连接方式均可接受，表示实施路线可选择，不等于用户要求首版同时交付两个连接入口。完整读写表示具备这些能力，不表示添加共享后默认执行所有写操作。仍沿用明确的整理设置和具体操作意图。当前以影片库为范围；没有据此扩展漫画库、NAS 部署或离线下载原片。

## 2. 当前代码事实

| 环节 | 已检查的证据 | 对本需求的意义 |
| --- | --- | --- |
| 前端路径 | `src/lib/path-validation.ts` 接受 UNC、Windows 盘符和 Unix 绝对路径 | 已存在输入 UNC 的基础，但校验较宽松；不接受 `smb://` |
| 后端路径 | `backend/internal/storage/library_paths_repository.go` 使用 `filepath.Clean/IsAbs` | Windows 后端可按 OS 路径处理 UNC；其他平台应使用对应挂载路径 |
| 扫描 | `backend/internal/scanner/service.go` 使用 `filepath.Walk`，遍历错误返回 | 可以复用 OS 文件访问，但需要验证网络断线、部分目录失败与大库性能 |
| 直播放 | `backend/internal/storage/movie_stream.go` 验证库根后 `os.Stat/Open`；`backend/internal/server/server.go` 使用 `http.ServeContent` | OS 可读取的 SMB 文件有机会复用 Range/seek 链路，尚无本轮实测证据 |
| 存储状态 | `backend/internal/storagehealth/probe_windows.go` 可解析 UNC 根并识别 remote drive；`checker.go` 比较卷身份 | 已有基础；网络身份稳定性、错误分类和阻塞调用需要专项验证 |
| 写权限 | `checker.go` 当前按 online 设置 `CanImport`，probe 只检查读取 | 在线不代表可写，必须为只读共享明确操作能力 |
| 自动更新 | `backend/internal/librarywatch/watcher.go` 使用 fsnotify，文件注释指出网络文件系统通知可能不可靠 | 不能直接承诺 NAS 上新增文件总能实时发现 |
| 文件整理 | `backend/internal/library/organize.go` 使用 Rename，失败可走 copy + remove | 启用写操作前需验证 SMB 中断、冲突与失败收尾 |
| 删除 | `backend/internal/storage/movie_delete_repository.go` 先提交数据库删除，之后忽略文件删除错误 | 网络删除不能直接以此流程作为可靠交付，需要操作记录、明确失败和恢复流程 |
| 当前回收站 | `backend/internal/storage/movie_trash_repository.go` 的 TrashMovie/RestoreMovie 只修改 trashed_at；永久删除才调用 DeleteMovie | 当前逻辑回收不等于文件已移入共享回收目录，必须补实际文件操作 |
| 影片查询 | `backend/internal/storage/library_repository.go` 共用过滤条件执行 COUNT 和分页；影片以 location 保存路径 | 新可见性约束必须在数据库查询分页前生效，并建立稳定库根归属 |
| 首页推荐 | `backend/internal/app/homepage_daily_recommendations.go` 可能直接返回已存当日影片 ID 快照 | 即使列表加过滤，推荐快照仍需按实时可见性校验 |
| 当前健康查询 | `backend/internal/app/app.go` 中 ListLibraryPathStorageStatus 调用逐路径实际检查；binding 写入将 last_status/last_error 置空 | 不能直接把现有 GET 或 binding 表当作可靠的非阻塞状态快照 |

现状结论：已有“操作系统可访问的网络路径”的技术基础；不能据此声称完整 SMB 支持已交付。当前媒体源模型仍以 OS 文件路径为核心。

参考既有相关研究：`2026-07-18-webdav-library-storage-feasibility-plan.md`、`2026-07-18-container-deployment-feasibility.md`。SMB 与 WebDAV 协议不同，本文件独立记录 SMB 决策，不直接照搬 WebDAV 适配实现。

## 3. 最关键的产品选择

| 路线 | 用户体验 | 实施范围 |
| --- | --- | --- |
| A：系统负责 SMB 连接 | Windows 已登录共享后，在 Curated 添加 `\\NAS\Movies`；也兼容映射盘。Linux/macOS 使用挂载目录 | 优先验证并修补现有扫描、播放、健康检测、写权限与恢复行为 |
| B：应用内连接，使用 OS SMB 能力 | 在 Curated 填服务器、共享、账号和密码，由应用建立系统连接 | 增加连接配置、凭据安全存储、会话重连及 Windows 同服务器多账号冲突处理；媒体 I/O 可能继续复用 UNC |
| C：原生 SMB 客户端 | Curated 独立连接 SMB，媒体访问不依赖预先挂载 | 增加存储类型、凭据引用、SMB 会话、目录遍历和随机读取；适配现有 OS 路径业务和 FFmpeg 输入 |

“应用内填写账号”不自动等于必须选 C，应先根据平台选择 B 或 C。A 在 Windows 上无需强制映射成盘符，可直接使用已授权的 UNC。

结合用户反馈，建议：以 Windows + 路线 A + 完整读写 + 自动发现作为首版交付范围。路线 B 可作为随后增加的连接便利功能；目前无需为了 SMB 重写成路线 C。先做只读链路验证可以是内部技术步骤，不能作为本次需求的最终交付。

媒体链路建议保持：NAS 经 SMB 提供原片 → 运行 Curated Go 后端的机器读取 → 桌面或浏览器经 Curated HTTP 播放。共享目录必须对后端可见；远程浏览器本机可见的共享并不自动对后端可见。外部播放器直接访问 NAS 属于另一条播放链路，需另行确认。

## 4. 需要完成的工作与实施顺序

### 4.1 共享接入与状态

- Windows 优先使用稳定 UNC，兼容已有映射盘；识别不完整共享路径与同一共享的重复添加，不能仅按字符串判断全部别名。
- 在后端运行账号下验证系统 SMB 会话，覆盖注销/重启与 NAS 重启后的访问。默认检查 SMB 2/3，实际版本以飞牛配置和协商结果为准。
- 区分在线、不可达、权限不足、目录缺失；将可读与可写分开。写能力测试使用独立临时文件清理验证，不触碰现有影片；实际操作仍需逐次处理权限变化。
- 单共享失败不得拖住设置页、启动和其他库。Go context 超时不能自动中断所有 Windows 阻塞文件调用，实施时需验证隔离与有界并发，避免无限积累挂起任务。

### 4.2 自动发现与文件写入完成判断

- fsnotify 用于尽快触发发现，周期目录对账用于补偿丢失事件；重连后补扫，并恢复监听。
- 建议默认每 5 分钟启动一次补扫，可配置；不并行堆积同一共享的扫描。该数值是初始建议，不保证未知规模目录能在 5 分钟内遍历完毕，需展示上次完成时间和扫描进度。
- 目录对账主要比较路径、大小、修改时间，避免每次读取 4–6 GB 全片或重新刮削未变影片。初次全库扫描与后续变更处理分开，使用有界批次。
- 忽略下载临时文件、导入 staging、Curated 回收目录和自身缓存。至少两次间隔检查大小/修改时间稳定后才处理候选文件；稳定时间只是启发式，不能证明外部下载已完成。优先推荐下载工具完成后重命名/移入正式库目录；探测失败可延迟重试，不对明显写入中的影片整理或移动。
- 合并重复事件；自身导入、整理和写回不能触发循环刮削。保留稳定影片 ID，维护路径变化与资料关系；外部重命名无法可靠识别时保留待核对记录，不自动合并不同影片。
- 不完整扫描、断网不判定源文件被删除；完整扫描发现缺失时建议保留资料并标记源文件缺失，自动清除评分/收藏不在默认范围。

### 4.3 完整读写

| 操作 | 需要达到的行为 |
| --- | --- |
| 导入/上传到 NAS | 分片或流式写入 staging，失败可恢复或明确清理，完成校验后发布成正式文件，监听忽略半成品 |
| 整理/重命名/移动 | 同共享优先 rename；按错误类型判断是否允许复制回退，不把权限/断线统一当成跨设备；复制成功、关闭与校验完成后才删除源，冲突不静默覆盖 |
| NFO/海报写回 | 使用临时文件再替换并处理冲突/失败，避免断线留下半份正式文件；本地缓存与共享资源身份要一致 |
| 删除原片 | 按用户选定的回收或永久删除语义执行；文件失败不可静默报成功，保留操作状态及重试证据，避免先丢资料再发现文件未删除 |
| 资料编辑 | 评分、收藏、评论和进度仍写本地数据库；有写回意图的字段按现有/补充写回规则处理 |

SMB 文件系统与 SQLite 没有统一事务，应使用可持久恢复的操作状态，覆盖“文件已改、数据库尚未更新”以及“远端结果未知”的中断窗口；重试必须先核对状态，不能重复覆盖或删除。写操作路径必须限制在所配置共享库根与受管理目录中。

用户已选择共享内回收目录。需要处理同名冲突、保留原路径与资料关联、恢复操作以及手动清理；默认不自动到期清理。回收失败不能回退为永久删除，也不能将失败报告为成功。不能宣称一定进入 Windows 回收站，也不能假设飞牛 SMB 回收站已启用；是否采用飞牛原生回收能力需实测后决定。

### 4.4 多设备播放与本地资源

- 统一链路为飞牛 NAS → SMB → Windows Curated 后端 → HTTP → 桌面/浏览器/手机平板。运行后端的电脑必须开机且可达。
- 本机外部播放器可评估 UNC；远程外部播放器优先评估可访问的 HTTP 媒体地址，必须验证应用 PIN/会话认证兼容性，不能把本机 UNC/localhost 地址直接发给远程设备或无条件放开媒体访问。
- 验证直接播放、Range/seek、ffprobe、HLS/转码、字幕、封面、截图/GIF以及两个设备同时播放的会话隔离。兼容具体播放器和编码需形成测试矩阵，不承诺所有播放器/格式通用。
- 数据库、运行配置、日志和转码缓存放在 Windows 本地；NFO/海报按写回设置可保存到 NAS。本地缓存需要容量与清理策略，不默认整片下载。
- 4–6 GB 是样本大小，不足以判断播放码率；以真实片长、编码、峰值码率和网络条件验证起播/拖动。没有影片总量上限承诺，先用分批扫描和增量处理适应增长。

### 4.5 应用内连接作为后续便利入口

两种连接方式均可接受，首版系统 UNC 已满足连接要求。若随后增加应用内入口，优先调用 Windows SMB 能力；后端管理连接配置，凭据使用系统安全存储/加密引用，不写进 URL、日志或明文配置。需处理同服务器不同账号的会话冲突，不能为连接 NAS 擅自断开其他程序的共享会话。跨设备网页提交凭据时需另行完善传输与授权边界。

### 4.6 文档和验证

实施前按仓库构建测试规范明确合约与检查命令；实施后同步 API、项目事实、操作手册与架构说明，重要配置变化按仓库规定更新相关文档。真实飞牛 NAS 验收是必要环节，不能只以本地临时目录单测宣称完成。

## 5. 已确认、待确认与建议默认值

已确认：飞牛 SMB、Windows 首个候选运行平台、两种连接体验均可接受、完整读写、多种观看终端、自动发现、单片 4–6 GB、影片数量不定。

用户已答复的最终边界：

1. 首版只支持同一局域网内观看，外网后续考虑。
2. 删除 NAS 影片先移入共享内回收目录，之后可清理。

当前没有阻碍需求定稿的产品问题；后续主要是目标 NAS 环境联调及实施默认参数的校准。

可先用于规划的建议默认值：

- Windows 系统连接 + UNC 为首版入口，应用内账号管理后续补充；完整读写和自动发现仍属于首版。
- 监听 + 默认 5 分钟补扫，可配置；大库扫描不重叠，实际发现延迟包含文件稳定等待和扫描用时。
- 本地 SQLite/运行配置/转码缓存；NAS 保存原片及按设置写回的伴随资料。
- 外部删除/缺失保留本地资料并标记，不自动清空记录。
- 回收项目保留用于恢复的路径及资料关联，支持恢复和明确确认后的手动永久清理；不默认定时清空。
- 首轮同时播放用两个设备做基线验收；更多并发及外网性能另据硬件和带宽评估。

真实联调前需要的环境信息：飞牛系统版本、Windows 版本、可测试共享路径、局域网连接方式、两部代表性 4–6 GB 影片及使用的播放器。账号在系统/应用中配置，不在对话中收集密码。网络速度与影片数量无需现在精确回答，不阻碍需求定稿。

## 6. 完整首版验收场景

- 已授权 UNC 共享可添加、扫描、重启后重新访问；中文/空格路径与嵌套目录可用。
- 4–6 GB 样本可起播、反复 seek 和按需转码；不用先复制整片。记录实际延迟和吞吐，再依据环境确定性能门槛。
- 本机桌面、远程浏览器/手机和选定外部播放器分别验证；同时两路播放互不挤掉会话，认证与访问范围正确。
- 其他设备在 NAS 新增影片，文件写完后自动入库；丢失监听事件时补扫能发现；正在复制/下载时不整理半成品。
- 导入、整理、写回、删除各自覆盖正常操作、权限收回、目标冲突、NAS 断线、应用重启和重试，源文件及资料状态能核对和恢复。
- NAS 启动前离线、扫描/播放/写入中断线时，正常浏览入口隐藏对应影片，Curated 仍可使用本地库；数据库资料保留，错误不误报成功。
- NAS 恢复后自动重连/补扫并恢复监听，同一影片不重复入库，评分、收藏和进度保留。
- 缺失文件与共享离线正确区分；回收目录和 staging 不会再次被自动扫描入库。
- 若增加应用内连接，补认证失效、凭据更换、Windows SMB 账号冲突与机密不泄露测试。

本轮仅做代码阅读与需求文档更新，没有连接用户 NAS、修改业务代码或验证真实 SMB 兼容性。

## 7. 离线隐藏的产品行为（最新要求）

### 7.1 展示范围

| 入口 | SMB 不在线时的行为 |
| --- | --- |
| 影片列表、收藏列表、已看/未看、保存视图 | 不返回该共享影片；分页 total 只计算可见影片 |
| 搜索结果、自动补全、演员关联影片、标签下影片 | 使用同一可见性范围，不出现不可用影片卡片或标题建议 |
| 首页轮播、每日推荐、继续观看、相似影片 | 过滤缓存候选并按需从在线影片补足；不足时少显示，不用离线条目凑数 |
| 播放队列、自动下一部 | 移除不可用候选，播放前复核状态 |
| 已打开的详情/播放器、历史收藏链接 | 收到状态变更后替换为简洁“存储暂不可用”状态，不继续显示常规影片详情；新播放/seek 被阻止，释放本应用 HLS 会话 |
| 回收站影片列表 | 离线共享的影片行同样隐藏；设置仍展示该共享有待处理回收内容，但不可恢复/清理 |
| 设置中的存储目录 | 保留目录行，显示离线/检查中与重新检测入口；库为空时给出“网络存储不可用，相关影片已隐藏”的原因 |
| 备份、恢复、维护审计 | 后台仍可访问完整记录，用于恢复与一致性核对；不受普通浏览过滤误伤 |

范围解释：本需求隐藏影片入口，不删除演员档案、用户历史统计或独立萃取帧作品。独立帧可继续展示，但关联影片链接禁用；历史播放时长保持真实。影片浏览数量/facet 使用可见集合，历史统计若包含离线记录需明确语义。AI 新查询与结构化影片卡片也使用可见集合；既有聊天原文不改写，历史卡片重新渲染时复核可见性。

外部播放器可能已经缓存视频字节，Curated 无法撤回已发送的数据，也无法保证控制第三方播放器界面；可保证本应用隐藏入口并阻止新的受控媒体访问。

### 7.2 状态与时效

- 独立于影片的 active/trashed 状态，增加共享的 availability；离线绝不通过 DELETE、trashed_at 或清空 location 实现。
- 网络根仅在当前后端会话已确认可读取且快照未过期时可见；offline、unknown、checking（尚无有效成功快照）、authentication_failed、permission_denied、path_missing、volume_mismatch 均不可见。读得了但写不了仍显示并允许播放，禁用写操作。
- 正常周期复查中的在线源继续使用有效快照，不每轮先切换 checking 造成闪烁。首次启动、过期或明确连接失效则隐藏。
- 默认初始参数：健康复查 30 秒、单次探测软预算 3 秒、在线快照有效期 90 秒、前端兜底对账 30 秒、新增影片补扫 5 分钟。健康检测与文件扫描使用独立调度器；这些是待实测校准值。
- 本应用遇到明确共享不可达时立即失效状态；单文件不存在只标记该文件，不能据此隐藏整个共享。软超时将来源设为 unknown 并隐藏，恢复成功再展示。
- 无活动故障提示时，默认目标是在下一次健康检查完成并同步后隐藏，约 30–35 秒；不是拔网线瞬间可知的硬实时保证。排队/系统阻塞时由快照有效期兜底失效，并将超预算作为验收失败排查。
- 后端启动生成新 sessionEpoch，旧持久化 online 仅用于诊断，不直接授信。前端不得先展示上次缓存的网络影片再隐藏；先取得当前状态快照再渲染网络影片。本地来源可独立展示。
- 恢复时确认目标库根可读且身份匹配，切换 online 后已有影片立即重现，后台补扫新文件；不要求先扫描完整个大库。每个原片仍在实际打开时检查，发现缺失则单片处理。

## 8. 实现架构与数据设计

### 8.1 总体路线

复用现有 Vue service contract → Go HTTP → Windows 文件系统 → SMB 链路。Electron 保持窄目录选择桥，首版不引入通用远端文件系统重写，也不将 NAS 密码交给前端播放组件。

后端增加专职 source availability coordinator（建议 `backend/internal/librarysource`），编排已有 storagehealth 探测、只读状态快照、过期失效、状态事件和网络源读写准入。storagehealth 保留底层平台探测职责，storage 负责持久化和显式查询范围，不在 SQL repository 中执行网络检查。

### 8.2 持久化模型（字段命名草案）

| 表/字段 | 用途 |
| --- | --- |
| library_paths.storage_kind | local / smb_os，显式标记网络根；映射盘在线时解析并记录 UNC，离线时不因 GetDriveType 失败退化成本地来源 |
| movies.library_path_id | 关联来源根，并建索引；路径迁移、导入、整理和扫描均维护，不靠请求时字符串模糊匹配 |
| library_source_states | library_path_id、session_epoch、revision、status、readable、writable（可含 unknown）、checked_at、valid_until、last_online_at、error_code |
| library_file_operations | 操作 ID、幂等键、影片/库根、kind、phase、源/目标清单、验证证据、错误与恢复状态 |
| library_trash_entries | 对应既有 trashed_at，记录 operationId、原位置、回收位置、受管理文件清单、回收时间及恢复状态 |

迁移序号按实施时实际 migration 最大值生成，不预占。新增归属字段先回填再启用过滤：使用路径段边界和最长匹配根，Windows 大小写/分隔符归一化，不能用 location LIKE 'prefix%'；冲突/无归属网络条目保持不可见并产生维护问题，不静默归为本地。

UNC 和映射盘可能指向同一共享，需规范化来源并报告重复配置；已离线且无法解析的映射盘归属保留为未确认，不猜测。影片已存在稳定 movieId，正常断线恢复不创建新 ID。多文件多来源不是现有单 location 模型的假定能力；若实施发现实际多文件模型，按可播放主来源定义可见性再扩展映射。

### 8.3 统一查询范围与一致性

在应用层区分 `BrowseVisible` 与 `MaintenanceAll` 内部查询范围，普通影片 API 固定 BrowseVisible，不给普通前端开放随意绕过的 includeOffline 开关。维护、备份、迁移、回收恢复、已存在影片去重按目的使用完整记录，避免离线过滤后再次扫描造成重复入库。

SQL 查询通过 movies.library_path_id JOIN 状态表：本地影片沿用原规则；SMB 影片要求当前 sessionEpoch、online、readable 且 valid_until 未过期，再叠加既有 active/trashed 与业务过滤。未知网络归属不可见；本地来源不因无网络状态行而整体消失。

COUNT、分页 items、facet、列表数量必须使用相同谓词及同一读快照，状态更新和 revision 递增在同一事务提交；列表读取使用短读事务，返回对应 visibilityRevision，避免离线发生在两次 SQL 之间导致 total/items 不一致。

统一审核所有影片投影：普通列表、批量 ID 查询、搜索索引、演员/标签关联、收藏/已看、首页快照、推荐反馈呈现、播放列表、AI 本地检索。不能只改 ListMovies。

首页已存每日推荐 ID 仍可保留，但返回前按当前范围过滤/补足；在线恢复不删除推荐反馈或曝光历史。所有响应/前端缓存使用 sessionEpoch + visibilityRevision 识别是否过期。

详情/播放单片读取区分“影片不存在”和“来源不可用”。面向浏览的详情接口不返回离线影片正常 DTO；内部维护可读取完整记录。媒体、HLS、ffprobe、字幕和截图等入口执行来源准入，之后仍检查实际文件 I/O 错误；不把缓存中的视频分片当成来源在线证据。

### 8.4 探测与任务隔离

现有 GET storage-status 会逐路径探测，应改为快速读取状态快照。主动检测合并重复请求，通过任务调度执行，单来源同时最多一次检查，SMB 探测全局建议最多两个 worker。

Windows os.Stat/卷查询可能不可中断：单纯超时返回的 goroutine 方案不足以保证资源边界。先用故障演练验证；生产验收需要真正可取消的 Win32 调用，或受控的独立探测辅助进程，超时后终止并回收。网络目录扫描/写入如存在相同无限阻塞，也必须纳入可中止 worker/恢复操作状态，不只修健康探测。

来源身份绑定与瞬时在线状态分开保存。不要继续用现有 binding Upsert 空状态字段代表健康状态；不要仅凭 NAS 卷序列号变化自动重新绑定或接受新共享。

### 8.5 HTTP/事件合约草案

| 合约 | 计划变更 |
| --- | --- |
| GET /api/library/paths/storage-status | 保留现有 items，扩展 sessionEpoch、visibilityRevision、readable/writable、validUntil 与稳定 errorCode；无网络等待 |
| POST /api/library/paths/storage-status/check | 前后端同批升级为检测任务回执 `{taskId}`，经任务/SSE 获取结果；记录这是现有同步响应的兼容性变化，更新所有调用方和 API 文档 |
| GET /api/library/movies 及相关影片查询 | 默认应用 BrowseVisible；分页/聚合一致，返回 visibilityRevision |
| GET /api/events | 复用现有 SSE 传输，新增 `library.source_state_changed`，携带来源 ID、状态、sessionEpoch 和 visibilityRevision；不携带密码或影片全表 |
| 回收/恢复/清理操作 | 沿用现有业务入口，升级为可追踪文件操作任务；增加回收 manifest 和冲突错误，不能只更新 trashed_at |

建议错误：`LIBRARY_SOURCE_UNAVAILABLE`（HTTP 503，可重试）、`LIBRARY_SOURCE_READ_ONLY`（403）、`LIBRARY_FILE_CONFLICT`（409）、`LIBRARY_OPERATION_RECOVERY_REQUIRED`（409）。按仓库已有错误目录核对去重后落地，不把 SMB 登录失败混同 Curated PIN 会话失效。

现有 SSE 从 tasks.Subscribe 取事件，实施时需明确事件总线的领域事件支持，不能假设加入一个事件字符串就已连接全部客户端。事件提交后发布；订阅掉线允许丢增量，但重连/hello 必须获取权威快照。仅在有意义状态变更时增加 revision，普通成功心跳不反复清空列表。

### 8.6 前端落点与竞态

- 在 `src/api/types.ts`、guards/endpoints、`src/services/contracts/library-service.ts`、Web/Mock adapter 增加来源状态、影片来源 ID 与 revision。
- `src/lib/backend-events.ts` 接收新事件，service 统一剔除受影响来源的已缓存影片并重新请求列表/统计/推荐。组件不各写一套路径前缀过滤。
- 丢弃旧 epoch/revision 的迟到请求结果，取消进行中的受影响请求；翻页到空页时回到有效页。SSE 不可用时按 30 秒拉快照，窗口重新聚焦立即对账；快照过期且后端不可达时本地网络影片缓存也隐藏。
- 设置显示“离线，相关影片已隐藏”，保留重新检测；不在普通影片列表摆一批灰色离线卡片。
- `use-player-playlist.ts` 与 active playback session 响应统一来源事件，处理当前影片消失、队列变空和自动下一部。详情路由/播放器替换为不可用状态，禁止离线后继续截图/生成 GIF。
- Mock 覆盖 online/offline/checking/read-only/recovery，避免伪造真实 SMB 连通性。

## 9. 分阶段实施计划与完成门槛

阶段按依赖顺序推进，每个阶段按最小行为单元提交；不进行并行 Agent 实施，除非用户后续明确要求。当前仅输出计划，不自动开始业务代码开发。

| 阶段 | 工作内容及主要落点 | 完成门槛 |
| --- | --- | --- |
| P0 基线与迁移预检 | 确定当前 schema/API/回收入口，隔离测试共享；枚举所有影片投影；设计 DTO 和归属回填 dry-run | 列出可复核归属/歧义报告；UNC 测试路径可读写；无真实影片被移动或删除 |
| P1 来源状态基础 | contracts/migrations、storagehealth、librarysource、app 编排；状态快照、会话 epoch、过期失效与任务隔离 | 启动不授信旧 online；单源故障不阻塞本地库；读取状态无 SMB I/O；超时 worker 不泄漏 |
| P2 离线隐藏闭环（最高优先级） | library_repository 与所有影片投影、推荐缓存、API/SSE、service/页面缓存、详情和播放准入 | 断线后各普通入口无该源影片；分页准确；迟到响应不回填；重连无需全库重扫即可恢复原 ID 资料 |
| P3 自动发现与恢复 | librarywatch/scanner、每源扫描状态、补扫调度、写入稳定判断、重连补扫 | 外部新增能被自动发现；半成品不整理；事件遗漏能补偿；自身写入不循环刮削 |
| P4 完整读写可靠性 | library_file_operations、导入 staging、organize/NFO/资源写回；结果校验与恢复任务 | 导入/移动/写回覆盖断网/权限/冲突/重启，来源和数据库可核对，失败不能静默成功 |
| P5 共享文件回收 | 扩展现有 movie_trash、共享内 manifest、恢复/清理任务与 UI | 文件确实进入共享回收目录；资料关联保留；回收目录不入库；恢复冲突不覆盖；回收失败不永久删除 |
| P6 局域网联调与发布门禁 | 飞牛真实共享、Windows/浏览器/手机/选定播放器，直接播放/HLS/字幕/GIF、双客户端；同步文档 | 全自动化门禁与真实故障矩阵通过；明确实际性能与播放器支持范围 |

P2 先交付新增核心诉求，但只有 P0–P6 全部完成，才算本次完整 SMB 需求交付。应用内账号连接列为后续 P7 便利功能，系统 UNC 接入已经是用户接受的方案；不因此削减完整读写、自动发现和局域网播放。

不在未连接目标 NAS 前承诺固定工期；P0 后根据不可中断 I/O、旧数据归属和外部播放器认证验证结果细化估时，不以“改路径输入框”的工作量估算。

## 10. 测试与验收清单

### 10.1 自动化必测

- 归属迁移：UNC/盘符别名、中文/空格、相似路径前缀、嵌套根、未匹配记录和回填重跑；不更改原 movieId/评分/收藏。

- 查询：混合本地/两个 SMB 根，COUNT/items/facet 一致；收藏/已看/搜索/推荐缓存/演员关联/AI 输出一致；维护导出和去重仍包含隐藏记录。
- 前端：首屏不闪旧网络影片、事件后所有入口隐藏、旧请求迟到、SSE 断线重连、后端重启、分页越界、播放器当前影片消失和缓存有效期失效。
- 同步：外部慢复制、临时扩展名、写入中暂停、监听漏报、两轮扫描合并、NAS 重连、自身 rename/写回事件、回收和 staging 排除。
- 文件操作：每个持久状态边界故障注入、幂等重试、目标冲突、共享中断/恢复、多个文件部分完成、回收失败/恢复失败/清理失败；不能丢失操作证据。

### 10.2 实机矩阵

至少准备一个本地库、飞牛共享 A 和共享 B（可为同 NAS 不同根），测试 NAS 全离线与仅一个库根无权限两种情况。两部 4–6 GB 测试片覆盖浏览器可直播放与需转码格式；所有写操作只使用隔离测试副本。

记录冷启动耗时、健康检查时长、离线到隐藏延迟、恢复到显示延迟、新文件发现延迟、初次/增量扫描耗时、起播/seek 延迟、双播放内存/吞吐、worker 数量与恢复结果。要求断开 A 只隐藏 A，B/本地库可继续使用；全 NAS 关闭则隐藏其所有关联库。

默认目标为正常环境中共享确认离线后立即更新服务端范围，前端收到事件后立即隐藏；无事件时由健康复查与快照兜底。不能宣称当前任一时间参数已经经过飞牛实测。
